# 据点交互区域配置与物品系统建议

> 当前M6-T1反馈批。区域设置对应本批实际组件；物品系统部分是建议，尚未增加新物品、配方、掉落或使用效果。最终验证结果见验收记录。

## 1. 你怎样在Editor配置三个区域

先退出Play Mode，打开正式SinglePlayer_Hub。展开`__HubInteractions`：

```text
仓库与魔法整备 · E
  WarehouseArea_仓库区域
据点商店 · E
  ShopArea_商店区域
实验平台 · 真实库存
  ExperimentArea_实验区
```

选择对应Area子物件。Inspector上有`BoxCollider`和`HubAreaVolume`两个组件：前者存储盒子的形状，后者让游戏读取这份形状。勾选Scene窗口的Gizmos，就能看到范围线框。点击BoxCollider的**Edit Collider**，拖动各面的控制点改范围；也可直接输入**Center**（盒子相对物件的中心偏移）与**Size**（完整宽/高/深）。把区域覆盖在你想让玩家交互的地面上，垂直高度需包含角色根点、台阶和允许站立的平台。盒子**Is Trigger保持勾选**，避免区域成为实体墙；BoxCollider与HubAreaVolume都要启用。

商店初始12×6×14m、仓库12×6×12m，只是本批可调整的起始范围，不是锁死规则。它们跟随各自站点物件，站点位置仍由你原有分布确定；避免把商店和仓库盒子重叠。实验盒子是你已扩大平台的子物件，X/Z覆盖整个平台，Y方向增加约6m许可高度；移动/旋转平台会一起移动范围。

**Center/Size都是Local Space（物件本地空间）参数。** 例如实验平台Y缩放为0.3，子盒子的Size.y=20，在世界里高度是20×0.3=6m。平台X/Z缩放约9.45/10.58，所以子盒子Size.x/z=1就覆盖完整平台。看Gizmos确认世界里的实际大小，不能把这些本地数字直接当世界米数。当前允许判断的是角色根Transform.position，而不是相机或手里法杖；区域底面应包含根点，上界为半开边界，站在上界外不算进入。

`__Systems/SinglePlayerInventory`上的引用已经接好：

| 组件字段 | 应指向 |
| --- | --- |
| HubInteractionController → Warehouse Area | WarehouseArea_仓库区域的HubAreaVolume |
| HubInteractionController → Shop Area | ShopArea_商店区域的HubAreaVolume |
| ExperimentAreaController → Area | ExperimentArea_实验区的HubAreaVolume |

平常只调整盒子，不要把引用清空。为空是兼容旧Sandbox的入口，会退回HubDefinition旧点/实验SO规则；本版正式据点使用实际Scene盒子。重命名Area不影响已序列化引用。如果你新建一个区域，创建空GameObject，添加HubAreaVolume（Unity自动补BoxCollider），设置Is Trigger与尺寸，然后把新组件拖到对应字段即可；不需要Rigidbody，不用自己写OnTriggerEnter。

**为什么不依赖物理进入回调？** 本游戏只需知道单个玩家“现在是否在区域内”，直接把世界位置转到盒子本地空间判断。瞬移、加载、Tab暂停、关掉Collider后都能立即得到真实结果，不会留下上次进入的缓存。BoxCollider在这里也是Editor的直观绘制工具，不承担阻挡玩家的职责。Play测试后请在Edit Mode自行保存需要保留的尺寸；不要只改Play中的临时对象。

**配置UI时，隐藏内部Panel，保持挂控制器的Canvas根物件启用。** 关闭整个GameObject会执行OnDisable，控制器因此退订EventBus；此时即便区域内E请求成功，也没有入口消费者来打开它。商店与仓库已按“根常驻、面板默认隐藏”接线；不想显示的交互提示Canvas可以继续关闭，它已不承担这两个入口的打开职责。也可只暂时关闭Canvas组件预览其他界面，预览完成后重新启用；不要关闭挂入口控制器的根物件。

## 2. 背包格子与准星的配置入口

背包网格Content上的`InventoryGridView`：**Cell Size=72、Fit To Viewport关闭**。容量仍从装备背包定义读取8×8；72决定每格可读尺寸，不改变资产容量。GridViewport的`ScrollRect`指向原Content，Horizontal/Vertical Scrollbar已接两个子物件。两方向内容超出视口时出现滚动条，可拖动或用滚轮；Viewport负责裁切，Content保存完整格子。UI用`Scrollbar`，数值调节控件`Slider`不适合直接替代库存内容滚动。

你可以把Cell Size调到80或96试读图效果；更大意味着同时可见的格子变少，需要更多滚动。不要重新打开Fit To Viewport，否则程序会为了完整展示8×8再次压小格子。已装备物品的位置还是原坐标；拖动时按移动过的Content换算格子，所以滚到最后一排后仍能准确放置。更改格子大小只在离散Refresh投影，不在Update逐帧重建。

左列增加`BackpackRuntime_Capacity`显示真实“已占/总格数”，用于替代你删掉的旧引用；钱包仍读取真实余额，未额外发放金币。移动这项容量文字只影响显示，不会改变背包格数。

屏幕中心白点移到`__UI/PlayerHUDCanvas_统一手持栏/Crosshair`，独立于停用旧HUD；Canvas上CrosshairUI消费现有角色事件，准星不拦UI射线。开Tab、仓库、商店时随手持HUD隐藏，关闭恢复。小白点是瞄准标记，实际射线仍由原P7角色控制路径读取；没有更改Mouse Look、攻击时机或法杖规则。

## 3. 我推荐物品系统怎么做

你之前列的是**四类**：容器、固体元素、炼金物品、法术。法杖和背包本体也仍是装备资产。推荐在既有定义/实例/归属框架上增加具体内容，不再建一套背包、仓库、商店各自的物品类。

固定配置回答“这类东西是什么”：名称、图标、占格形状、能否旋转、Stack Limit（最大相容堆叠数）、用途与交易规则，存在ScriptableObject定义中。具体实例回答“玩家这一份还剩什么”：唯一身份、数量/次数、材料混合组分、附着等。归属表回答“这一份在哪里”：地面、普通包、法术专区、法杖程序或仓库。金币属于钱包数值，不再放进格子制造第二套余额。

**类别、用途与实例状态分别管理。** 容器是类别，采集/撒出/投掷是用途，装有36水+24毒是这一个实例的状态。花草属于炼金物品，常规花草可以先只作为交易/配方素材；将来允许直接使用的药品再赋使用能力。道具栏4–0只绑定已有使用能力的真实包内实例，不因为“属于某类”就自动变成可左键使用。法术走编程路径，不能把程序复制显示当成多一份资产。

| 类别 | 背包/仓库建议 | 商店与使用建议 |
| --- | --- | --- |
| 容器 | 占真实形状；装料后按组分和数量保存；不同混样不合并。空容器只有规则/状态相容才堆叠 | 优先明确出售空容器；装料容器若可出售需连同真实内容预览计价，不能出售价只看名称。采集/撒出/投掷复用原链 |
| 固体元素 | 原MaterialId与GMU数量继续沿用；拾取/丢弃必须与ElementWorld真实转移，不能免费生成第二份 | 可购买/出售明确剂量，受有限商店预算；每格GMU上限需单独平衡。释放后继续参与材料世界 |
| 炼金物品 | 先做少量花草/生物素材的定义、占格、有限相容堆叠。稀有Boss产物可独占大形状，提高收集取舍 | 首批只交易/持有，等确认配方或消耗效果再赋用途；当前敌人仍按既定法术掉落，不自动增加新Boss掉落表 |
| 法术 | 优先12专区、满后入包；程序/专区/仓库都移动原实例。不同次数/附着/保护状态不混成一份 | 显示具体剩余次数和资格；报价需明确按实例状态，不能把8次与1次永远按同一完整价格收购。无限使用仍受死亡损失 |

**“万物皆元素”应保持材料身份和数量的统一。** 这不要求每棵背包里的草实时跑流体Solver。物品可以保留材料来源或组分，只有实际投入世界/实验时才把真实剂量交给ElementWorld；视觉表示和模拟粒度按游戏用途选择。这能让背包里100份稳定素材不产生100份环境模拟，同时避免库存与世界各自凭空生成材料。

商店建议提供“一次买卖的具体内容和结果”预览：买几份、收到哪种状态、放在哪里、金币增减；空间/货源/预算任一不满足时整笔不提交，不静默掉地或自动存仓库。建议购入法术沿用专区优先规则；普通物品入普通包。这个购买目的地扩展尚未实施，需要在具体物品阶段对现有交易链统一确认。仓库负责储存与跨局资产，容量规则另定，不作为道具栏的远程使用来源。

推荐下一步先用最小的具体物品集合打通真实循环：现有容器、一个固体样本、两种普通炼金素材、一个稀有素材定义和现有法术；逐一验证拾取/排布/存仓/交易/保存/成功返回与死亡。掉落配置、美术图标、定价和Stack Limit做成定义数据，给你自行配置。背包通过后，再按选中类型分支制作右侧详情，展示“身份名称/尺寸和数量”共通信息加各类专有信息。

替代是先把所有素材做成“名字+数量”的通用物品，最快但容易掩盖混样/真实材料转移和法术次数，后续返工多；或直接为每类写独立完整背包/交易逻辑，可定制但规则重复且更难保证原子性。本项目已经有成熟的唯一实例与事务框架，推荐继续扩展数据定义和少量能力处理器。

需要随后集中确定的内容只有会改变玩家资产的新规则：普通素材Stack Limit与占格、装料容器是否可卖/如何计价、有限法术残次收购方式、仓库容量，以及购买法术是否沿用专区优先。上述都是建议，本批不擅自写成确认规则。
