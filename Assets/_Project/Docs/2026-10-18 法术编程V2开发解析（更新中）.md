## 本阶段的学习地图

法杖程序首先是数据：卡牌定义和实例ID描述“有哪些指令”；Compiler将它们冻结为某个版本的Program。一次施法从这根杖当前的deck/discard出发，解释器在候选区执行Draw，形成独立Scope与未来Trigger结构；Scope结束时统一结算最终参数。只有后续Run资源事务成功，候选才成为真实进度。阶段一先做纯规则和独立观察界面，让同一份结果同时回答“会发生什么”和“为什么”，暂不消费玩家资产。

学习顺序为：冻结边界→连续Draw状态→Scope统一结算→Trigger子程序→只读预览与Trace→UGUI观察。理解一个结果时先找所属Scope，再找抽牌调用，最后追溯具体伤害/运动贡献，不能只按屏幕上的左右位置猜测修正范围。

## Task 1：冻结程序与编译边界（代码与自动验证完成）

本Task解决的玩家问题是：研究面板给出的解释必须与实际运行使用同一版规则。如果程序直接保留ScriptableObject引用并在触发时重新读数值，玩家飞弹尚未命中时修改卡序或资产，旧攻击就可能悄悄变样；预览也无法可靠回放“刚才那次”。因此我们先把显示名、Mana、生成方式、伤害、运动修正与时间贡献冻结成只读值，并为每个卡实例保留稳定身份和原始槽位。Prefab、Sprite和AudioClip是Unity资源，允许保留引用，规则数值则不能回读可变定义。这个边界服务后续Runtime、事务和研究台，暂时不改变正式玩家的施法路径。测试先确认V2入口缺失，再验证旧Double配置、非法数值、实例身份与数组别名，避免只写一份看似不可变但仍受外部集合修改影响的数据壳。

### 1. 职责与取舍

- `SpellDefinition`仍是Authoring Data。新增时间贡献与TriggerDrawCount只供V2使用，Legacy忽略这些字段；现有资源GUID保持。
- `SpellProgramCompileInputs`捕获法杖固定属性与实例ID；样例可以自动生成槽位ID，正式Run接入时必须提供真实实例ID。
- `SpellInstruction`/`SpellEmissionData`冻结规则值；`SpellProgram`只公开只读集合，SourceSlot保留空槽前后的作者位置。
- Compiler只校验语义与数值，不代替库存所有权和物品容量校验。纯规则上限1024条用于技术边界测试，真实杖仍受Run的16/32槽规则约束。
- Copy留到T8发布，避免Legacy的未知Kind分支没有推进位置时暴露未实现指令；已发布0—3不变。

## Task 2：连续Draw、Scope与候选执行（代码与自动验证完成）

玩家看到的核心变化是：一次施法不再把整排卡机械重跑，而是从当前deck继续抽牌，抽到的卡暂留hand，结束后进入discard。Modifier和Multicast都能继续请求Draw；deck不足时，允许的嵌套请求可以从discard恢复，但不能回收本次hand中的卡。这样卡序、上次进度与一次请求的边界共同决定构筑行为。另一个关键变化是投射物先登记输出，Scope关闭时才用该Scope的最终参数统一Bake，所以同一Scope中后出现的增伤也能影响较早登记的普通弹。Trigger建立默认参数独立的子Scope，不能把父层的增伤偷偷继承过去。所有未来层都在根构建期间解释并预付Mana，未来命中只释放已冻结的输出；这为后续事务防止免费复制、未来资产变化改写旧飞弹提供基础。

### 1. 数据流与事务边界

`Program + BeforeSnapshot + ExecutionInputs → Machine候选区 → Graph / NextState / Trace / Summary`。`TryBuild`成功表示纯规则候选可用，不表示已经扣玩家资源或射出对象。输入冻结，工作区可复用；成功后输出另存冻结数组，复用工作区不会改写旧结果。拒绝候选时不公开Graph或NextState，原输入保持不变。有限次数用尽的卡退出下一状态，但历史图仍保留其实例身份。Skip与整次Rejected不同：低Mana、无资格或次数为零会记录原因并尝试当前deck后续卡；技术预算超限拒绝整次候选。

显式栈替代C#调用栈递归，限制1024次指令尝试、128输出和16层子Scope。Trace最多16384事件；关闭或截断Trace不能改变玩法结果。冻结结果会在离散构建时分配内存，本阶段未宣称整次构建零分配，后续连续施法需单独Profiler验证。

## Task 3：由同一解释器驱动独立工作台（代码与自动验证完成，等待Editor Gate 1）

这个Task把前两个Task的规则变成玩家可以观察、提问和验证的界面。研究台保留上方的安装顺序，但中间不再只画一排卡，而是把每次实际构建的Scope与Output分层展示；右侧说明基础值、最终Modifier以及贡献卡和Step；下方单步回放Draw调用栈、deck/hand/discard与候选Mana。这样玩家看到的是解释器的执行证据，而不是UI根据卡序猜出来的连线。点击后置增伤时，绿色输出来自相同Scope的贡献记录；点击Multicast时，关联范围来自DrawRequest的父子关系，能跨入真实创建的Trigger子程序。折叠仅影响显示，输出数量和来源保持不变。当前所有内容明确标为Sandbox模拟：构建出未来层不等于未来已经命中或已经在世界释放，这个区别必须在UI中保留。

### 1. 预览为什么不推进真实法杖

`SpellProgramPreview`只用冻结输入调用同一个Machine。每个虚拟Root产生新的AfterSnapshot，下一次模拟接着这个副本运行；调用者提供的Before不变。下一发模式只构建一个Root；整周期模式假设持续输入、外部资格不变，并按`max(Cast,Reload)`等待与ManaRegen推进虚拟时钟，到Reload或预算结束。最多32个Root、1024输出；超出预览输出预算时停止在完整Root边界，不把真实Machine的128输出上限偷偷放大。`FromBeginning`是显式假设：重建牌序而不恢复已消耗的次数，不能冒充真实下一发。

Trace的游标表示“已经消费的事件数量”：0是执行前，N包括第N条事件。输出登记和Scope关闭是两个事件；关闭前只显示“待结算”，不会把最终数值提前标成已生效。未来子层标题是“等待命中/存活到计时后释放（假设）”，没有伪造世界发射时间。参数值直接来自Graph，UI只格式化，不再次实现伤害公式。

### 1. 从执行证据到格子，而不是另写一套解释器

输出图只包含最终投射物，不能拿它当完整卡序：Multicast和Modifier也执行过，却不会单独产出投射物。因此格子投影读取Trace中的ManaPaid与跳过事件，按记录的ScopeId分排；OutputId只用作内部关联，不印在卡面。七卡例的根排是1、2、7，命中子排是3、4、5、6。选中5号时，4、6号格子受影响高亮；上方与下方是同一源卡的映射，没有额外复制Owned物品。

低Mana、无资格和次数耗尽保留“跳过”灰态，不能把它们画成已执行的发射。空子层也保留；例如计时触发没有可读取子卡时，命令可能退化为普通输出，但子排的触发身份仍应取冻结源指令，避免画成命中触发。逐步播放只推进可见的读取/跳过/组结算事件，隐藏内部集合移动和调用编号，完整记录仍能在Editor Review Window查看。

### 2. 为什么缩放画布要分两层

UGUI的RectTransform表示一个矩形及其相对父级的位置。此处模型采用左上角为原点、向右/向下为正的逻辑坐标；放进UGUI时由Place统一把向下的y变成负值。绘图层Drawing持有整幅图，缩放只改它的localScale；外层Extent保持scale=1，宽高取`max(Viewport尺寸, 逻辑画布尺寸×Zoom)`，交给ScrollRect计算滚动边界。若把Content本身缩放，却仍把原始宽高交给滚动条，常见结果就是“图看起来有空间，滚动却到不了最后一张卡”。

缩放时先把当前视野中心换算成Drawing逻辑坐标，再用新倍率恢复同一个中心，最后钳制到有效边界。FitAll取横向和纵向可容纳比例中较小的一个；构筑很长时允许Slider进入更小的倍率，而不是固定最小倍率导致完整图永远放不下。极小倍率用于看整体，玩家仍可放大、平移查看具体卡牌，不承诺缩小到几像素时文字仍可读。

## Task 4：真实资源事务、冻结票据和Session归档（隔离服务已实现，阶段二仍在进行）

本次继续推进的重点是把“解释器算出了什么”变成“这根具体法杖可以可靠地支付并推进一次”。上一版工作台使用的是只读规则样例：格子能解释Scope，仍不能证明真实库存会正确扣次数、失败会完整回滚、已经飞出的触发弹能继续执行。现在新增显式选择的V2资源服务，由Run从当前归属表捕获真实实例与Mana，再调用同一个Skills Machine构建候选。准备阶段锁住库存和本杖资源，成功后一起提交Mana、有限次数、下一牌堆、随机状态和等待时间，最后公开冻结记录。后续触发使用根已支付的Graph，不再拿当前卡序解释，也不再次支付同一批Mana。正式角色仍走Legacy入口，因此本节完成的是可单独审查的服务接缝，不代表已经接好据点研究区、真实连发和Schema14。用户明确认可多排格子的视觉方向，但尚未人工试玩；这个事实保留，不能用自动测试代替玩家是否看懂的判断。

### 1. 从候选到提交：为什么不能先扣一点再补一点

调用链为：Core身份请求 → Run核对Inventory/Program/Execution/Resource版本 → 从真实库存捕获次数与资格 → Skills Machine构建冻结Graph、Trace、NextState、ManaAfter → Run预约库存和法杖 → 调用方成功准备根输出后Complete，或失败后Cancel → 原子更新资源 → Session归档提交记录。Editor Sandbox没有调用世界生成，因此它的Complete只代表资源提交，不代表弹体已经发射。

库存版本表示物品归属/次数是否变化；ProgramRevision表示安装的程序是否变化；ExecutionRevision表示同一程序已经读到哪里；ResourceVersion表示Mana/等待的观察起点。这些维度不能只用一个“卡序没变”来替代。Core请求仍是struct，只有ID、版本和枚举，不引用Skills的Graph或可写Run服务，保持依赖方向。

Prepare之后，ItemOwnershipStore的PreparedInventory阻止移动/配置/材料来源变更；WandLoadoutService的本杖预约同时阻止另一条Mana入口和该杖Tick。只锁库存不足以保护法杖资源，因为Mana恢复和旧支付接口并不通过库存字典。Complete写入前再次确认两边预约仍属于本事务，失效时返回StaleResources或StaleExecution，保留Mana、次数、Draw、RNG和等待。提交区间不发布中间观察事件，归档在资源都更新后才可见。

V2允许负ManaCost，经过Machine钳制至MaxMana；缺少资格的AddMana也要跳过，不能因它能恢复Mana就免费执行。有限Modifier/Multicast仍按已有Raid资格支付一次，不能每次Draw再次扣资格次数。旧Legacy入口的逐层Mana支付保持原样，两个服务不因共用请求struct而自动切换。

### 2. 耗尽、旧Graph与材料各自保留什么

普通Emit的有限次数在根提交时统一支付，包含未来子层。最后一次被成功提交后，实例从库存移除。新程序使用RetainInstances保留原冻结指令字段，按稳定实例ID将候选deck/discard索引映射到新程序；不重新读取SO数值，不把未读到的卡重新排成满deck，也不重置CycleIndex、CycleReloadDelta或RNG。手动改卡是另一条Reprogram路径，不能与自然耗尽混用。

旧票据保留自己的ProgramRevision与完整Graph。卡牌消失、当前Mana被花到0、玩家改了卡序，都不使已经支付的子层重新收费或重新解释。子层只在父层资源已提交且自己未尝试时获得一次预算；取消按调用者和子树清理，不能顺手清掉另一位施法者的票据。当前只登记资源层状态，世界Released/Cancelled要等Character的真实观察接入后再记录。

材料不在根构建时替未来层预取：根层只准备当前根输出，子层到实际PrepareLayer时再检查携带容器并预约剂量。这样容器被移到仓库会让未来供料失效，但普通弹仍能按已支付Graph执行。两路输出顺序共享同一个实际来源余量，30单位最多分成20和10，各自有独立OutputId；取消根或放弃未触发子层不取相应材料。这里测试的是多路输出；动态Copy尚在T8，其专属预算场景不能提前标为已测。

### 3. 收据与历史记录为什么要分开

重试收据回答“同一请求原来是否成功”，归档回答“这次施法当时发生了什么”。本次修复了只缓存每个Caller最后一条请求的问题：Complete后插入PrepareLayer，再重发原Complete，仍应取得原成功结果且不重复扣费。收据保留最近256条；窗口外的旧请求按Caller水位拒绝，不会重新执行，但不保证无限期返回原收据。这是明确的内存边界。

WandExecutionReplayArchive归Session所有，全Session共享最近3条Root，可按具体法杖查询最近保留记录。淘汰诊断引用不取消真实票据，仍在飞行的Graph由票据独立持有。AdoptCommitted重建资源服务后，原归档对象及冻结来源继续存在；它不进入Profile DTO，不恢复历史Mana或物品，不把耗尽的实例复活。WorldStatus初始为NotObserved，服务Sandbox提交成功不能把它写成Released。

## Task 9：显式终止原因与寿命编程

一枚弹消失不代表它正常走完寿命。命中、计时触发、场景卸载、事务回滚和主动禁用都可能最终走到Unity的OnDestroy；如果把后续攻击挂在OnDestroy上，玩家离开地图或失败回滚时反而会产生新攻击。本Task让Combat发布通用的`ProjectileTerminationReason`，Character只对Impact和LifetimeExpired释放终止载荷，Cancel及清理不发攻击。原Impact/TimedTrigger/Finished合同继续保留，材料清理仍走原生命周期。寿命成为冻结命令参数，短寿命卡可以让终止触发弹在空中展开子序列；Skyfall的寿命从弹体真正出生开始，而不是从预警开始计算。箭矢命中后的残留时间属于表现停留，与飞行寿命、触发次数分开。

### 1. 从隐式Destroy改成明确状态

`ProjectileBase`不再在Init调用延迟`Destroy(maxLifetime)`，改为Update中的复用float倒计时。正常到点先消费终止状态并发布原因，再Destroy；命中先消费碰撞、发布原Impact，再发布同一次Termination。`_terminated`确保一次通知，禁用或OnDestroy兜底只能报告Cancelled。没有在这些回调中直接读取Skills或库存，Combat依赖方向保持不变。

`SpellDefinition.LifetimeSeconds=-1`沿用Prefab旧值；新内容显式写寿命。`CastModifierState.LifetimeAddSeconds`在同Scope累加，`SpellEmissionData/EmitCommand/SpellCommandBaker`冻结最终结果；显式寿命按同一个Baker计算，沿用Prefab时携带加法值交Runtime处理。最终至少.01秒、最多600秒，以免永生弹无界累积。`SpellCaster.ConfigureProjectileMotion`在Init前配置寿命，`WirePayload`订阅明确原因；未来层仍释放冻结Graph，不重新求值SO。

## Task 10：固定特性、内容、正式接入与验证封口

最后这一Task把可计算的解释器变成可以走完整玩家路径的玩法。法杖现在有独立Cast与Reload、确定性Shuffle、最多32个普通槽，以及不占普通容量的AlwaysCast固定区。固定法术通过稳定ContentId引用，编译时冻结为Intrinsic指令，既不是一张库存卡，也不能从界面拖出一份物品。我们增加九张清楚命名的基础卡和三根不同节奏的研习杖，进入商店、掉落和四关奖励；研究台只显示玩家实际能访问的卡牌，不免费填满背包或自动解锁永久知识。场景处理先做副本，再走真实F输入、库存拖拽、P7施法与返回回放，最后才把已经验证的接线应用正式Hub，并逐个比较原有RectTransform。性能记录也按问题拆开：稳定热路径是否分配，与一次性生成大量弹体是否卡顿，是两件需要分别测量的事。

### 1. AlwaysCast为什么单独执行

固定指令附在冻结Program末尾，`IsIntrinsic`由SourceSlot<0判定，普通deck只包含真实槽位指令。每次Root先执行固定指令，再执行BaseDraws。正Mana免付，负成本仍获得Mana；固定Modifier的`draw_actions(1)`不再多抽一张，所以BaseDraws=1仍只产出一张普通弹。这对照了原gun.lua第300行附近的`playing_permanent_card`特殊分支。固定Multicast的多Draw仍普通调用，实际抽到的新卡照常收费；固定触发的单Draw同样遵守永久卡规则。

Run捕获输入时为Intrinsic提供无限次数/有效资格，但不在库存里找`@always:N`这种内部调用ID；材料附着也不会凭空出现来源。`RetainInstances`耗尽过滤保留固定指令，只按真实实例重映射deck。UI固定格标“固定”，不能拖动或拆成卡；执行格复用同一套样式。Schema14只保存随机法杖实例上的固定ContentId列表，不保存Graph或回放。列表冻结成ReadOnlyCollection，调用方修改原数组不会改变实例。未知固定ContentId、空定义和非法语义拒绝，不在加载失败时发一份默认物品顶替。

### 2. 新增内容与兼容差异

`ScriptableObjects/SpellProgrammingV2/`包含九张卡：法力回流、快速施放、快速周转、α借用、γ借用、短寿命、终止触发弹、双重施放、增伤；后两张使用明确的Draw2与伤害+6，方便复现七卡示例。三根研习杖分别偏快、偏重载、偏Shuffle，容量16/32，重载杖带固定周转修正。图标复用已有Sprite并叠类别字符/名称，属于功能性fallback，没有要求用户提供新美术。

### 2. 最终运行规则与取舍

- 右侧库是“尚未安装、可访问的实例”。已安装到任意法杖的实例都排除；同一种 ContentId 的另一份物品仍是独立格子，不能按图标或名称删除。拆卸、交换后重新读权威位置，不由 UI 私自销毁物品。
- 和平实验须有剩余资格大于零的 Modify/Multicast/Copy（无限卡例外），不消耗下次远征的资格。Mana、Emit 次数、材料仍按原事务支付。真正 Raid/练习 Raid 仍只认可其已经提交的资格集合；UI 不授予此权限。预览和实战共用 Run 的资格判定。
- V2 单击/按住先经地面或空中接缝进入 PlayerWizardAttackState，锁定来源与 Aim Snapshot；Animator 达到 AttackDefinition.ArrowSpawnTime 才提交资源并生成弹体。CrossFade 显式从0重播，校验目标 shortNameHash，不把归一化进度取模，避免卡顿跨过一整遍时吞掉释放。松开按钮不会取消已开始的单击；换出法杖或停用角色会取消尚未释放的旧来源，已经生成的触发弹持有独立冻结上下文。
- 恢复动画起手的代价：实射间隔包含动画起手和法杖冷却，不能再引用旧版“快杖实际0.05秒”的指标。没有偷偷加速原动画或用计时器冒充 Animator 阈值。
- Home 的研究 Box 位于初始落点右侧 `(6,1.5,0)`，大小 `(4,4,4)`；金色地面边界与判定 Box 同源，南侧返回金门保持原位置。按 F 打开同一独立界面，Esc关闭，Tab切原背包。副本不增加研究入口。

## 内容去重与目录归位首轮 Task（2026-10-19，首轮证据）

这次修改来自两个真实的维护问题：已有双重射击、法术增幅，却又为同种机制创建了独立规则和占位图；同时把法术、物品、法杖参数、Hub 配置混进“V2”目录，将早期实验与正式内容并排。继续按开发批次叠加目录，会让下一位开发者无法判断哪个是正式来源，也容易让测试读取旧 Review 后误以为正式场景已验证。因此本 Task 以现有游戏整体为边界，统一资源归属和当前开发入口。Runtime 仍由原九个业务 Assembly 承担各自职责，没有再复制一套施法或库存，也没有为了改目录重写战斗行为。实际迁移保留了 `.meta` GUID、物品 ContentId 和正式场景加载路径；名称易读化只涉及部分物品资源的 `m_Name`，它不承担存档身份。旧审阅快照先保存可核验 ZIP，再移出 Assets；仍服务自动测试的夹具被移到测试目录。这里的取舍是保留明确的兼容 ID 与有用途的诊断代码，让正式目录容易理解，同时不给现有存档和其他职业制造额外风险。

### 1. 同一种机制只有一份正式规则

双重施放物品直接复用 `Spell/Definitions/Spell_Mult_DoubleShooting.asset` 和旧 Icon。它原本说明两次，但 `ExtraDraws=2`；两个解释器都以一次基础 Draw 加额外 Draw 计算，因此实际为三次，现修正为 1。法术增幅复用 `Spell_Mdy_DmgUp.asset`，保留 ×1.5 和 10 Mana，退出另加的 +6 版本。旧 `norn.v2.double/damage` ID 仍能读取，旧新实例都指向同一 SpellDefinition；这是存档兼容，不是两种法术。

终止触发保留为独立机制：命中或自然寿命结束释放载荷，与旧命中触发、定时触发条件不同。七个新机制需要的新 Icon 清单已修正，继续使用现有 `Art/UI/Skill_Icon`，不再提议另建美术版本目录。研究台仍按同组最终修正运行，增幅数值变化不影响“同组前面的弹也受修正”这一解释器规则。

### 2. GUID 为什么能保留引用，为什么仍需修路径

Unity 的 Scene/Prefab 通常用资源 GUID 与 fileID 保存引用。`AssetDatabase.MoveAsset` 移动文件并保留 `.meta`，所以移动法术不会要求重绑法杖。脚本中的 `LoadAssetAtPath`、`FindAssets` 范围、`Root + name` 拼接、Editor 类型反射却使用字符串，Unity 不会替开发者全部重写。移动之前必须盘点，移动之后仍要实际加载和施法。

本轮 ScriptableObjects 归为 Spell、Character、Combat、Enemies、Items、Input、World、ElementField、Materials、Rendering。Spell 内再按 Definitions、Items、Programs、Libraries、Wands 区分真实数据职责。测试专用数据不再混在正式配置旁；Editor 从阶段名 Assembly 改为 `Game.Project.Editor`，工具按领域归位；三个系统的 `_Debug` 统一到各自 Diagnostics。正式 Hub/Home 的布局和五个 Build Settings 路径不动，避免把目录优化变成关卡加载迁移。

### 5. 合并规则必须同时解决奖励反向查询

真实 P7 路径随后暴露了比目录更重要的一处兼容问题。`ItemCatalogIndex.TryGet(contentId)` 用于恢复某个旧物品，允许旧新 ID 共用 SpellDefinition；但 `TryFindSpell(spell)` 用于发奖励，原来要求只有一份匹配。直接让两种物品指向旧规则后，后一查询会拒绝歧义，P7 的 DungeonRunContent 因而报“随机奖励法术未注册”。这不是应该删掉断言的测试问题，也不能按字典顺序拿第一项。

最终只在现有 Run 的 `Inventory/ItemCatalog.cs` 增加显式 `_canonicalSpellItems`：目录冻结时验证被选物品属于本目录，每种法术只选一次；奖励反向查询优先读取此表，未配置者继续要求唯一。所有旧 ContentId 的正向恢复规则保持，存档 Schema 不变。内容工具给两种已合并法术选择原完整法术库物品，不重建实例、不增加额外法术效果。此后本 Task 的 Runtime 差异是这一份必要兼容修复；前面的“纯移动阶段 Runtime Hash 一致”只说明当时状态，不能继续当作最终零修改声明。

这一步继续处理目录整理背后的设计遗留。仅把 V2 文件夹移动到 Spell 下面，还不能保证整个游戏只有一条玩家流程：P7 原来仍会创建 RunSpellSession，克隆开场法术库和法杖，再与据点带来的库存同时存在；旧编辑器、奖励和出口也各留有兼容分支。新程序员很容易误把这套临时库当成当前玩家财产，接入后就会出现预览、真正持有的法术和场景发射各有一份来源的问题。因此本 Task 以“主菜单进入据点、携带物品进入地图、提交后返回据点”为主线撤下旧入口，而不是继续保留两套系统再在运行时禁用其中一套。这里需要区分可删除的旧玩法与必须保留的基础能力：NPC/Boss 的只读 WandLoadout、CastEvaluator、Warrior/Archer 和关卡本身仍有用途；存档里的旧 ContentId 也仍有恢复价值，不能为了名字整齐一并删除。本次不需要新模型、纹理、VFX 或声音，作者新导入的 Icon 保持原内容和导入属性。

### 1. 从据点到地图只保留一份资产权威

玩家财产仍由 SinglePlayerProfile / ItemOwnershipStore 持有。HubPracticeSession 负责携带和回程，BossEntryTrigger 从它捕获真实物品 checkpoint；旧 RunSessionCoordinator 和只保存法术数组的 BossCheckpointSnapshot 不再参与正式流程。开场法术改由据点初始库存、存档及当前携带配置决定，不再克隆 P7 的 StartingSpellLibrary / StartingWandLoadout。Editor 直接 Play 地图仍可以从同一份据点模板建立内存试玩档，这条开发入口不写正式 Profile，也不意味着副本重新发一套旧开场物品。

### 2. 文件名不是存档 ID，也不是 UI 节点名

正式资源采用类型、分类、用途组成的下划线名称，例如 Spell_Modify_ManaRestore、Spell_Copy_Alpha、Item_Spell_Emit_Fireball 和 Wand_ResearchRapid。Modifier / Multicast 使用完整英文词。所有法术物品统一在 Spell/Items，旧 Library 子分组已撤销；真正的 SpellLibrary 数据另归 Spell/Libraries。药草等物品也采用 Item 前缀，避免同一类资产有的叫 bare name，有的又叫 dot ID。

### 1. 读取次数与实际弹体为什么不同

对于“散射、十重、触发火球、粘液、冰块、火球、火球”，Mana 足够且本轮从首槽开始时，根组是触发火球、冰块、两颗普通火球；粘液属于触发火球的命中子组。十重发出十次 Draw 请求，不创建十个火球副本。Draw 可以遇到 Modifier、Multicast、触发子组、费用失败或没有可回收卡，不能用卡片读取次数替代最终弹体数量。此时四颗根弹先飞出，粘液等触发火球命中才释放。已读成功的牌暂存在 Hand，不会为了凑足次数在本次构建里随意重复读它们；之前轮次的 Discard 在规则允许时仍可回收。

实际费用顺序是散射10、十重40、触发25、粘液5、冰块5、两颗火球各20。以本次开始100 Mana为例，读到普通火球时只剩15，两个火球都跳过，根组只产出触发弹和冰块；120 Mana可多放一颗，足够时两颗都放。图中没有可验证的起始Mana，所以截图本身不足以确定玩家当时是哪种具体余额。这里的数值用来解释复现，不再添加到玩家侧边栏。

### 2. 根因、修复与取舍

`SpellProgramMachine.Take` 已经在一次请求中扫描完整个可用 Deck；扫描失败时，原外层循环只在没有 Discard 时结束。Mana 不足的牌恰好进入 Discard，因此后续预算反复回收它们，再次失败。现在结束当前失败请求的剩余相同尝试，继续正常返回父请求；保留第一次失败 Trace、付费、Hand/Discard 与技术预算。技术预算测试改用最后一张恢复 Mana 的合法继续读取来触发超限，避免依赖已经移除的无效空转。

## Task 9：两种CD的区分、短寿命叠乘、水面兼容与地图性能（完成）

这一轮同时处理玩家理解、法术数值链和真实地图开销，不能把四个现象都归结为法术解释器。快速施放先要区分“同一轮内两次施放的间隔”和“整根法杖读完后的装填”，否则缩短了正确的计时器，玩家仍可能因为另一个更长的计时器而感觉没有变化。短寿命的旧公式本来是线性的固定减秒，异常体感来自第三张已经接近零；用户确认改为每张将剩余寿命减半，这才需要增加一项贯通数据、编译快照和世界弹体的倍率。水面紫色来自新扩建地图仍引用 Built-in 材质，与可采集的 ElementWorld Water 是不同系统。性能则先对正式 Hub、P7、P8 做不施法基线，再定位到 P7 旧Cell路径中与当前材料无关的扫描。全过程保留据点新布局，不通过关闭玩法、降低材料数量或修改传送位置换取测试通过。

### 1. 快速施放为什么可能看不到收益

一轮中未读完法杖时，只等本发的 Cast Delay；整轮结束时，本项目同时倒数 Cast Delay 和 Reload，等待 `max(Cast Delay, Reload)`。例如基础两者都是0.8秒，快速施放将Cast Delay减到0.68秒：如果下一张牌仍在待抽区，就能更早开始下一发；若只有一颗火球或一次Multicast已经用完整轮，Reload仍为0.8秒，总等待保持0.8秒。快速周转改变的是后者，因此两张卡并不重复。最低施放间隔是0.05秒，多张减速卡不能无限把间隔降到负数。

`FastCastCommitsReducedDelayBeforeReload` 在真实Owned事务中确认0.68秒写入法杖冷却；它证明的是实际提交值，不是两次鼠标出手的端到端间隔。后者还包含Animator过渡和ArrowSpawnTime之前的动画时间，其他PlayMode用例继续确认点击起手不会立刻发射。卡放在触发子组时也不能修改父组的Cast Delay。没有把快速施放改成同时减少装填，也没有删除用户要求的动画出手时机；两张卡的描述改为直白说明各自影响哪一种等待。

### 2. 短寿命的数学和冻结链

旧默认寿命5秒，固定−1.6秒：两张剩1.8秒，三张剩0.2秒。若暂时忽略碰撞、重力与速度修正，速度20时射程会从36降到4，虽然每次只少1.6秒，视觉上却相差9倍。前面把第三张说成已经触及0.01秒下限是不准确的；实际还剩0.2秒。

现在短寿命是×0.5：5→2.5→1.25→0.625秒，数量每多一张都再减半。通用公式为 `(显式寿命或Prefab默认寿命 + 加秒总和) × 倍率乘积`，最后钳制到0.01～600秒。旧加秒字段保留给其他内容，只有短寿命这张卡从加秒改为倍率。默认倍率1对旧资源是恒等变换，不修改存档ContentId。

SpellDefinition的`ModLifetimeMul`被编译成`SpellInstruction.Modifier`，保存在不可变`CastModifierState`中，再由Baker写入`EmitCommand`。显式寿命在纯规则层就结算；`LifetimeSeconds=-1`表示基础寿命只有Prefab知道，因此命令携带尚未应用的加秒/倍率，由Combat的`ProjectileBase.ConfigureLifetime`结算一次。不能先拿一个猜测的寿命做乘法，也不能在Baker和Runtime各乘一次。Scope继承规则保持：触发子组的短寿命不缩短父弹或另一颗根弹，命中/正常到期/取消仍使用原来的Termination Reason。

### 3. 水面为什么紫色，修复保留什么

资源包的 `beffio/Medieval_Kingdom/Water` 和 `Water_Mobile` 是 Built-in Surface Shader，使用GrabPass；当前项目使用URP，不能靠换成普通Standard材质解决。复用已有 `Game/Environment/BeffioDecorativeWaterURP`，将10份供应方旧水材质接到它，保留材质GUID、原Normal纹理、颜色和UV速度，所以新增Prefab也得到兼容材质，不用逐个覆盖场景Renderer。

Normal纹理不是几何高度，而是在Fragment光照中扰动表面朝向。现有Shader将两层不同UV速度采样的Tangent Space Normal，通过顶点的世界Normal/Tangent/Bitangent构成的基底变到World Space，再参与URP PBR和Fresnel。World Space用于光照与视角关系，Clip Space用于最终光栅化位置；透明混合保留水下底色，ZWrite关闭避免透明面写深度遮住后续透明物体。该装饰实现没有移植旧实时平面反射、GrabPass折射和岸边泡沫，不会新增一台相机重复渲染地图。Reflection_pass本来已有SRP提前返回，不能把它误判为本次P7下落扫描的根因。此水面也不会自动变成可采集的材料世界。

### 4. Profiler定位与优化取舍

Hub/P7/P8都先加载正式入口，不施法，预热后采90帧，保留Native `.data` 和按线程导出的TSV。Main Thread的PlayerLoop、模拟Marker与Render Thread等待分别观察；EnlightenWorker的Semaphore等待不是同等数量的CPU计算，不能把所有线程的等待加起来声称一帧耗时几百毫秒。Editor重绘、GPU等待、Shader导入和后台账号请求会影响帧时间，所以短样本不能当作Standalone的目标帧率承诺。

P7初始 `ElementWorld.Simulate` 平均约5.67ms，PrepareNeighbors约2.24ms，FireFall约2.66ms。问题包括GPU/Grid液体路径仍为残留Cell Water扫描不需要的邻居、对内部Cell做跨Chunk判断，以及每次FireFall逐格坐标变换后才发现绝大多数格子不是火。第一轮将模拟降到约3.94ms；第二轮对无Fire源Chunk跳过源扫描、线性读取当前数组，只对真正Fire格子计算坐标，最终模拟约1.75ms、FireFall约0.41ms、邻居准备约0.89ms。

`HasFire`来自已有离散写入和Tick末批量刷新，不额外维护第二份材料世界。是否需要火阶段使用本Tick开始的保守快照：有火时即使它落进原本为空的接收Chunk，仍执行该阶段和后续衰减，避免仅凭接收端旧HasFire=false漏处理。Current只读、Delta预约、Next统一提交及跨Chunk守恒全部保留。没有改变火焰下落速度、衰减量、液体Backend、伤害或材料守恒来换取性能。P8空闲模拟约0.001ms，没有复现P7同等级的模拟瓶颈，Exposure与Rendering仍有独立成本。
