## 一、模板用途与执行约定

后续用户指定学习计划中的某一板块生成资料时，按本模板组织内容，并生成独立 Markdown 文件。模板用于约束讲解方法和资料质量，具体篇幅与章节深度随板块调整。

资料主线：

```text
本节在全局中的位置
→ 玩家看到什么、系统要解决什么问题
→ 基本思路与责任划分
→ 关键数据及状态所有者
→ 成功和失败的 Runtime 过程
→ 最小源码阅读链
→ 技术原理与 trade-off
→ 理解检查与独立设计解释
```

### 1. 生成前必须做的核对

1. 阅读配套计划，确定板块编号、目标、前置知识和范围。
2. 核对当前 AGENTS.md 与相关项目约束。
3. 用当前生产源码、实际 ScriptableObject/Prefab/Scene 配置及相关测试确认实现；历史解析用于理解背景，不自动代表当前行为。
4. 如有旧版路径、NPC/Boss 独立路径、Editor 预览或测试夹具，明确本节实际跟踪哪一条。
5. 文件或接线缺失时先说明缺口；能由本地只读检查确定的内容先自行核对，仍影响结论的缺口再向用户确认。
6. 本任务默认只生成学习文档。发现潜在问题时记录证据和影响，不擅自修改 Gameplay、Scene、Prefab 或存档。

### 2. 文档生成与保存

- 目录：`F:/Develop Project/RPG/RPG/Assets/_Project/Docs/`。
- 文件名：`生成日期 编号 板块名称 学习资料.md`。
- 子节示例：`2026-10-20 B2.1 二维背包占格与容量 学习资料.md`。
- 只生成本次指定板块；用户要求完整板块时覆盖该板块，用户要求小节时不提前展开后续小节。
- 在正文顶部链接学习计划与本模板。关联资料已有文件时再添加链接，不创建指向尚不存在文档的占位链接。
- 本模板中的填写提示可以保留在模板内；交付的学习资料必须替换提示，不能残留未填写的空表或占位文本。
- 不为文档手写 Unity `.meta`，由 Unity 自行导入。

### 3. 表达与深度

- 使用简体中文，保留 C#、ScriptableObject、FSM、Snapshot、GC Alloc、Rasterization 等专业术语的英文原词；首次出现时先解释概念和用途。
- 源码专用名称先用中文说明业务意义与 Runtime 职责，再给准确标识符。例如：用于判定当前法杖仍在执行哪一版程序的版本号（ProgramRevision）。
- 去掉括号中的标识符后，主要解释仍应能读懂；不能用一串类名代替因果说明。
- 从框架进入局部。先解释为什么需要这一层，再给最小源码；不以长代码块开篇。
- 每一节围绕一个核心问题推进。完整资料可以包含多个有依赖的小节，但不要重复讲已经解释清楚的系统。
- 原理、实现过程和设计取舍应形成连续叙述。表格用于对比、状态和职责，不把全文拆成零散术语清单。
- 默认按纯学习资料组织，不自动追加模拟面试答案。用户明确要求面试训练时，再在本模板基础上增加相应内容。

## 0. 本节目标与全局位置

先用一到三段说明：本节在整个游戏中负责什么，玩家何时会遇到它，前面哪些系统提供输入，后面哪些系统消费结果。先建立边界，再引出内部实现。

列出两到四个可以检查的学习目标，例如“能够解释容量不足时物品为什么留在地面”，不要只写“掌握背包系统”。

必要时给出一条小范围关系图：

```text
〈上游玩家操作或系统事实〉
→ 〈本节负责的规则与状态变化〉
→ 〈下游世界结果、资产结果或界面结果〉
```

说明本节暂不展开的相邻机制，并引用对应学习编号。只标记真正影响边界的内容。

## 1. 玩家效果、问题与基本思路

### 1.1 从一个具体场景开始

选择一个能贯穿全文的最小例子，交代初始状态、玩家操作、成功结果和一个相关失败结果。

例如，B 类主题可选择“背包剩一格时拾取某件物品”；C 类主题可选择“普通弹与一张修正卡”；E 类主题则选择实际可执行的完整 Gameplay。示例数量和卡序应取自已核对配置；自拟数值必须标成教学示例，不能冒充项目默认值。

### 1.2 为什么需要这套机制

解释没有这一层时会出现什么具体问题，以及当前机制需要保护的规则。避免只说“为了低耦合”“为了扩展性”，应明确是哪两个职责不应互相拥有、哪种错误状态必须被阻止。

### 1.3 最小心智模型

用简单语言解释核心模型，再引入必要术语。清楚区分配置、实例、运行状态、规则求值、Unity 对象和显示结果，只展开本节涉及的部分。

## 2. 架构职责、关键数据与状态归属

先说明各参与者为什么这样划分，再用紧凑表格记录责任。不要列出全部相关类。

| 参与者的中文职责及源码名称 | 所属 Assembly | 拥有什么 | 接收什么、产出什么 | 与下一层的连接 |
|---|---|---|---|---|
| 〈实际参与者〉 | 〈当前 asmdef〉 | 〈配置/状态/无状态规则〉 | 〈输入与结果〉 | 〈调用/请求事件/结果事件/只读读取〉 |

对本节最关键的两到四个状态容器单独解释：

| 关键数据及其业务意义 | 具体类型与逻辑形状 | Owner 与修改入口 | 创建、更新、消费和清理 | 保护的规则 |
|---|---|---|---|---|
| 〈例如物品归属表，而非仅写字段名〉 | 〈Dictionary/List/struct/单一状态引用等，说明键值或元素含义〉 | 〈谁写、谁只读〉 | 〈关键生命周期〉 | 〈不允许出现的状态〉 |

补充说明实际涉及的区别：

- 配置身份与具体实例身份是否不同？运行期 Unity Object ID 能否用于存档？
- 数据是活引用、独立副本、只读视图还是冻结 Snapshot？谁仍可能修改底层集合？
- 当前数量、版本和资源状态由谁维护？是否跨 Scene、跨局次或跨程序启动保留？
- 如果涉及资源和金额，类型、单位、精度、容量及溢出处理分别是什么？

只回答本节需要的问题；没有该数据或机制时不强行套用。

## 3. 完整 Runtime 过程：先成功，再失败

### 3.1 正常流程

沿用第 1 节的例子，从输入或系统事实开始，追踪至可观察结果。每一步先解释系统效果，再给源码入口。

| 顺序 | 当前发生什么、为什么 | 调用或事件入口 | 读取/修改的状态 | 结果交给谁 |
|---|---|---|---|---|
| 〈序号〉 | 〈玩家或系统意义〉 | 〈已核对的方法/事件〉 | 〈实际数据〉 | 〈后继参与者〉 |

用简短流程图补充时，标明直接调用、请求事件、结果事件和只读读取，不把所有箭头都画成同一种通信。

涉及 Unity 时明确入口：Awake、OnEnable、Start、Update、LateUpdate、FixedUpdate、Coroutine 恢复点、碰撞回调或 UI 回调。解释这些时序为何影响结果，不机械列出生命周期名称。

### 3.2 用状态变化证明结果

选择最少的关键字段，以“操作前 → 候选或等待 → 已确认结果”展示变化。没有候选或事务阶段的功能直接展示真实阶段，不虚构统一三阶段模型。

| 时刻/阶段 | 关键状态 | 玩家可见结果 | 是否已经确认生效 |
|---|---|---|---|
| 〈实际阶段〉 | 〈值及单位〉 | 〈可观察效果〉 | 〈确认边界〉 |

### 3.3 一个重要失败分支

选择当前功能真正存在的失败路径，例如容量不足、旧版本请求、低 Mana、区域无权限、资源忙或写盘失败，说明：

1. 在哪一步被识别，依据是什么？
2. 返回什么结果，哪个状态保持原值或需要回滚？
3. 世界对象、资产和 UI 分别如何处理？
4. 能否重试，重复请求是否再次扣费、抽奖或生成？

## 4. 关键源码与实现原理

### 4.1 按依赖拆解核心机制

通常选择两到四个问题，逐个按照“规则是什么 → 为什么需要 → 当前代码怎样实现 → 结果是什么”讲解。第 3 节建立完整路径，本节只深入其中关键控制流或算法，避免重复抄写调用链。

使用最小真实源码片段，标明文件和方法。代码片段后解释重要部分的具体类型、业务意义、读写对象、C#/Unity 行为和设计原因。纯示意代码明确标记为示意，不能当作现有方法。

### 4.2 实际使用的技术

| 技术或 API | 本节用于什么 | 背后的原理或约束 | 选择它的代价 |
|---|---|---|---|
| 〈本节实际使用的技术〉 | 〈具体问题〉 | 〈必要原理〉 | 〈trade-off〉 |

技术解释服务于本节。例如读取 Dictionary 时解释键、查找和身份关系；讲解 Animator 阈值时解释 normalizedTime、CrossFade 与释放去重；不附加无关的 C# 或 Unity 全知识点教程。

### 4.3 架构为何成立

说明状态 Owner、允许的依赖和请求入口如何共同保护规则；指出 Gameplay 与 Presentation 的具体边界。事件发布本身不等于事务提交，读取接口本身也不自动保证底层集合不可变，涉及这些情况时解释实际保证来自哪里。

## 5. 设计取舍与关键边界

选择一到三个有意义的决策，比较当前实现和一个合理替代方案。

| 决策问题 | 当前实现 | 合理替代方案 | 当前收益与代价 | 什么条件下值得改变 |
|---|---|---|---|---|
| 〈具体问题〉 | 〈源码确认的方案〉 | 〈真实可用方案〉 | 〈具体 trade-off〉 | 〈条件而非擅自提出开发任务〉 |

写明当前实现的适用范围。不要为了比较而重讲已经退役的版本；用户要求重构复盘时，再引用真实历史证据。

性能按本节实际调用频率讨论：每帧热路径、固定 Tick、离散操作还是初始化。结合集合规模、Physics 查询、分配、复用和预算解释成本；没有 Profiler 证据时只能给静态分析，不能写“整个项目零 GC”或虚构优化前后数字。

## 6. 如何阅读源码与观察结果

### 6.1 最小源码阅读顺序

通常选择三到六个文件；框架入门或很小的子节可缩减到一到三个。每个文件给出可点击的绝对路径、职责、首个阅读入口、下一跳和阅读问题。

| 阅读顺序与文件链接 | 职责与先看入口 | 接下来跟踪什么 | 读完应能回答 |
|---|---|---|---|
| 〈真实链接〉 | 〈方法/类型/字段组及意义〉 | 〈后继方法或消费者〉 | 〈机制问题〉 |

一般顺序：数据或 Contract → Pure Logic → Runtime Adapter → Unity 边界 → 结果消费者 → 一个相关测试。FSM 主题可从 Controller 和状态转换入口开始，不机械照搬顺序。

说明哪些内容需要记住：状态归属、数据形状、调用时序、关键规则、Unity 约束与 trade-off；哪些可以查阅：私有字段拼写、行号、普通空值防护和非设计性的默认值。

### 6.2 Unity 中怎样观察

若本节有实际场景操作，列出已确认的 Scene、GameObject/Component、必要 Inspector 字段、操作步骤、预期现象和观察数据。只做学习观察时不要求重装场景或修改正式配置。

需要修改配置才能复现实验时，明确说明改动、隔离方式、恢复办法，以及示例与正式默认值的区别。若未核对场景接线，写明限制，不编造可运行入口。

### 6.3 测试与证据

选一个相关测试解释它保护的契约、输入和断言。测试存在与测试实际通过分别记录。

| 证据类别 | 本次核对或运行范围 | 可以支持的结论 | 未覆盖范围 |
|---|---|---|---|
| 〈源码/序列化配置/历史记录/本次 EditMode/PlayMode/人工试玩/Build/Profiler〉 | 〈文件、用例或采样范围〉 | 〈具体结论〉 | 〈实际限制〉 |

文档生成任务不要求为了“完整”主动运行整套 Unity 测试。需要运行时按请求与环境执行，并准确记录结果；无实际输出就写“本次未运行”。

## 7. 理解检查与独立解释

提供二到四道题，重点检查模型、状态和机制，而非字段记忆。问题可覆盖：

- 规则解释：为什么这一状态由该模块拥有？
- 结果预测：改变容量、顺序、资源或事件时机后会发生什么？
- 失败推理：某一步失败后哪些资产应保持不变？
- 设计解释：给不看源码的人解释本功能，并说明一个 trade-off。

默认不紧接着给完整标准答案。用户需要自学核对时，可在折叠区提供简短判断要点；用户要求面试模拟时再生成相应回答。

要求用户能串起“玩家效果 → 数据与 Owner → 核心流程 → 失败保护 → 设计取舍”。这比背出全部类名更能证明理解。

## 8. 本节回顾与下一步

用简短自然段指出本节最需要保留的机制，标出下一板块编号及其承接的问题。存在尚未核对的事实时，一并明确，不能留给读者自行猜测。

如果本节依赖外部研究资料，在相关论断处给原始来源链接，解释该来源支持什么；Norn 的实际行为仍以当前源码和配置为准。

## 三、不同主题的裁剪规则

| 主题 | 重点保留 | 应控制的范围 |
|---|---|---|
| A：框架入门 | 玩家路径、模块责任、状态生命周期、最小调用链 | 可合并正文第 2～4 节，不强行加入复杂算法、事务和性能分析 |
| B：搜打撤与资产 | 配置/实例/归属、数量、权限、成功与失败、持久化边界 | 不把某条 Raid 规则套用于所有 P7/P8 或 Home 路径；不由物品枚举推导未接入行为 |
| C：法术程序 | 输入与冻结结果、Deck/Hand/Discard、Scope、资源、生命周期、世界观察 | 玩家新版与 NPC/Boss 路径分别说明；Noita 来源不能替代 Norn 实现证据 |
| D：基础回顾 | 基础功能、技术栈、职责和主系统连接点 | 不展开完整 3C、求解器或 Shader 教材 |
| E：跨系统案例 | 调用图与状态表并列，真实入口、关键失败和资源保留 | 避免把多个模块逐个介绍却没有完整事件和数据流 |

特殊主题额外要求：

- **Debug 复盘**：按“玩家症状 → 证据 → 初始假设 → 层级隔离 → 根因 → 排除的修法 → 最终修复 → 回归与边界”组织，只引用有记录的经历。
- **Graphics/Shader**：按初学者深度解释 Coordinate Space、向量和公式、Shader Stage、输入输出、Material/Renderer/Texture 职责及 Rendering trade-off。
- **资源与事务**：解释具体预留对象、提交时机、取消影响和重试语义；不能只贴 Prepare/Commit 方法名。
- **施法时序**：分别核对输入、攻击 State、Animator 出手点、Cast/Reload、延迟出生和 Trigger。不能把冷却提交值写成实际端到端射速。
- **跨场景**：区分纯数据移交、DontDestroyOnLoad 上下文、Scene 对象归属、世界模拟资源与真正写盘。说明保存失败时玩家和资产怎样留在合法状态。

## 四、生成后的检查清单

- [ ] 板块编号、前置关系、范围与学习计划一致，未提前扩写整个项目。
- [ ] 开头先解释全局位置、玩家效果与基本模型，再进入内部名称和源码。
- [ ] 已解释是什么、为什么、怎么做，以及至少一个重要 trade-off。
- [ ] 关键数据有类型、业务意义、Owner、读写入口和生命周期。
- [ ] 成功流程连到可观察结果，重要失败分支有状态与资源解释。
- [ ] 当前生产路径、保留独立路径、历史记录、测试内容与未来设想没有混用。
- [ ] 源码片段真实且足够小，路径和核心符号已核对，引用文件存在。
- [ ] 相关技术与 API 的解释服务于当前机制，不堆砌知识点。
