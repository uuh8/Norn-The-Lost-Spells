## 1. 当前系统怎样统一

据点的三套库存界面是 Tab 随身背包、仓库、商店内嵌背包，复用 `SinglePlayerInventoryController`。研究台另有 Workbench。正式单人路径也已接入账号资产和 DS，不等于从旧本地 Profile 开一条完全独立的资产路径。

“共用界面”并不能自动保证行为统一：Hub 的命令经 HTTP 到业务服，Home/P7/P8 在局命令由 DS 的 `OnlineOwnedWorkspace` 执行。两个 Owner 各自有版本、租约和收据。这种隔离必须保留；要补齐的是同样拖放操作的事务语义，而不是让 Client 同时直接写两份资产。

## 2. 已复现的 UI 问题

1. **同种物品只有代表实例能选。** 仓库按 ContentId 分组显示，但每一份法术的剩余次数、每把法杖的固定属性仍属于各自 InstanceId。账号分支先经过写权限门，误挡住后面的纯 UI 成员轮换；这一步本来不应写资产。回归以同类不同实例验证选择，继续检查拖放/出售使用正确身份。
2. **商店拖拽 R 无效。** 内嵌背包正确让 Shop 管理 Tab/Esc，却连 Rotate 引用也被清除。修复方向是从 Shop 的原背包取得 Rotate binding，内嵌界面维护自己的 InputAction 生命周期，不能关闭别人持有的 action。测试发送真实 Keyboard R 事件，不直接调用 RotateDrag。
3. **Hub 附着编辑按钮可点却无反应。** 当前账号上下文不提供附着编辑命令；显示层仍将按钮启用，Submit 又因只读来源返回。应保留已确认附着的展示，并明确可编辑场景和操作能力，不能为了按钮生效绕过账号写权限。
4. **普通账号更新重置附近排列。** 每次新 Profile 会创建新 Source，引用变化不一定表示换账号或换世界。附近布局应在同一账号/Scene 的连续版本间保留，在真正换身份或世界时清理。测试包含换账号负控制，避免修复后串用别人的附近排列。

`first-regression-red.xml` 中 UI 的 8 个新增 case 为 7 个预期失败、1 个身份隔离负控制通过。既有五尺寸 `UiViewportLayout` 已经存在，本轮不按旧截图重建布局。

## 3. Hub 与在局物品操作的差异

1. **工具槽替换。** DS 已有原子替换与工具槽互换，Hub HTTP Move 仅移动 incoming 的位置，遇到已占槽就被完整验证拒绝。修复应先在候选状态中腾出 incoming 原格，再给旧瓶找到合法回包位置，整组验证后发布。仓库来源且包真的放不下时仍应失败，两瓶都保留。
2. **材料堆合并。** UI 的 placement preview 允许兼容材料合并，Hub 业务 Move 却没有对应分支。partial merge 必须保留源余量，full merge 才退休源；GMU 总量不变。Client 的确认逻辑也要按具体 source/target 身份和数量核对，不能要求已被合并退休的 source ID 仍位于目标，也不能用整包总量判断包内搬运成功。

这两项属于已有玩家操作的规则缺失，继续沿现有合同和收据字段实现，不新增物品体系或 Schema。Unity 的两个合法材料合并确认 case 已得到预期 RED，坏数量/身份的负控制保持通过。

## 4. 元素世界的可见问题与原因

1. **有效 Solid Collider 暂时消失。** Replica Store 返回的是过滤后的紧凑 Key 数组。将数组下标当成几何槽身份，会在前面的 Chunk 退出 Interest 时让后面的 Key 全部换槽，进而关闭仍有效的 Mesh/Collider。修复应维护稳定 Key→槽映射，仅回收真正离开的 Key，同时保留每帧有界 Build。
2. **液体与细固体占据不一致。** 正式场景液体粗格覆盖多个固体细格。只查中心点会漏掉角落冰块；`DriedSlime` 的 Partial Volume 则应抬高液面底部，不能简单当整格墙。需要分别保留实际点查询、粗格阻挡、residue 高度三种语义，并让固体变化正确触发液体表现刷新。
3. **Authority Exposure 时钟分叉。** 材料/角色走 DS 有界固定 Tick，Exposure 却继续按 Render delta 追步。大卡顿时，两套时钟可给出不同累计接触量。修复应由同一合法 Authority Tick 推进接触采样，保留 SinglePlayer 原入口，并验证 Frozen/重复 Tick 不积债。
4. **DS 创建纯状态 VFX。** Authority 需要状态剂量和 DoT，不需要 Burning/Poisoned 的视觉 Prefab。测试同时要求 DS 不实例化 VFX、伤害仍发生、可见端仍保留原表现。没有测量前不声明 CPU/GC 节省比例。

上述新增 case 在首轮完整相关 fixture 中出现预期失败；整体为 **217 passed / 25 failed / 0 skipped**。失败证据保留，后续 GREEN 单独落盘。

## 8. 冷启动恢复审计（实现与回归中）

已有重连依赖进程内的 Room/Coroutine。关闭客户端进程后，这些内存自然丢失；再次登录得到 `AssetsLocked/ActiveRunId` 时，主菜单正确拒绝进入 Hub，却没有调用业务端已有的 current room 恢复接口。它不是资产需要重新初始化，而是缺少从新进程重新取得原身份的入口。

业务端已有所需权威事实：current room 按当前登录的 CharacterId 查询 PartyMembers；Ticket 只授予仍活跃且有租约的本人；兑换保留 Seat 对应 ActorId、递增 ConnectionEpoch。新增 `RoomSessionRecoveryTests.cs` 对单人 P7、单人 Home、合作 P7 各跑一例，在 TestServer 的正式 HTTP pipeline 与真实 test MySQL 中吊销旧 Session、重新登录、查询 current/instance、签票及通过控制 endpoint 兑换。`business-cold-session-green.trx` **3 passed / 0 failed**，同 Run/Instance/Actor 和冻结资产保持。这组不启动 TCP listener 或 DS；实际 Kestrel 的投递检查见上一节独立检查点桥。

这组业务测试使用 2 次卡与 137 金币作为隔离种子，不能据此声称已经运行了 DS 的两次施法。首次 3 项失败是 TestServer 没有声明请求具有正文，Minimal API 在业务校验前返回 400；仅修复测试的 `IHttpRequestBodyDetectionFeature.CanHaveBody`，保留首次证据 `business-cold-session.trx`，没有放宽产品认证或 JSON 规则。

客户端方案保留主菜单 Enter 意图，以本次 Profile 决定进入 Hub 或恢复原 Run。恢复固定 Player/Run 与请求代次；未知结果、404、重登均不能补资产。原 Hub 仍按原路径挂起/恢复；新进程没有原 Hub 时，菜单作为独立导航来源，个人退出 receipt 与完整 unlocked Profile 确认后回菜单，再经原 Enter Gate 进入据点。该方案避免在冷恢复分支重建另一套 Hub 生命周期，代价是退出后多一次进入据点点击。

核心先运行 RED：`cold-recovery-red.xml` 中 7 个既有负控制通过、32 个新增 case 失败；导入产品后，`cold-core-green-dialog-red.xml` 中核心 39 项全部通过，新增 Dialog 8 项为 1 通过、7 个预期失败。后者实际复现了旧 World 继续发布事件盖住登录菜单、Esc 穿透、重新启用没有重放导航权、库存输入占用残留。

恢复菜单不能靠一次 `RoomPhase.None` 关闭副本弹窗：保留的 Replica 仍会在后续 Update 发布状态。现在通过账户只读视图重放 `RecoveryMenuVisible`，Dialog 在菜单持有导航权期间拒绝旧 Room/Gameplay/Esc 请求，解除时重新读取当前 World，而不复活旧快照。独立 review 又补出了“已有 World 的菜单重试连接失败后卡在 Busy”路径，该失败可重试路径已修复并通过第10、14节回归；完整构建与Native结果见后续交付记录。

## 9. 广泛回归的失败分类（修复中）

首轮 427 个 fixture 为 **4314 passed / 107 failed**，证据 `broad-editmode-first.xml`；这是诊断结果，不能写成全部通过。主要分组如下：

- `AccountEntryNavigationTests` 对 never-active 的对象反射调用 `OnEnable` 后直接 Destroy，Unity 不会为这种对象自动补 `OnDisable`，导致全局事件持有已销毁 Session。修复在该夹具 finally 中配对调用真实 `OnDisable`，没有给产品加 null 掩盖、也没有全局 Clear 其他观察者。
- 一批旧库存 fixture 没有提供现合同要求的 `CurrencyVersion`/`CombatAssets`，或者仍按旧网络 Rebind 重建 Combat Owner 的假设检查。正在修正输入前提与生命周期断言，保持生产拒绝非法快照的 Gate。
- Rendering/元素测试部分依赖其他 fixture 预先创建 `Temp/ElementPerformance`，单独执行或改变顺序就失败；GPU timeout 与物理场景污染另行定位。保留真实失败，不以删除断言或跳过失败来生成 GREEN。

该广泛运行期间曾通过只读 Mono debugger 短暂停顿检查 TestRunner 进度，没有取消或修改运行状态。因此此轮只作为功能诊断，不作为 Native/全帧性能数据。

## 10. Unity 生命周期与测试隔离（验证中）

`cold-dialog-green.xml` 的 8 个导航/输入 case 已全部通过。PlayMode 首轮 `playmode-runtime-first.xml` 为 13 passed / 4 failed；其中两个 fixture 缺少 `CurrencyVersion=1`，仍应补合法前提而不是放宽产品快照验证。

容器满容量旧夹具只填 3×3×3 近邻，现有生产 Impact 在容量拒收后允许投放半径由 0.75m 逐步扩到 2m。因此瓶子成功释放到外圈是合法行为，不是丢物品。夹具改为填满最大投放球的包围盒，保留暂停 Solver、在途余量、另一个真实空瓶采集腾空间、最终数量守恒等断言；不改变生产半径和重试预算。

Input System 的 `InputTestFixture` 会切换全局 runtime，旧 ActionMap 可能仍持有此前设备状态。最初给当前库存实例克隆正式 Action 配置后，Early + OnlineShared 三项通过，但原 17 项组合仍失败，说明该修正不足。随后只读检查 pending `InputActionState`，确认真正异常 Owner 是 `InputSystem_Actions/Player` 与 `/UI`：Setup 后仍有 38 个 control 来自旧虚拟 Keyboard，库存克隆则全部属于当前 runtime。最终夹具在 Setup 前释放项目 Actions 的非序列化 runtime state，TearDown 后恢复原 manager 引用及逐 Action enabled；不修改 bindings、项目配置或保存资产。原 Scope/Prefab/Raycast 与输入回调保留，必须用原 17 项组合验证，不能靠拆开测试或忽略日志判定通过。

## 12. Rendering 测试环境诊断（验证中）

当前 Editor 使用 Direct3D12 / RTX 4070 Laptop GPU。GPU readback 在 10 秒内多次 `Update`、`QueuePlayerLoopUpdate` 后仍未完成，且 `hasError=false`；其他批次又能在约 0.2 秒完成。因此不能将此等待直接解释为产品 GPU 性能不足，也不能仅凭 `Time.frameCount` 判断提交是否发生。新增证据 helper 将 Editor 等待、request 状态与实际 CPU 构建工作分别保存到唯一输出目录。

测试现在在每批异步 readback 入队后调用一次 `GL.Flush()`，验证 D3D12 pending command list 是否是等待原因；保持原异步 callback、错误检查和 10 秒上限，没有同步等待兜底。Unity 的接口合同见 [GL.Flush](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/GL.Flush.html)。是否解决必须以本轮回归为准。

CPU fallback 的 scenario 11 原先等待 10 秒，仅执行约 343ms 构建：每个 Editor test step 间约 100ms idle 被混入完整 Mesh 的功能超时。该功能测试改为有界连续调用正式 LateUpdate，每次仍保留 2ms/8192 工作预算，外层限制 10 秒及 16384 步；证据明确标注不代表真实帧率。

坡面法线测试先隔离自己的 Physics layer，排除其他夹具地形污染后，反半球样本由 11 个降为 1 个。剩余点位于实际坡体之外，旧 local X/Z 投影仍误把它当坡面主体。分类改用自有 Collider 的重力方向支撑，完全不读取待验 Normal；新增两个真实支撑正例与一个记录的坡外负例。原穿透、面积、法线阈值和正样本非空断言保持，坡外样本仍记入诊断。此用例不覆盖坡外薄液帘的完整视觉体验，也没有修改生产 Compute/Shader。
