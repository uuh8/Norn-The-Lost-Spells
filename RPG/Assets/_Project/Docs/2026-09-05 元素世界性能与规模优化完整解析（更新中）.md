## Task A1：把“水为什么没有生成”拆成可以证明的状态

这一 Task 的目的，是先建立不会误导我们的观测系统。玩家发射水球后，写入要依次经过世界路由、固定容量的 Spawn Queue、CPU 向 GPU 提交 Dispatch、GPU 从 Free Stack 取得空槽、低频 Gameplay Readback 聚合，以及角色 Exposure 查询。此前 Inspector 虽然能看到若干数字，但 Pool Counter 与 Activity Counter 交替回读，时间并不相同；“请求已入队”也容易被理解成“GPU 已经生成”。本次把这些状态分开，并给异步样本加入版本和时间。这样池满时能够证明失败发生在容量分配，而 Gameplay 延迟或 Exposure 截断也会留下不同证据。诊断本身沿用 `AsyncGPUReadback`，没有在正常帧中加入同步 GPU 等待；所有公开结果都是只读值类型，外部工具只能读取，不能反向修改模拟。

### 1. 玩家可见问题与诊断对应关系

一颗 PBF GPU 粒子是模拟与渲染共用的离散样本，同时携带材料身份。每颗粒子代表多少 Gameplay 数量由材料配置决定：当前 Water 为 8，Poison 与 Sticky 为 4。这里不存在独立的“Gameplay 粒子池”；Gameplay Bridge 低频读取同一批 GPU 粒子，再把它们投影到世界格子。

当一次水写入没有形成可见水时，需要依次辨别：请求是否进入 Queue、CPU 是否提交了对应粒子数量、GPU 是否还有 Free 槽、Dropped 是否增加、Gameplay Snapshot 是否在提交后完成并发布、Exposure 查询是否碰到 64 个候选上限。统一材料换算比例会改变固定写入量对应的粒子数，因此会同时改变容量消耗、初始 Spawn Packing 尺寸、接触采样和反应数量粒度。Phase A 保留 8/4 配置，后续用“相同 Gameplay 写入量”与“相同 GPU 粒子数”两种对照分别判断性能和玩法影响。

### 2. 数据所有权与 Runtime 调用链

GPU 流体运行组件（`GpuPbfFluidRuntime`）唯一拥有 Pool、Activity、固定 Tick 与 Spawn 提交统计。每次 Development Counter 请求发起时，会冻结本次读取的是 Pool 还是 Activity 以及请求时间；回调按照这份冻结信息解释 Buffer。Pool 样本在同一次回读中取得 Alive、Free、Dropped，只有 `Alive + Free == Capacity` 才满足容量守恒。资源释放时旧样本立即失效，避免重新初始化期间把上一代 Buffer 写成当前状态。

玩法占用桥接组件（`FluidGameplayOccupancyBridge`）分别记录 Readback 请求、GPU 完成和 CPU 聚合发布时间。失败只增加错误次数，上一份成功 Snapshot 的版本和时间保持不变，因此“有一份旧数据”和“刚刚成功更新”不会混淆。CPU 世界协调器（`ElementWorldRuntime`）记录最近一帧实际执行的 Tick、因追赶上限而丢弃时间债务的帧数，以及已经完成的写入、拒绝写入和反应对累计量。角色环境接触系统（`ElementWorldExposureSystem`）公开最近一次候选 Collider、唯一状态目标和状态提交次数；NonAlloc 数组达到上限时设置 `LastQueryMayBeSaturated`。

### 3. Profiler Marker 与测量边界

`GpuFluid.SubmitTick` 表示 CPU 为一个完整 GPU PBF Tick 组织并提交命令所花的主线程时间，它不等于 GPU 执行时间。`GpuFluid.Gameplay.Request` 观察 Readback 请求边界，`GpuFluid.Gameplay.Aggregate` 观察回读完成后把粒子聚合为 Gameplay Cell 的 CPU 成本，`ElementWorld.LiquidReaction` 观察液体与 Cell Fire 的反应规划。后续必须结合 GPU Module、Frame Timing 与这些 Marker 判断瓶颈，不能仅凭一个 CPU Marker 推断 Shader 成本。

所有计数都避开每帧 `new`、LINQ、Closure、Delegate 和 Boxing。回调 Delegate 在 `Awake` 缓存，诊断快照是 `readonly struct`。Submitted Particle Count 在 Spawn Dispatch 成功提交后按请求中的粒子数累计；它仍只代表“提交给 GPU”，实际生成数需要下一份同一时刻的 Pool Counter 证明。

### 6. 本轮旧测试失败的完整定位过程

用户首次运行得到 307 Passed / 39 Failed。大量用例在初始化时报告 Sticky 不在 Material Catalog；用户补齐生产 Catalog 后，结果变为 335 Passed / 11 Failed，说明这次修正解决了共用生产资产的初始化问题。继续追踪发现 Exposure 测试自己创建了仅有 Water/Fire/Poison 的 Catalog，却引用已经包含 Sticky 的默认反应表，因此仍会在 SetUp 失败。修复是在这个独立 fixture 中加入 Sticky 及 Unsupported 路由，保留生产 Catalog 的严格校验，不能为了测试通过而跳过反应依赖验证。

其余四类问题分别为：Bounds 计算发生浮点舍入而测试要求 Vector3 逐位相等，改为小于 0.00001 m 的空间误差；远处粒子的 Gravity 测试漏设 `_MaxSpeed`，导致速度被截为零，补齐该 Kernel 输入以消除跨测试 uniform 残留依赖；只有 3 GMU Water 的测试却期待按 1:2 移除 10 GMU Fire，正确期望应为 6，并新增 5 Water/10 Fire 对照；默认状态投影已含 Sticky，旧测试仍期待只有三项，改为显式验证四项。全部都是可追溯的 fixture 或断言问题，没有修改生产 Shader、反应比例或放宽有效性规则。

## Task A2：把实验输入变成可重放排程

这个 Task 让我们能够比较两次运行，同时知道它们受到的是同一批输入。手动点击包含动画、飞行、手速和落点误差，不适合直接回答“保留 4096 粒子比保留 8192 粒子贵多少”。实验 Profile 因此记录预热、填充、稳定、测量和等待诊断的独立时间，指定每批粒子数、间隔、材料和世界坐标落点。Lab 启动前克隆配置、验证它并一次性生成事件数组；运行中只推进数组索引。负载经过现有 ElementRuntimeRegistry，仍接受真实路由、Queue、Spawn Packing 和 GPU 容量约束。这个设计保留了底层工作量的可比性，同时把真正的水球投射物、角色动画和实战相机留给后续端到端回归。

### 1. 配置、排程与 Unity 生命周期

`ElementWorldPerformanceProfile` 是 ScriptableObject 资产，保存一套实验条件。它在启动前拒绝空引用、非有限时间、非法路线和超过 ushort 的单次材料写入，避免在测量中抛异常或扩容。`ElementWorldPerformanceSchedule` 接受初始化分配的事件数组所有权；每条 `ElementPerformanceWrite` 都是包含序号、计划到期时间和生产 ElementWriteRequest 的值类型。实际出队只递增一次索引，拒绝的写入也不会重试，因为重试会悄悄改变输入量。

`ElementWorldPerformanceLab` 在 Start 确认世界初始化完成后启动。Warmup 用于吸收首次资源和代码开销；Prefill 分批填充；Settle 留出流体稳定时间；Measure 收集可比较窗口；Drain 等待请求时间晚于最后一次写入的 Pool 与 Gameplay 样本。每帧最多补发 MaxWritesPerFrame 条，超过预算的事件保留 FIFO，并记录 LatenessSeconds。这样卡顿可见，同时不会制造无限补算。

### 2. 玩法对照与移动责任

InterestOnly 移动独立活动中心，CameraOnly 移动独立相机，TravelReturn 沿明确路线往返。它们帮助区分 Bounds 改变造成的求解唤醒与相机运动造成的渲染负担。玩家控制器完全不参与实验移动。清洗目标在 Measure 开始时通过 StatusController.ApplyStatus 获得指定初始状态，之后读回 Burning/Wet/Poisoned/Sticky 曲线；干燥对照同样经历自然衰减，因此不能只看到负面状态降低就宣称清洗成功。

停止与禁用恢复原 VSync、targetFrameRate 和实验 Transform。一次进程仅允许运行一套配置，下一次对照重新启动 Player，确保粒子池和静态状态从干净状态开始。命令行 `-ewperfScenario <id> -ewperfQuit` 从预绑定资产选择配置并在导出后退出。

### 3. 创建的源码与验证

- `Diagnostics/ElementWorldPerformanceProfile.cs`：实验数据与启动前验证，属于 Game.ElementField。
- `Diagnostics/ElementWorldPerformanceSchedule.cs`：纯排程与粒子预算拆批，不持有 Unity 场景对象。
- `Diagnostics/ElementWorldPerformanceLab.cs`：Unity 生命周期、生产入口提交、状态读回、停止恢复。
- `Editor/ElementPerformanceSceneSetup.cs`：仅 Editor 的独立场景、28 个 Profile 与 Windows Build 创建入口，使用 AssetDatabase、SerializedObject、EditorSceneManager，资产不手写 YAML。
- `Tests/ElementField/ElementWorldPerformanceScheduleTests.cs`：跨帧跳跃 FIFO、8192 粒子完整拆批、8193 粒子最后余数、时间倒退与 Amount 溢出。

新增测试先因缺少合同而编译失败，实现后静态编译通过；Unity Test Runner 发现 TestCase 的 int 与 uint 装箱类型不匹配，改为明确的 uint 常量后通过。实验场景已经由 Editor 创建；真实 Player 负载与视觉验收在后续记录。

## Task A3：保留原始证据，再在测量外统计

这个 Task 解决“测到了一个数字，却不知道它代表哪一帧、是否有效”的问题。CPU 帧间隔、主线程、渲染线程、GC、GPU timing、Pool 和 Gameplay 并不共享一个完成时刻。采集器因此保留每种数据原有的有效性和时间，CPU Recorder 标明读取最近完成帧，GPU timing 保留自己的 frameStartTimestamp，以及它何时被 CPU 收到。所有样本数组在开始前分配，测量中只写值类型；数组满时停止并标记 Incomplete，绝不覆盖最早的异常。停止后再排序、拼接字符串和写盘，把报告生成开销放在测量窗口之外。

### 1. 时间、有效性和分位数

`PerformanceMetricSample` 的 Valid=false 表示没有证据，不能自动解释为 0 ms。`ElementWorldPerformanceStatistics.Calculate` 过滤无效、NaN 和 Infinity，使用 nearest-rank：排序后取 ceil(p×n)-1，下标分别对应 P50、P95 和 P99。全缺失时结果继续无效。相同平均帧率下，P99 可以暴露少量严重卡顿，因此报告同时保留分位数与最大值。

GPU Frame Timing 延迟到达，所以 phaseAtReceipt 只说明接收阶段，不宣称它就是 GPU 执行阶段。本版导出独立 GPU 原始流，尚未建立严格窗口映射时不发布 GPU 窗口分位数。Pool 的 Alive/Free/Dropped 属于同一份样本；Activity 与 Gameplay 有各自版本，读取者必须比较 RequestedAt 才能判断数据年龄。

### 2. 资源所有权与导出

`ElementWorldPerformanceCapture` 拥有固定 CPU/GPU/Event 数组与 ProfilerRecorder，容量为 262144 帧和 16384 事件。Stop/Dispose 释放 Recorder，OnDisable 同样收口。`ElementWorldPerformanceExporter` 只接受停止后的 Capture，写出 configuration.json、manifest.json、frames.csv、gpu-frames.csv、writes.csv 和 summary.json。路径冲突拒绝覆盖，异常保留内存样本；CSV 引号、逗号和换行按标准转义，数字使用 InvariantCulture，缺失指标在 JSON/CSV 中写为 null。

### 3. 文件责任与验证范围

- `Diagnostics/ElementWorldPerformanceCapture.cs`：原始数值仓库、Recorder 与 FrameTimingManager 读取、容量停止。
- `Diagnostics/ElementWorldPerformanceStatistics.cs`：纯分位统计与缺失值规则。
- `Diagnostics/ElementWorldPerformanceExporter.cs`：测量后的文件输出与统计，不在 LateUpdate 写盘。
- `Tests/ElementField/ElementWorldPerformanceStatisticsTests.cs`：缺失过滤、nearest-rank、空数据与非法 count/scratch。
- `Tests/ElementField/ElementWorldPerformanceExporterTests.cs`：null 保留、特殊字符、路径覆盖/逃逸拒绝，以及写满后保留首个事件。
- `Editor/ElementPerformanceGateRunner.cs`：显式请求的 Editor TestRunner API 入口，先刷新并等待 Domain Reload，再执行最新测试，导出真实结果 XML。

当前 ElementField 与 Rendering 合计 517 个 EditMode 用例全部通过，包含上述新增用例、真实 GPU fixture、材质出现位图和错峰刷新 Pure Planner 测试。测试执行器还暴露了 Unity 中 NUnit WorkDirectory 可能为 null，测试已使用系统临时目录回退。Player 编译曾因旧 Editor 仍加载不含新字段的 Lab 类而出现 Editor/Player layout mismatch；根因是外部请求早于 Domain Reload，已对打包请求加入同样的刷新等待。真实性能、GC 与开关采集的 A/B 仍以实际 Player 结果为准。

## Task A4：Development Player 核心基线与玩法故障复现（核心完成，扩展矩阵待续）

这一 Task 把“残留多会卡”和“水球偶尔不出水”变成可以复现、可以比较的实验。首先固定当前机器、1920×1080、DX12、Development Player，并让每次实验重新启动进程。其次将空场、固定水粒子量、满池继续写入和角色清洗分开，让性能与玩法各自具有对照。这里的目标 60 FPS 对应每帧 16.67 ms；报告使用真实帧间隔的 P50/P99，不能把主线程 Recorder 的等待时间解释为纯 C# 计算，也不能把采集到的异步 GPU 数字强行贴到同一 CPU 帧。当前已经取得九轮有效核心基线，容量故障也由计数器与清洗状态曲线交叉确认；扩展矩阵、隔离对照和退出稳定性仍在验证，因此本节保留“执行中”。

### 1. 测量工具自身的问题怎样被排除

第一次空场 Smoke 失去焦点后停了很久。项目默认 `runInBackground=false`，所以窗口焦点影响实验时钟；同时 `Time.unscaledDeltaTime` 没有如实反映暂停缺口。该次目录 `A00-empty-20260905-173243-125` 判为无效，不进入基线。专用 Lab 启动时临时设置 `Application.runInBackground=true`，停止后恢复；帧间隔改为相邻 `Time.realtimeSinceStartupAsDouble` 的差，另存 Focused 标志。记录位置放在阶段切换之前，防止 Measure 末尾的大卡顿被归到 Drain，导致统计看起来更好。

这些设置只属于专用实验，窗口切换与初次分配由 Warmup 吸收。结果里的 `renderMs=null` 表示本机 DX12 没有取得有效 Render Thread Recorder，绝不能读成 0 ms。GPU 原始时间仍单独保存。

### 2. 九轮核心基线：性能与容量分别成立

硬件：AMD Ryzen 9 7940H、RTX 4070 Laptop GPU、约 32 GB RAM；Unity 6000.3.16f1，DX12，1920×1080，VSync=0，uncapped。此处使用三次运行各自的数值范围，不把所有帧混在一起冒充一次实验。空场指没有液体粒子，三个生产 Surface Renderer 仍然存在。

| 实验（三轮） | 帧间隔 P50 | 帧间隔 P99 | 最终 Alive / Dropped | Measure GC 最大值 |
|---|---:|---:|---:|---:|
| A00 空场 | 3.455–3.472 ms | 6.178–6.350 ms | 0 / 0 | 0 B |
| A01 4096 个水粒子 | 17.549–17.595 ms | 21.756–22.072 ms | 4096 / 0 | 0 B |
| A04 8192 填满后再提交 1024 | 28.933–29.234 ms | 33.508–33.912 ms | 8192 / 1024 | 0 B |

核心结果目录的 UTC 后缀范围为 `20260905-174007-034` 至 `20260905-174744-764`，位于 `Application.persistentDataPath/ElementPerformance`。`Tools/ElementPerformance/summarize.py` 在 Player 停止后读取 manifest、CSV 和 summary，输出逐轮汇总；它不改写原始证据。

CPU Enqueue 成功只说明写入进入队列。GPU 真正执行 Spawn 时要从 Free List 领取槽位，满池时没有槽位可领，因而这三轮始终 Alive=8192、Free=0、Dropped=1024。这与 Solver 是否休眠是两件事：Sleeping 保存粒子身份与空间残留，仍然占用槽位。仅仅加强 Sleep 无法修复容量耗尽。

### 3. 清洗必须和自然衰减对照

Burning 的第一组 dry / water / full 已完成。有空间时 256 个新水粒子成功生成，Probe 的 Wet 达到 100；满池时新增 256 个粒子全部 Dropped，Wet 全程为 0，dry 同样没有 Wet。专用隔墙把预填充旧水隔在 Probe 之外，避免旧水流到脚下，伪装成满池新水生成成功。不能仅凭 Burning 变少判断洗净，因为 dry 对照本身也会衰减。

状态场景已经观察到 192 B / 432 B 的个别 GC 样本，因此不能把核心三组的 0 B 扩大成“全游戏零 GC”。状态首次激活的 VFX 实例化是待对齐的来源，需要结合具体帧和调用链进一步判断是否属于持续热路径。

## Task B1：跳过确定为空的材质液面（已实现并完成核心验证）

## Task B3：统一生产液体的 Gameplay Amount 比例

最终选择统一为每颗 GPU 粒子 8 个 Gameplay Amount Units。原因来自当前生产数据而非“比例完全不影响渲染”的假设：Water、Poison、Sticky Projectile 的 `_totalAmount` 都是 1600、半径都是 0.75；旧配置会分别生成 200、400、400 个粒子。按质量/静止密度估算，每颗粒子的体积都约为 0.001–0.00109 立方米，因此旧 Poison/Sticky 在同一法术数量下约有 Water 两倍的物理体量，同时更快占满全局 Pool。

现在三种生产 `LiquidMaterialProfile` 都使用 8:1，同样的 1600 Amount 会统一生成 200 粒子。材料差异继续由质量、静止密度、Viscosity、Cohesion、Sleep Threshold、Shader 材质和状态投影表达；“毒更强”“粘液更黏”不再借由偷偷多生成一倍粒子实现。这样降低 Poison/Sticky 法术的 GPU 成本和池占用，也让 Gameplay Amount 成为统一计量单位。

这个比例会影响 GPU 表达：同一个旧 Poison/Sticky 写入现在粒子数减半，覆盖范围与液面体量可能变小；总 Gameplay Amount 仍是 1600，但它分布到 Cell 的方式会变化。因此该修改需要真实 Projectile 的视觉、接触与反应回归，不能称为免费优化。底层仍保留 per-material scale 能力，Focused Test 中 4:1 的假数据继续用于证明算法没有硬编码 8；只统一当前三种生产资产。

Phase C 当时已把生产资产与对应 Spawn Planning 测试改为 Water/Poison/Sticky 全部 8:1，并通过当时的 517 项 Unity Gate；Phase D 完成后的全量 Gate 已增长到 576 项。P7/P8 自动 Smoke 已验证生产场景初始化、写入和粒子池无丢弃；实际从 Wizard 连续发射三种 Projectile 后，对可见体量、接触覆盖与手感的人工 Playthrough 仍属于玩家视觉验收。

## Task C1：远处流体归档的安全地基（已实现，尚未启用自动 Streaming）

这一 Task 开始解决“Sleeping 降低计算却仍占 GPU slot”的容量根因。空间上把玩家当前 Active Chunk 范围再外扩 `WarmPaddingChunks` 得到 Warm Region；范围内流体继续留在 GPU，范围外才允许成为归档候选。正常移动等待 `ArchiveGraceSeconds`，避免玩家在边界附近来回一步就反复搬运；当 Free 粒子小于 Gameplay Reserve 时可以跳过等待，但 Archive/Restore 仍只能有一个事务进行。

GPU Readback 的临时数据逐粒子保存 Position、Velocity、Material 和 Flags，共 32 byte；RAM 的长期数据按 `(Chunk, Local Cell, Material)` 聚合，Amount 使用 `uint`，Water 与 Poison 即使位于同一 Cell 也不会互相覆盖。速度只保留平均值，这是用少量 RAM 换取远处物质持久化的精度 trade-off。Builder 与 Store 都在构造期预分配 Open Addressing 数组，运行时聚合不创建 Dictionary/List；Store 提交前先验证 Chunk/Record 容量，失败不发布半份数据，删除使用 Tombstone 保持 Hash 探测链有效。

粒子 Metadata 布局升级到 v9：`ArchiveLocked` 表示 GPU 仍是权威、粒子仍可见，但普通 Activity 和 Solver 不能再改它；`RestoreLoading` 预留给恢复中的未激活 slot，不参与 Surface、Hash 或 Gameplay。归档 GPU 流程已经具备四步：锁定 Warm 外候选、按原 slot 打包、CPU 失败时取消并恢复 Simulation Lease、CPU 成功时用 CAS 清除 Metadata 并把每个 index 恰好一次推回 Free Stack。释放拆为 Core 与 Auxiliary 两个 Kernel，把 D3D11 每个 Kernel 的 UAV 数量控制在 8 以内；最初 10 UAV 的 Shader Warning 已经通过这个拆分消除。

当前 Runtime Backend 能冻结 Transaction Id、Layout/Topology Version、Bounds、坐标参数和 Amount Scale，并持有 exactly-one Readback Lease。最新静态编译为 0 Warning / 0 Error，Unity ElementField + Rendering Gate 为 529 Passed / 0 Failed / 0 Skipped；真实 GPU fixture 验证 3 个 Alive 中只释放 Warm 外 2 个，最终 Alive=1、Free=3，近处 slot 保持不变。Feature Toggle 仍为关闭，因为自动 Async Readback 调度、Cold Chunk 恢复和 Gameplay Query 权威切换尚未接完；现在打开只会形成“能安全归档、不能自动回来”的半条链，不能用于生产场景。

## Task C2：自动 Archive 调度与失败回滚（已实现，Feature Toggle 继续关闭）

这一 Task 把 C1 的手动 GPU Archive 能力接成了自动半链。玩家的 Interest Chunk 变化后，系统计算 Warm Region 并开始 Grace 计时；Grace 到期时归档范围外粒子。GPU Free Particle 小于 Gameplay Reserve 时会立即触发容量回收，不依赖玩家刚好跨越 Chunk。Runtime 同时只允许一个事务，避免两次 Readback 对同一粒子争夺权威。

异步时序采用两阶段提交。GPU 首先给范围外粒子加 `ArchiveLocked`，此时 GPU 仍是唯一权威，粒子不会提前消失。`AsyncGPUReadback` callback 只把 transaction 标记为完成或失败；下一次主线程 `Update` 才运行 Builder、尝试原子提交 RAM Store，并根据结果二选一：提交成功则释放 GPU slot，失败则取消锁定，让原粒子继续模拟。这样 Driver callback 不会在不可控时刻修改世界状态，也能统一处理 Readback error、Store capacity failure 和组件销毁。

Readback 被抽成初始化期创建的 Scheduler。生产 Scheduler 包装 Unity 静态 `AsyncGPUReadback` API，测试 Scheduler 可以精确控制 callback 到达时机。这个抽象不是为了替换 GPU，而是为了证明“callback 到达”和“权威切换”之间必定隔着一次 Runtime Tick。所有 Delegate、`NativeArray`、Builder、Store 和 Pending Queue 都在初始化边界创建；归档热路径没有 LINQ、临时 List 或逐帧数组。

流体写入口已经从 `ElementWorldRuntime` 接到 `FluidChunkStreamingRuntime`。Warm 内写入仍立即下发给现有 GPU Deposit Sink；与正在归档的范围相交或命中 Cold Chunk 的原始 `ElementWriteRequest` 进入固定容量 FIFO，完整保留 Position、Material、Amount、Radius、Falloff、Velocity 和 SurfaceNormal。恢复链尚未完成，因此这些 Pending Write 本 Task 只保证不被错误下发或覆盖，实际重放将在 Restore 与单写者权威集成 Task 完成。

## Task C3：确定性 Restore 粒子规划（Task 5 前半，已实现）

RAM Archive 保存的是 Cell 总 Amount 和平均速度，GPU PBF 需要重新得到逐粒子 Position、Material、Velocity 与 Transaction Id。`FluidChunkRestorePlanner` 先严格检查 `Amount % AmountUnitsPerParticle == 0`，只有整除时才生成 `Amount / Scale` 个粒子；损坏记录直接拒绝，不能用 Ceiling 悄悄创造额外物质量。Water、Poison、Sticky 当前生产比例统一为 8，但 Planner 仍接收显式 scale，因此算法没有硬编码某种材料。

同一 Cell 内使用确定性的三维 lattice 排列，lattice 间距由 CellSize 和粒子数计算；每个位置只加入不超过格距 15% 的稳定 jitter。Seed 只来自 Chunk Key、Local Cell Index、MaterialId、Snapshot Version 和 Cell 内粒子序号，不读取 `UnityEngine.Random`，所以相同 Archive 在不同运行中会得到相同上传结果。完整重载还显式接受 World Origin、ChunkSize 和 Transaction Id，负 Chunk 坐标通过 long/double 中间计算，避免整数乘法回绕。

## Task C4：GPU all-or-nothing Restore 与 Cold Chunk 恢复（已实现）

Restore 不能逐粒子 Pop Free Stack，否则池在中途耗尽时会留下半滩液体。`ReserveRestoreSlots` 由单个 GPU Thread 检查 `required <= freeCount` 且 `gameplayReserve <= freeCount - required`，成功后一次性扣除整批容量并冻结 FreeIndices 区间；失败时 Counter、FreeIndices 和粒子 Slot 全部不变。

Stage 分为 Core 与 Auxiliary。Core 写 Position、PredictedPosition、Velocity、Material，并只设置 `RestoreLoading`；粒子此时没有 Alive，Solver、Surface 与 Gameplay 都看不到半成品。Auxiliary 清理 Density、Delta、Stable Tick 和 Wake。拆分后各 Kernel 均不超过 D3D11 的 8 UAV 上限。

CPU 异步读取 16-byte Transfer Status，只有 Succeeded、TransactionId 和 ParticleCount 全部匹配才 Activate。Activate 根据 ActiveBounds 设置 Interest Active 或 Remote Spawn Active，并增加 ActiveCount。错误状态、Readback failure 或组件销毁执行 Rollback；它只回收仍为 RestoreLoading 的 Slot，因此重复 Rollback 不会重复增加 FreeCount。

Streaming Runtime 每次选择 Warm Region 内距离 Interest Chunk 最近的 Cold Chunk，用预分配数组展开并上传。GPU Activate 后 RAM Archive 继续持有 Gameplay 权威；Gameplay Occupancy 的 Topology Version 追上 Restore Version 后才删除 Cold Record，避免查询空窗。静态 Rebuild 为 0 Warning / 0 Error，Unity 完整 EditMode Gate 为 544 Passed / 0 Failed / 0 Skipped。下一 Task 将完成组合 Gameplay Query、Pending Write 重放及 Reaction/Exposure 的单写者边界。

## Task C5：Gameplay Authority 与 Pending Write 闭环（已实现）

完整运行链现在是：

```text
Projectile
→ ElementWorldWriteRouter
→ FluidChunkStreamingRuntime
→ Warm: GPU Deposit / Cold 或 Transfer: Pending FIFO
→ Archive / Restore Transaction
→ Material Query 与 Exposure 读取组合权威
→ Reaction 只读取已发布的 GPU Gameplay Snapshot
```

Streaming Runtime 同时实现流体写入和只读 Gameplay Occupancy。查询 Global Cell 时先计算 Chunk：RAM Store 持有该 Chunk 且它位于 Warm Region 时，Archive Amount 饱和到 byte 后返回；Cold Region 外返回 false，使离屏角色和反应暂停；Store 不再持有时转发到 GPU Gameplay Bridge。SnapshotBounds 始终限制为 Warm Region，不会因为历史 Archive 扩展为覆盖整张地图的巨大 Broadphase。

恢复提交后，GPU 粒子已经可见，但 Store 在 Gameplay Topology Version 追上前继续是唯一查询权威。`CopyOccupiedCells` 会剔除 GPU Snapshot 中属于 Archive Authority Chunk 的重复 Cell，再追加 Archive Record，避免同一份物质量相加两次。Topology 追上后才删除 Store 记录并完全切换为 GPU 查询。

Pending Write 采用严格 FIFO。每帧最多检查配置容量次；队首仍覆盖 Cold/Restoring Chunk时停止，GPU Sink 拒绝时也保留队首。恢复和 Topology Gate 完成后，原始请求才下发并成功后 Dequeue，因此不会丢失、重排或重复播放。

`ElementWorldRuntime` 现在明确保留两个读视图：Material Query 与角色 Exposure 使用 Streaming 组合权威；Water-Fire、Poison-Fire、Sticky-Fire Reaction 只读取 GPU Gameplay Bridge。原因是反应结果会生成 GPU Consume/Convert Command，若它读取 Cold Archive，就会计划一条当前根本没有 GPU 粒子可消费的命令。恢复后的 GPU Snapshot 发布后，反应链自然继续。

新增测试验证旧 Topology 下 Archive 仍返回 8 GMU、Topology 追上后切换、Cold 写入恢复后 exactly-once 重放，以及连续 256 次 Idle Tick 与 Warm Query 的 managed allocation 为 0。静态 Rebuild 为 0 Warning / 0 Error，Unity ElementField + Rendering 完整 Gate 为 547 Passed / 0 Failed / 0 Skipped。Scene 中 Exposure 的组件引用和 Feature Toggle 将在 Task 7 统一 Wiring 与 Playthrough。

## Task D1：局部稳定流体从 GPU 粒子转成 Dormant Cell（已完成）

Phase C 只能回收远离活动区域的液体；玩家如果一直站在同一战场，已经静止的水、毒液和粘液仍会占满 8192 个 GPU slot。Phase D 在容量压力出现时，把 Active Region 内已经进入 `Solver-Sleeping` 的粒子压缩为 RAM 中的 `Dormant` Cell Record。这里的 `Dormant` 表示“仍在玩家附近、保留物质量与接触能力，但暂时不执行 PBF 求解”；远处历史数据继续使用 `Cold`，两者共享同一 Archive Store，却有不同的自动恢复规则。

本地归档只依据速度稳定性。最初沿用 Density Error 会让静止但受压的水永久无法休眠；D00 速度分布证明大量粒子速度已经很低，密度误差却因堆积长期存在，因此本地条件改为连续 30 Tick 低于 0.1 m/s。邻居唤醒也增加 0.1 m/s 门槛，低幅数值抖动不会把整片水反复叫醒，真实运动仍会传播 Wake。归档时 GPU 先锁定所有候选，CPU 再按 Cell 排除与仍活动粒子共享空间的样本，最后由新的 Exclude Kernel 解锁这些索引；这样不会把一个仍在流动的 Cell 拆成两个同时运动的权威。

## Task D2：Cell 级权威、静态表现与按需唤醒（已完成）

同一个 Chunk 现在允许部分 Cell 留在 GPU、部分 Cell 存在 Dormant Store。查询端用预分配 Hash Table 合并相同 Cell 的 GPU Amount 与 Archive Amount，`CopyOccupiedCells` 同样去重相加。相同材质的新写入可以直接覆盖 Dormant Cell，由合并查询维持总量；不同材质可能发生 Water/Fire、Poison/Fire 或 Water/Sticky 反应，必须先请求恢复，再把原始写入放入 FIFO。Exposure 命中 Dormant Cell、Fire 扫描邻接 Cell 或显式扰动也会分别以 `Exposure`、`Reaction`、`Write` 原因请求唤醒；同一 Chunk 已在 Requested/Preparing/InFlight/Topology Wait 时会去重。

恢复准备每帧最多展开 128 个粒子。RAM Archive 在整批 GPU Reservation、Stage、Activate 和 Gameplay Topology 发布完成前继续承担唯一查询权威；成功后才移除记录，失败保留原数据并重试。`DormantLiquidCellRenderer` 读取只读 Cell 接口，用固定矩阵缓存和 `RenderMeshInstanced` 绘制低成本静态体积；单批最多 1023 个实例，材质在复制属性后再启用 GPU Instancing，避免 Unity 把开关覆盖。唤醒完成后原 GPU Surface 重新接管。

## Task D3：满池 Backpressure 与异步容量快照（已完成）

第一次 D01 虽然能够持续归档，却仍出现 2417 个 Dropped。根因是 `AsyncGPUReadback` 的 Free Count 是过去某个提交点的快照：CPU 在下一份快照回来前继续相信旧的 Free 值，多个 Spawn Request 会重复消费同一份“可用容量”，最终由 GPU 丢弃超额部分。

新的保守容量预算（`FluidSpawnCapacityBudget`）在 CPU 接受请求前先 Reserve，并记录累计接受量。Pool Readback 同时捕获 Submitted Watermark；回调发布 Free 时，预算会扣除快照之后已接受、但快照尚未看见的粒子。Archive/Restore 会直接改变 Free Stack，因此每次 Transfer 开始先让预算失效，直到同一 Mutation Version 的新快照返回。预算不足或 Spawn Queue 暂满时，Streaming Runtime 不再把请求当作处理完成，而是保存完整 `ElementWriteRequest`，之后按 FIFO exactly-once 重放。这条 Control Plane 在 Release 也必须工作，所以低频 Pool/Activity Readback 不再被 `DEVELOPMENT_BUILD` 条件整体裁掉。

性能 Lab 的 Drain 同时等待 World Queue、GPU Spawn Queue 和 Streaming Pending Queue 清空；旧判据只看前两者，会把“还剩一条待重试写入”错误标成完整。Sandbox Gate 也补上后台推进，并把无候选或过期容量引起的安全 Rollback 与 Readback Error 区分开。

## Task E3：GPU 粒子按同一 Region 并集分类（已完成）

CPU 把最多 32 组 Region Min/Max 上传为 Compute Shader uniform array。这里的 uniform 是一次 Dispatch 共享的小参数，和保存粒子的大型 UAV Buffer 不同，不会新增一套粒子资源，也不会占用 DirectX 11 的 UAV 槽。`PbfParticleLifecycle.compute` 的 `InsideActivityRegions` 对每个粒子做一次 OR membership，控制 Interest、Archive 候选和 Restore 激活；Solver 不会按来源重复 Dispatch，所以重叠来源不会让粒子获得两次 Gravity 或把时间推进两遍。

Archive 是跨多帧事务。若 Begin 时来源在 A，Readback 完成时来源已移动到 B，用完成帧 Region 重新解释旧候选就可能同时失去 GPU 和 RAM 权威。现在 `FluidChunkStreamingRuntime.Activity` 在 Archive Begin 复制一份 frozen Region set，GPU Lock、CPU filter 与 Commit 全程使用同一份快照。多个 Write/Exposure/Reaction 唤醒进入有界去重 FIFO，前一个请求不会被单字段覆盖；恢复仍遵守 `Reserve → Stage → Activate → Topology Gate → 删除 RAM 权威`。

`FluidChunkArchiveStore` 原先在 Commit 中为每条 Cell Record 线性扫描已经见过的 Chunk，形成 O(Records × Chunks) 峰值；现在使用预分配 open-addressing scratch table，把 Chunk 状态查找压到平均 O(1)，同时保留 all-or-nothing Commit。Camera 可见性通过 `IFluidVisibleArchiveReadOnly` 只复制视锥 AABB 中的 Cold/Dormant Cell 给静态实例 Renderer，不触发 Restore。E03 中 Camera 移动前后 Archived 始终为 1642、Restored=0，活动仍是 3 Regions/2 Sources。

`GpuLiquidSurfaceRenderer` 保持以 Camera 为中心的固定世界尺寸 Density Grid。它不会为了同时包住远端单位而拉伸一个网格，否则每个 Voxel 代表的世界尺寸变大，近处液面会失去细节；远端动态精细 Surface 仍受当前单个 Camera Grid 预算限制，静态残留由 Dormant Renderer 表达。

## Phase F 进行中：原始多源负载积压修复与回归（2026-09-09）

### 1. 症状、根因与实现取舍

活动范围内的休眠记录称为 Dormant；活动范围之外的冷记录称为 Cold。来源移动后，一个原来保存为 Dormant 的 Chunk，可能在下一次归档时应该成为 Cold。过去 Store 对分类不一致直接拒绝，使整批归档回滚，GPU 空间不能及时释放。现在先检查所有记录、容量和数值合并是否可行，再把本批涉及的 Dormant Chunk 原子重分类为 Cold，并合并材料量。预检失败不修改权威数据；反向 Cold→Dormant 仍要通过 Restore，防止未恢复的数据绕过活动区恢复流程。

同 Cell 中有 Awake 粒子时，原逻辑会排除该 Cell 的 Sleeping 归档候选；高负载下这限制了可回收空间。目前实现允许 Sleeping 子集进入 RAM，Awake 留在 GPU，查询端合并两份不同粒子的材料量。**这一修改的数量结果已有回归，物理等价尚未成立。** RAM 数量查询没有自动成为 PBF 的密度邻居或碰撞边界，不能以 GMU=0 差额推断堆积形状、扰动传播和接触反应完全连续。必须继续验证这一边界；必要时补充表示之间的物理交互机制。

曾经把来源移远、写入点移到 x=64 的隔离实验只能用于缩小问题范围，不能当作原负载的修复证明。本次明确恢复原配置后重新运行。旧 D01 的21粒子等效差额同样不能未经证据归因为量化；新样本闭合也不能反推旧样本根因。

### 4. 独立Player的CPU余量与GPU证据缺口

当前代码的DX12、1080p、Development Player原始F02单轮完整提交18432粒子当量，Pending/Dropped为0，Water/Poison/Sticky Audit有效且未解释GMU均为0，Drain约0.518秒，Measure GC Max为0B。Limited的Interval P99为18.4166ms，因此严格18ms门槛仍失败；没有超过33.33ms的帧。相同Build的Uncapped结果为Main P99 4.8257ms、Interval P99 4.9917ms、Max 8.2539ms，说明CPU侧在不等待60 FPS节拍时具有余量。两种模式行为不同：Uncapped不能替代Limited的玩家帧间隔体验，也不能凭CPU低耗时推断GPU已完成。

更关键的证据缺口是两轮`gpu-frames.csv`都没有有效GPU时间：Limited 5419条、Uncapped 213119条全部为null。null表示Unity没有返回正值，不表示GPU耗时0ms。`Assets/_Project/Scripts/ElementField/Diagnostics/ElementWorldPerformanceCapture.cs`因此扩展每条FrameTiming，保存firstSubmit、Present、FrameComplete三个CPU时钟点、CPU总帧/主线程/Present Wait/Render线程时间和syncInterval；初始化时保存FrameTiming Feature、CPU/GPU timer frequency及VSync频率。`ElementWorldPerformanceExporter.cs`把原始字段与有效/缺失计数写入CSV/manifest。`Tools/ElementPerformance/summarize.py`同时兼容旧五列与新格式，缺失GPU数据单独计数，不纳入百分位。

这些字段用于判断测量管线，而非用CPU时间戳伪造GPU Busy Time。FrameComplete减FirstSubmit包含排队和同步含义，只有Unity返回的`gpuFrameTime`才进入正式GPU百分位。先用短A00分别检查DX12和DX11；若仍缺失，再选择Unity Profiler/Recorder或外部GPU采集证据，不能继续堆积没有GPU时间的完整压力样本。

实测进一步确定：隐藏窗口的A00中，DX12/DX11虽然`FrameTimingFeatureEnabled=true`且Timer Frequency有效，firstSubmit、PresentCalled、FrameComplete仍全部为0，GPU时间全缺失；Uncapped还填满262144帧固定缓冲并正确标记Incomplete。原因边界应表述为“当前隐藏运行方式没有形成可用的Present/GPU计时链”，不能扩写成Graphics API不支持。性能Player随后改为可见窗口，避免窗口遮蔽改变Rendering工作量。

可见1080p Target60 A01验证了采集链：DX12 Measure GPU P99 2.536448ms、Interval P99 18.1393ms；DX11 GPU P99 2.297856ms、Interval P99 17.7689ms。这里的GPU样本按`phaseAtReceipt`筛选，测量窗口足够长，但边界帧仍不宣称精确执行时点对齐。DX12单轮出现一次102.5741ms长帧以及后续一帧1036B GC，DX11没有相同现象；在取得Allocation Stack或可复现证据前，既不能归因于元素热路径，也不能忽略。A01只有4096水粒子且Surface off，因此只证明采集能力和轻负载API正确性。正式判断继续使用可见F02以及完整Surface。

### 5. F02可见压力、Surface真实性与Player清洗Harness

可见DX12原始F02在Surface off下得到GPU P99 0.580608ms、FrameTiming主线程P99 4.5045ms、GC Max 0B，18432提交、队列和三材料Audit闭合；Interval P99 18.3893ms仍超过18ms。Surface all单轮GPU P99 0.579584ms、主线程P99 4.7605ms、GC Max 0B，数量同样闭合，但整个Measure窗口失焦，因此只保留为辅助证据。这些数据表明计算本身没有接近16.67ms预算，同时60 FPS软件节拍仍有约1%尾部抖动；后续用显式记录的目标FPS Override验证少量节拍余量，默认样本仍应用60，不能偷改configuration。

Surface all与off数值过于接近时，首先要证明完整路径真的工作。`GpuLiquidSurfaceRenderer.cs`新增只读Target Material、Stage、Geometry Stage、Triangle/Overflow、Rebuild/Draw和Grid计数；每帧只做uint饱和自增，不分配对象。`ElementPerformanceSurfaceIsolation.cs`仅在Development Player退出时输出每种仍启用Surface的最终诊断。若Stage不是DrawReady、Triangles为0或Draws为0，该轮不能被描述为完整画面性能；若有效，再接受GPU本身确实很快这一结果。

Editor在当前机器上无法稳定推进60 FPS，因此F4增加独立Player路径。`Assets/_Project/Scripts/Character/Diagnostics/PhaseFWaterGameplayBenchmark.cs`位于Game.Character，只读取Water Wand、SpellCaster、Combat Projectile与Status，不引用Game.ElementField。真实运行仍是Water Projectile Prefab命中后由其已有ElementField组件提交材料，Character Harness只记录Cast→Impact→Wet和干湿最终强度。这样维持单向Assembly边界，同时让1080p Player提供真实时钟。`ElementPerformanceSceneSetup.cs`只在构建专用性能Scene时挂载Harness并绑定Water Validation Wand；P7/P8生产Scene不添加组件。该路径不读取Water Cell/Snapshot细分，所以与Editor Gate互补，不能取代它的Impact→Water证据。
