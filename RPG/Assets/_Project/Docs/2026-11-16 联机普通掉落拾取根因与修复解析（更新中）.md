# 联机普通掉落拾取根因与修复解析（更新中）

## 1. 本轮要解决的玩家问题

用户确认：问题发生在联机副本；普通掉落物按 F 无法拾取，也不能从“附近物品”拖入背包。此前还反馈施法后反复提示“物品资源正在使用”，停手很久不恢复。单机尚未由用户复现。

本轮沿用已授权的自动回归，实际游玩仍由用户验收。实现计划见 [排查与修复计划](<../../../docs/superpowers/plans/2026-11-16 联机普通掉落拾取根因排查与修复计划.md>)。

## 2. 先区分两种施法状态

`Prepared` 是正在准备提交的短事务。库存已持有一份候选表，随后 `Complete` 会提交它。这时若容许另一条拾取写入，新物品可能被旧候选表覆盖，因此必须继续拒绝所有库存写入。

已 `Committed` 的法术票据不同。Mana、次数和执行图已经确定，输出可能继续等待命中、定时或 Projectile 生命周期。`ActiveReservations > 0` 可能只是表示这份已支付的旧输出还活着，并不表示整个库存仍处于短事务准备期。

旧代码把这两种状态都当作全局库存 Busy：

1. `OnlineCastDriver` 在起手 Timeline 或排队期间直接拒绝所有库存命令。
2. `OnlineOwnedWorkspace` 又在任意活票据存在时拒绝所有库存命令。
3. 原 F 和 Nearby→背包都最终进入这两道门，所以即使 UI 目标、WorldOwner、距离、空格完全正确，也会收到同一个 Busy。

这解释了一种可确定复现的“施法后 F 和拖包同时失败”：有效 Trigger 子层等待时，整套地面拾取一直被锁住。它不要求出现票据泄漏；仅合法的长生命周期就足够复现。

**归因边界**：此前截图中的四 Damage＋Fire Rapid 没有 Trigger，本轮不能把上面的 Trigger 重现宣称为那张截图的唯一现场原因。上一轮空 Trigger 泄漏、无收据 pending 恢复缺口也不能互相替代归因。本轮修复的是已得到失败断言支持的共用拾取忙门。

## 3. 如何取得根因证据

新增四个领域回归，使用正式 Catalog、Owner、ProgramMachine 和共享 Ground Store：

- 真正提交非空 Trigger 根层，并观察根输出；子层保持 `Unattempted`，票据仍活着。
- 权威时间推进 60 秒，保留旧票据，不通过超时取消法术。
- 普通新法术与固定 Ice 256，分别走自动 F 目标和明确背包格位。
- 旧代码四项均在真实 Owner 命令入口返回 Busy。RED 证据保留在 `docs/superpowers/evidence/ordinary-pickup-20261116/passive-pickup-red.xml`。
- 修复后四项都实际迁移同一个地面实例，旧票据保持活跃；随后旧子层仍能 Prepare、Complete、接收输出观察并自然结束。

另补正式 CombatPresentationScope、OnlineGroundItemPresentation 和真实 InputSystemUIInputModule 的 PlayMode 测试。Mouse 的 down、跨 Drag Threshold、移动和 up 都由 Input System 派发，不用 `ExecuteEvents` 代替输入。覆盖新生成实例、原 F、附近拖包、同版本新 Store 重绑以及活 Trigger 票据期间的两种输入。

第一轮两个 PlayMode 的测试主体已完成拾取，但 fixture 清理把 null 写到 `EventSystem.current` 导致错误。已修复为禁用自身 EventSystem、让 UGUI 自行注销；保留首轮失败记录，没有把它当产品 RED 或屏蔽日志。

## 4. 最小修复和为什么安全

`OnlineGroundItemStore.IsStoragePickup` 只读地分类目标，`OnlineOwnedWorkspace.IsGroundStoragePickup` 供 Driver 与领域忙门共同使用。它们不迁移物品、不取消票据、不授予 Client 写权限。

只允许地面物品进入**本人现有装备背包内部**或**本人 SpellStorage**。普通法术 F 保留原优先专区的规则；容器和 Material 沿原包内路径，Material 仍使用原数量合并/身份退役事务。

以下操作继续保持旧保护：自动装备地面背包、直接插入 WandSlot、替换装备、移动旧物品、配置附件。`Prepared`、Store 资源锁、`IsPending`、RaidFrozen、世界权限和退出门仍优先拒绝。身份、Epoch、ExpectedInventoryVersion、WorldOwner、3m 距离、背包占格、资格和收据幂等仍由原路径裁决。

没有另写“加一件到背包”的旁路。成功仍是原 Ground/Owner 双 Store 原子提交，Client 等完整 Snapshot 再更新地面模型和背包。

`PrepareLayer` 使用已冻结的旧 Ticket/Graph；纯收纳只增加新物品或合并包内 Material，不改变旧程序和已有供料瓶。起手阶段的实际 `OwnedWandCastAdapter.Request` 会读取提交时的库存/资源版本。测试同时检查拾取后原施法仍正常 Released、扣费一次，避免“修了拾取却吞掉这次施法”。
