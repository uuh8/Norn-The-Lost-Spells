## 1. 玩家症状与已确定的边界

- 账号进入 Hub 后，Tab 可以出现背包，但鼠标未解锁，画面曾出现“未装备背包”。前者已定位到本机输入所有权；后者涉及账号最低资产初始化，由业务模块独立修复，不能在 UI 伪造一只包。
- 玩家进一步澄清副本拖放是“能抓起图标，松手后回原位/没有变化”。因此应沿 Submit → 网络 → DS receipt → 完整 Owner 快照检查，不能继续把抓起门禁当成已确定根因。
- 原商店在账号模式下不能完整打开/交易。旧 `SinglePlayerInventorySession.ReadOnly` 故意不可用，但旧 Shop UI 和 Session 仍等待该本地入口。
- Home 原门/研究台沿旧 Session 工作。恢复完整实验玩法需要可信单人 DS，不能通过恢复旧 Profile 写权或客户端保存完整 Profile 绕过权威边界。

## 2. Hub Tab：服务器资产来源与本地输入 Owner 是两个维度

### 症状 → 证据 → 根因

账号 Hub 的库存使用 `PresentationSource` override，原 `SinglePlayerInventoryController` 据此一律发送 `InventoryPresentationVisibilityEvent`。该事件用于 DS 场景的本机输入捕获；Hub 角色仍由原场景的 `RunPauseCoordinator` 管理，所以等待一个不存在的副本输入消费者不能解锁鼠标。

旧判断混淆了“资产来自服务器”和“角色在 DS 世界”。账号资产只读并不改变 Hub 的场景输入 Owner。

### 拒绝的方案

- 不把账号分支改回旧本地 Profile，也不生成 UI 专用 StarterKit。
- 不在鼠标显示处无条件写 `Cursor.visible=true`；否则关闭、叠加暂停与换源时无法释放正确 Owner。
- 不让 DS 背包调用本地全局暂停，避免一个玩家的 Tab 暂停整个合作世界。

### 修复与职责

[SinglePlayerInventoryController](../Scripts/UI/Inventory/SinglePlayerInventoryController.cs) 按命令上下文区分：账号 Hub 与本地分支申请原 Inventory pause reason；DS 源继续只申请自己的本机输入捕获。Close 释放相同路径，保留其他 Pause reason。换源先按旧来源 Close，避免把旧 Owner 的释放发到新世界。

### 实际验证

[hub-cursor-green.xml](../../../docs/superpowers/evidence/multiplayer/single-player-regression-20261103/hub-cursor-green.xml)：2026-11-03 09:57:53 UTC 开始的 EditMode，3 passed / 0 failed。覆盖账号 Hub 独立解锁鼠标、Inventory 与其他暂停叠加、DS 分支不误加本地暂停。此前有效 RED 已保留为 `hub-cursor-red.xml`。这不是 Native 用户手感验收。

## 3. 副本拖放：先看真实命令结果，再判断失败层

### 已观察的证据

正式 `CombatInventory.prefab` 的 `_status` 原来没有引用，因此 Controller 即使判断拒绝或收到失败 receipt，玩家也看不到原因。它可以解释“没有反馈”，不能单独证明服务器命令为何失败。

最初尝试在 EditMode 对实际 Prefab 做 native `GraphicRaycaster` 断言，得到 `depth=-1`、已注册且未 cull 的 Graphic。后续还有 EventSystem module 生命周期错误。这些属于测试环境问题，保留原始失败后删除了不适合 EditMode 的七项组合，没有改生产 `raycastTarget` 或伪造 depth。

实际组合迁至 PlayMode。第一次 ground Drop 的预期也被修正：附近区域的合法 `IDropHandler` 是 Viewport 上的原 `InventoryDropTarget(Ground)`，不应强行要求外层区域组件。生产没有为适配断言而改 Raycast。

### 最小可观测修复

[SinglePlayerInventoryController](../Scripts/UI/Inventory/SinglePlayerInventoryController.cs) 的 `SetStatus` 总是保存只读 `LastInteractionStatus`，不要求场景预先接好 Text。最近严格匹配的 receipt、当前等待 CommandId/InventoryVersion 也公开只读，供诊断读取；只读信息不授予命令或资源写权限。receipt 仍严格检查 Actor、Caller、Epoch、Command，失败不会被无关库存快照改写成成功。

[SharedInventoryPresentationTools](../Editor/UI/SharedInventoryPresentationTools.cs) 的导出器在原面板 header 空白处补一条独立 Text：中心锚点 `(0.5,1)`、位置 `(0,-52)`、尺寸 `980×44`、字号 18，`raycastTarget=false`。运行时沿原 Controller 字体配置。文案显示等待与玩家可理解的失败原因，不把协议 ID 塞进玩家画面。导出 SourceHash 标记升级，已有资产须由主 Agent 集中 Export/Verify。

### 实际验证与局限

- [bridge-feedback-envelope-green-home-preview-red.xml](../../../docs/superpowers/evidence/multiplayer/single-player-regression-20261103/bridge-feedback-envelope-green-home-preview-red.xml)：反馈相关三项已 GREEN；同轮 Home 尚未实现的两项 RED 不应隐藏。
- [formal-seven-actions-playmode-green.xml](../../../docs/superpowers/evidence/multiplayer/single-player-regression-20261103/formal-seven-actions-playmode-green.xml)：2026-11-03 11:43:57 UTC 开始的 PlayMode，1 passed / 0 failed。该一项实际覆盖七个动作：wand/card/container → bag，wand/card/container → ground，以及 container → shortcut；通过正式 Prefab、实际 Raycast 和原 handler 发出正确意图。也检查正式有限次数卡片的原 Text 与字体。
- 上述组合使用内存 Authority 生成完整 Source，未连接真实业务/UDP/DS，不能证明玩家当时的旧部署与真实账号命令闭环已经修好。真实一次拖动仍须观察 receipt 和 Owner 快照。

## 4. 账号商店：复用原界面，替换资产和交易适配

### 症状 → 证据 → 根因

账号模式故意不创建旧本地 Profile，但旧 Shop `Start` 协程等待 `_inventory.ReadOnly`，因此永远等不到可用数据。仅删除 Hub 的只读拒绝仍无法解决等待、报价、钱包、库存嵌入与交易结果的整条链。

### 采用的合同与分层

- [OnlineAccountShopContracts](../Scripts/Core/Online/OnlineAccountShopContracts.cs) 只含中立值与 `struct + IGameEvent`。Open 按 Caller/Scene/Inventory 关联；交易 wrapper 保留原 `ShopTradeRequestedEvent`，结果仍用原 `ShopTradeResultEvent`。
- [AccountShopReadModel](../Scripts/Run/Trading/AccountShopReadModel.cs) 将业务库存与受控 Manifest 报价组成的 Core snapshot 投影为原 `IShopReadOnly`。逐字段比较冻结的原 `ShopDefinition`：OfferId、ContentId、材料键、买卖价、次数、是否无限、初始 GMU/库存等均须一致，再使用真实剩余库存。显示名与图标沿原 SO。
- Core/Run 不反向依赖 Shared，不重复实现一套 Hash 算法。`ConfigHash` 表示来源一致性；报价数字逐字段核对才决定本地 UI 是否可用。Client 交易只发 OfferId、数量、目标与 expected versions，不上传价格。
- [SinglePlayerShopSession](../Scripts/Run/Runtime/SinglePlayerShopSession.cs) 保留完整 local 分支；账号分支冻结原配置、发 Open、安装合法候选并转发 wrapper，不创建 Profile、不保存旧 repository。
- [ShopController](../Scripts/UI/Trading/ShopController.cs) 在账号模式读当前 `_inventoryUi.PresentationSource.ReadOnly`、Wallet 和同一实例集，不再等待故意为空的旧 ReadOnly。事件只标记离散刷新，数据未完整确认时不把旧商品行或旧钱包当成当前可交易事实。
- 商店真实嵌入复用原库存 Controller 与原账号 HTTP 结构网关。`SetEmbeddedOpen` 仅给账号上下文解除 blanket 拒绝，DS source 继续不能借此开启 Hub 商店。
- Hub 只在真实商店适配可用且原区域许可成立时开放 Shop，未适配的 Research 没有随之被提前放开。

### 失败与未知结果

匹配当前 Caller 的错误报价或失败回包清掉已经准备的商店读源；错误 Caller 不能破坏当前合法来源。Profile/Shop 版本不一致则等待完整确认，不恢复本地钱包或乐观扣费。

HTTP 结果未知时保留原固定命令身份，由账号桥恢复；UI 不把 Unknown 当成未发生后随意提交另一笔。相关网络与持久事务实现由业务/账号模块记录，本页不把源码存在等同于跨进程验收。

### 实际验证

模型新增 23 项先有效 RED：[shop-model-red-manifest-green.xml](../../../docs/superpowers/evidence/multiplayer/single-player-regression-20261103/shop-model-red-manifest-green.xml) 为 6 passed / 23 failed，失败均为缺少新 ReadModel。后续主 Agent 已观察模型全 GREEN、Shop Start GREEN、账号 embedded HTTP 路径 GREEN、错误报价撤销旧源 GREEN。中间 fixture 的 Unity 6 `SceneHandle` Reflection 类型错误与 internal `Profile` 反射读取错误已修夹具，未把生产字段公开或改 Core int 合同来迁就测试。

后台已有的 Shop/Backpack/Move 41 项通过由主 Agent集中报告；它不代替正式 Hub F → 商店 → 买卖 → 关闭重开 → 重新登录的玩家验收。

## 8. Home 后端：同一次最终事务保存携带物、原地面和真实消耗

### 玩家路径与边界

Home 仍是个人和平实验场。业务服冻结本人的完整账号 Profile，携带闭包进入 `CombatAssets`，原 `home.map1` 地面根及安装卡保留在完整 Profile 的 `Items/WorldItems`。两个集合都登记到当前 Run 的 custody，地面不会混入携带背包。入场不赠送副本开局瓶，不允许合作创建 Home，也不接受 Home 最终死亡清包或经济成功进度。

和平往返的 Mana、Draw、CD 和历史由 DS 形成压缩连续性正文，业务只按同一登录 Scope 保存。Scope 是原 Bearer 服务器摘要再作 domain separation 的 opaque 值，不是原 Token 或 TokenHash。新登录会隐藏旧 Scope 正文；这不删除历史记录，也不改变真实物品归属。业务服的保存成功只证明这份可信正文与资产同事务提交，Core 状态能否严格恢复仍需 Unity 接线验证。

### 为什么必须显式区分携带、地面和退休

[HomePracticeAssets](../../../../Server/Norn.Business/Features/Runs/HomePracticeAssets.cs) 将最终 `keep` 集合定义为当前携带物加仍在 Home 地面的完整树。原物品 ID、roll、有限次数、整数 GMU、父卡和世界姿态均原样保存；WorldOwner 在数据库仍是 32 字符身份。仅兼容旧非 hex WorldOwner 时，才按 Run 与原值作确定性转换，不能扩数据库字段或每次恢复产生新的物品。

`RunMemberExitRules/RunMemberExitService` 要求原 Entry、当前 Active custody 与已确认 Journal 的每个身份都在 keep 或显式 `FinalRetiredItems` 中。缺项不能自动当作销毁。原 G 破瓶确实使用 `Destroyed`，有限卡消耗用 `Consumed`，完整材料合并用 `Merged`，所以 Home 保留三种原原因；每条仍核当前 Run、Content、Revision、真实出生或原身份与 keep 互斥。普通副本和 FinalDeath 原规则不因此放宽。

地面替换必须先删除该账号旧 `home.map1` 位置，再安装本次携带和新地面。如果反过来，刚从旧地面拾回背包的法杖及其卡片会被后续旧位置清理误删。`hub.map1` 有独立 Scene key，不能在 Home 替换时清掉。013 的地面外键还要求命令来源，事务写入真实的 `HomePracticeExit` 锚点，关联最终 SettlementId 与正文 Hash，不伪装一条客户端 Drop，也不重写已应用迁移。

### 周期 Journal 先提交时暴露的第二层回归

仅测试“退出先于周期 Head”会漏掉一种正常时序：卡或瓶已被真实消耗，周期 Checkpoint 已将 custody 标为 `Retired`，但原 SQL 位置为了审计仍挂在法杖或背包下，等待最终退出统一清理。旧 `PersistCarried` 只允许父物的旧子项处于 Active，因而把这三种合法退出都误判为 OwnershipConflict。

新增回归先调用真实 Checkpoint 保存接口，再提交同一真实退休事实。主 Agent 的 [home-backend-current-20261104.trx](../../../docs/superpowers/evidence/multiplayer/single-player-regression-20261103/home-backend-current-20261104.trx) 得到 28 passed / 3 failed；三个失败都是 `checkpointFirst=true` 的 Consume/Merge/Destroy，并定位到父物旧子位置检查。最小修复只给 V3、可信 Home Scope、当前已逐条核准的 `FinalRetiredItems` 建 ID 集合，允许清理这些同 Run 已 Retired 的旧子位置。未知墓碑、普通副本和没有本次真实证据的 Retired 子项继续拒绝；没有关闭通用归属检查。

### 启动取消、历史兼容与当前验收范围

未 Admit、没有任何 Checkpoint 或退出收据时，Home 的冻结 seed 尚未代表玩法变化，可以随启动取消释放，之后再次冻结同一批真实资产。已经 Admit 或存在持久玩法事实时保留 custody 和恢复锁，不能借 Fail 重授旧 Entry。新增两项取消重入和一项已 Admit 保锁回归由主 Agent 集中运行。

### HTTP 200之后为什么仍锁住入局

现场日志见[user-hub-http-observed-20261104.txt](../../../docs/superpowers/evidence/multiplayer/single-player-regression-20261103/user-hub-http-observed-20261104.txt)。用户购买后余额9820；数据库只读取证确认其法杖Move已提交至版本3、装备槽1，客户端却停在版本2。原CommandId连续三次POST均200，但没有进入后续Profile GET，说明拒绝发生在收据匹配之前，而非拖拽抓取或数据库事务本身。

原收据JSON含`WorldPose:null`。Unity的`JsonUtility.FromJson`却将这个Serializable inline class恢复成非空的默认`OnlineHubWorldItemPose`。普通Move的严格规则要求没有WorldPose，于是合法成功收据被当作非法；pending不清，后续拖放被拒、单人入口也按原保护规则阻止。旧测试直接`new InventoryMoveReply`，其WorldPose是真的C# null，完全遗漏了HTTP反序列化边界。

先把原解析提取为等价的私有入口，再用实际HTTP字段形状取得[有效RED](../../../docs/superpowers/evidence/multiplayer/single-player-regression-20261103/hub-http-null-pose-red-20261104.xml)：期望null，实际是`OnlineHubWorldItemPose`对象。修复只在[OnlineAccountClient.Inventory](../Scripts/Multiplayer/Accounts/OnlineAccountClient.Inventory.cs)冷解析边界扫描有界原始JSON：顶层WorldPose唯一且明确null时，恢复真正null；Drop继续保留真实姿态。非null空壳、重复或转义重名、缺失字段不借此解锁。其余Owner/版本/命令及Profile校验全部保留，未直接清pending或修改数据库。

### 原商店与钱包的两种显示问题

[SinglePlayerShopSession](../Scripts/Run/Runtime/SinglePlayerShopSession.cs)原来对同账号同版本的重复Scope通知也重新请求供货，会把已确认报价再次变为pending。现在同版通知保持已确认读数；显式重新打开仍重新GET，新版本仍撤旧报价，非法报价仍撤交易资格。原Hub ShopController和嵌入库存分属两个兄弟Canvas，测试必须成组克隆并让Unity重映射引用，不能只克隆一个Canvas后留下跨Preview外链。夹具先有两轮安装失败，均保留为夹具失败，不当作生产缺陷。

### 已定位的表现缺口

1. Hub 的 Tab 已读取账号 Source，但 HeldItemHud 默认仍读取被账号写保护隔离的本地 Session。修复使原快捷栏跟随原背包的当前 Source，保留 CombatPresentationScope 的显式绑定优先级，不构造假 Mana/CD。
2. 原 F 拾取列表位于 Tab Canvas 的兄弟 Canvas；旧 CombatInventory 导出只克隆了 Tab。现在导出保留原五行 NearbyPickupList，Scope 绑定同一 Actor 的拾取控制器，打开 Tab 时隐藏，退出时解绑。F 能拾取但没有提示，属于消费者缺失而不是交互权限丢失。
3. 攻击时 Authority 修正根朝向，子模型随之旋转；表现插值却从已经变化的世界旋转重新开始，产生跳变。OnlineCastDriver 缓存上帧实际呈现的世界朝向，活动攻击和自然收尾从该值插值；显式取消仍释放所有权，不用动画时间改变权威攻击结果。
4. 毒爆有伤害无特效包含两层遗漏：DS 的 ElementReactionEvent 没有复制到 Client，正式地图导出又去掉了 ReactionBurstVisualController。本轮复用 CombatFact 的受控 ReactionBurst 事实和原渲染消费者，环境反应不需要伪造玩家 Actor。Client 只发布表现事件，不再次伤害、扣资源或投放材料。兼容版本升至 Protocol16，必须配套重建 Client、DS 和业务 Shared，旧15程序不能混测。
5. Fire GPU 表现错误地将受限的物理积分 dt 同时用于播种计时和粒子年龄，低 FPS 时连表现时钟也变慢。播种与年龄改用真实 scaled elapsed，积分保持 dt 上限；每帧最多一批，长暂停不积压补种债务，保留原发射间隔与池容量。Compute Dispatch/GetData 的实际 RED/GREEN 验证覆盖年龄推进，不能据此宣称公网材料首帧延迟已测量改善。
