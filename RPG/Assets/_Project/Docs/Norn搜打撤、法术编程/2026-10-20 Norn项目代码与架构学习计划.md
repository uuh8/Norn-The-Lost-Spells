## 1. 学习目标与使用方式

本轮学习围绕已经形成 Demo 的两条核心玩法：搜打撤与法术编程。目标是从玩家体验出发，理解真实代码如何组织数据、执行规则、管理资源、连接 Unity 和跨系统协作，最终能够不看源码独立解释设计。

总体顺序：

```text
A：建立全局地图
→ B：学习物品、资源与搜打撤闭环
→ C：深入新版法术编程
→ D：简要回顾 3C、战斗与元素基础
→ E：用完整 Gameplay 案例连接系统
```

共 32 个学习板块：A 阶段 3 个、B 阶段 13 个、C 阶段 10 个、D 阶段 2 个、E 阶段 4 个。编号作为后续提问与资料命名的固定索引；一个板块较大时继续拆成 B2.1、B2.2 等小节。

建议精力分配：搜打撤约 40%，法术编程约 35%，全局架构与完整案例约 20%，3C 和元素基础约 5%。不设强制日程，以理解程度决定进度。

后续使用约定：

1. 用户指定板块后，先读取本计划与配套模板，再核对当时的生产源码、配置与相关测试。
2. 默认生成一份独立 Markdown 资料，保存到本目录。命名格式为“生成日期 编号 板块名称 学习资料.md”，例如“2026-10-20 B1 物品定义实例身份与归属 学习资料.md”。
3. 每次只展开指定板块。涉及尚未学习的系统时，先解释必要的输入输出，链接后续板块，不提前展开整个系统。
4. 用户要求交互教学时，每次只讲一个已选小节，确认理解后再继续；用户要求完整板块资料时，交付该板块的完整文档，内部仍按由浅入深组织。
5. 本计划中的资料尚未逐节生成，学习目标也不表示用户已经掌握；开始记录进度后再据实际情况更新。

## 2. 当前实现边界与阅读原则

### 2.1 先区分当前入口与历史记录

本计划依据当前生产脚本、场景配置及近期开发解析整理。开发解析保留了阶段性实现过程，同一文件的早期 Task 可能已经被后续 Task 修正。后续讲解应以当时实际入口和源码为准。

| 需要区分的内容 | 当前阅读口径 |
|---|---|
| 玩家资产与场景显示 | 玩家 Profile 和物品归属表管理真实财产；UI、世界模型和拾取代理展示或操作这些资产 |
| 玩家与 NPC/Boss 施法 | 玩家学习新版有状态程序及真实资源事务；NPC/Boss 的独立只读程序求值路径另作必要说明 |
| 法术定义与玩家拥有 | 规则目录中存在某种法术，不代表玩家拥有对应物品实例，也不代表该实例当前有资格执行 |
| Hub 与 Home | Hub 主要承担整备、交易、研究与出发；Home 承担材料实验和相关世界玩法。当前 Hub 禁止世界实验，Home 开启 |
| 通用 Raid 与 P7/P8 | 两条流程共享库存等基础能力，但进入、目标、奖励、返回、死亡和重试规则必须分别核对 |
| 正式场景与验证场景 | 当前通用 Raid 配置仍指向 RaidWorldSandbox；不能把灰盒规则直接当作所有正式地图的实际规则 |
| 新版施法时序 | 当前玩家先进入施法 State，达到 Animator 的 ArrowSpawnTime 阈值后释放；法杖 Cast/Reload 冷却约束下一次攻击。不能把端到端射速直接等同于冷却数值 |
| 元素世界与法术表现 | 元素世界是具有材料身份、行为和生命周期的基础世界；法术、容器和角色都可与之交互 |

以上边界只记录本次静态核对，不代表本次重新完成了 Unity Play Mode、Build 或 Profiler 验收。

### 2.2 每个功能都识别四类职责

| 职责 | 学习时需要回答 |
|---|---|
| 配置数据（Authoring Data） | 作者在 ScriptableObject、Prefab 或 Scene 中配置什么？哪些值可以共享？ |
| 可变运行状态（Runtime State） | 真实数量、位置、资源、阶段和版本由谁拥有？谁有权修改？ |
| 纯规则（Pure Logic） | 输入什么，计算什么，返回什么？能否脱离场景独立验证？ |
| Unity 连接与表现 | 谁接入输入、生命周期、Scene、Physics、Animator、UGUI 和 Rendering？ |

阅读代码时始终追踪两条线：调用线说明谁请求谁、事件怎样传播；状态线说明数据由谁拥有、何时修改、失败时留下什么。

## 3. A 阶段：全局地图与最小功能链

本阶段建立责任和生命周期框架。先认识玩家会经历什么，再认识模块，不要求提前读完大型协调脚本。

| 编号 | 学习板块 | 核心问题与完成标准 |
|---|---|---|
| A1 | 玩家完整流程与场景地图 | 识别主菜单、Hub、Home、P7、P8 的职责和入口；分别画出进入、返回、失败、Boss Retry 的路线，标出哪里携带资产、哪里加载或卸载世界 |
| A2 | 全局 Assembly、职责与依赖 | 理解九个 Runtime Assembly 的分工、允许的直接依赖、请求、只读服务与 EventBus；能解释哪个模块拥有状态，以及具体避免了什么反向依赖 |
| A3 | 从一次拾取认识基本架构 | 用一个地面物品追踪输入、请求、校验、归属变化和 UI 刷新；能说明容量不足为什么应保留地面物，而不能只隐藏模型 |

九个 Runtime Assembly 的职责预览：

| Assembly | 学习中的主要职责 |
|---|---|
| Game.Core | 基础契约、事件通道、日志和跨域通知 |
| Game.Materials | 稳定材料身份与共享材料规则数据 |
| Game.Combat | 伤害、生命、状态、Projectile 生命周期及战斗契约 |
| Game.Skills | 法术定义、编译、程序规则、执行图与预览 |
| Game.Run | 玩家资产、库存、资源事务、局次、经济、持久化与转场协调 |
| Game.Character | 玩家输入、角色 FSM、敌人 AI、Animator 连接与 Unity 施法桥 |
| Game.ElementField | 材料世界模拟、查询、反应和角色接触 |
| Game.Rendering | 消费 Gameplay 数据的材料世界与角色等渲染表现 |
| Game.UI | 背包、商店、研究台与 HUD，通过请求和只读服务连接 Gameplay |

依赖关系以当前 asmdef 和 AGENTS.md 为准。EventBus 负责通知和已定义的请求协议；允许的模块依赖也可以调用显式服务或读取接口，不把所有调用一律改写成事件。

阶段产出：一张场景流程图、一张模块责任图，以及一次拾取的最小调用链。

## 4. B 阶段：搜打撤与资产资源体系

先学习单个物品和局部操作，再学习跨场景生命周期、可靠结算与异常恢复。技术名称用于定位知识点，具体原理在对应资料中解释。

| 编号 | 学习板块与范围 | 核心机制、技术与独立解释目标 |
|---|---|---|
| B1 | 物品定义、实例身份与归属：法术、法杖、背包、容器、材料等 | ScriptableObject、ContentId、InstanceId、Dictionary、物品位置与父子归属；解释同名配置如何对应多件独立资产 |
| B2 | 背包空间、堆叠与容量：二维摆放、形状占格、移动、合并、拆分和整理 | 二维坐标、占用检测、状态相容性、候选操作与版本校验；解释数量上限与空间容量为何是不同规则 |
| B3 | 物资生成与世界拾取：场景物品、随机来源、附近列表、全拾取、丢弃与再拾取 | 生成标识、随机规则、世界代理、拾取事务、容量不足；追踪地面资产变成携带资产的过程 |
| B4 | 装备、法杖与快捷位：装备背包、多法杖切换、法术安装、道具绑定 | 装备归属、操作请求、只读投影和实例资源连续性；解释换槽、换杖和换场景怎样保留合法状态 |
| B5 | 物品使用、容器与材料流转：采集、组分、持续撒出、投掷、破碎、固体回投和附着 | 整数材料计量、容量、资源预留、世界与库存两端提交；解释数量守恒、在途资源与失败回退。按已接入行为讲解，不从 Consumable 等枚举推导未接入的使用效果 |
| B6 | 仓库、Profile 与持久化：访问权限、保存、加载、备份、旧档迁移 | DTO、JSON、稳定身份、保存代数、临时文件与替换；解释仓库和随身资产怎样共同恢复，写盘失败后如何处理 |
| B7 | 商店、货币与经济：物品和材料买卖、有限供货、收购预算、补货进展 | 报价与成交、整数货币、数量计价、版本、交易收据、重复请求与可靠保存；解释一次交易何时才算成功 |
| B8 | 出发、地图切换与局次管理：携带资产出发、加载、激活地图、返回 | 局次状态机、Coroutine、LoadSceneAsync、Single/Additive、玩家 Scene 归属与失败回滚；分别识别 Raid、P7/P8 和 Home 路径 |
| B9 | 探索、遭遇、战利品与奖励：敌人死亡掉落、遭遇推进、关底有限随机奖励 | DeathEvent、目标过滤、概率与权重、死亡源去重、待领取奖励和可到达的掉落位置；解释重试为何不能重新抽奖或重复发放 |
| B10 | 撤离条件与成功结算：采集或目标条件、区域、主动开始、倒计时、取消和返回 | 纯条件与进度状态、距离检测、同帧裁决、结算收据；解释为何先完成可靠保存，再展示和卸载世界 |
| B11 | 死亡、失败惩罚与资源保留：保护具体卡、背包本体、放弃、异常退出、Boss Retry | 最终携带判定、父链、出发快照、Pending Raid 与恢复；比较 Raid、P7/P8 死亡和 Boss checkpoint，不能用一套描述代替全部规则 |
| B12 | UI 与 Gameplay 同步：背包、仓库、商店、资源 HUD、撤离和结果 | EventBus、请求/结果、Read-only Interface、拖拽草稿、暂停原因和失败反馈；解释界面为何不能直接修改权威数量 |
| B13 | Home 实验区与联动：研究、试法、采集、投放、和平转场和世界清理 | 区域权限、共享资产、材料世界、Scene 生命周期和资源释放；解释库存、在途资源和场景残留的保留边界 |

B 阶段贯穿三条问题线：

1. **归属**：物品此刻在哪、属于谁、谁有权移动或消耗？
2. **守恒**：库存、容器、法术和世界之间转移资源时，如何避免复制或丢失？
3. **可靠性**：容量不足、旧版本请求、重复通知、加载失败或写盘失败时，系统留下什么状态？

推荐检查点：

- B1～B3 后：独立解释一件物品从定义、生成到拾取的过程。
- B4～B7 后：独立解释一次装备、一次使用和一次交易分别由谁提交。
- B8～B11 后：对比成功撤离与死亡失败的场景、资产和存档变化。
- B12～B13 后：解释 UI 和实验区怎样使用已有权威服务，且不建立第二份资产来源。

B5 先学习服务的职责、请求和结果；法术执行内部的分层支付留到 C8，材料模拟算法留给专项学习。

## 5. C 阶段：新版 Noita-inspired 法术编程

核心问题：玩家真实拥有的一组法术卡，怎样变成可持续执行、可解释、可支付并能在世界释放的程序？先建立单次普通输出的模型，再加入抽牌状态、作用域、未来触发和事务。

| 编号 | 学习板块 | 核心问题、技术与独立解释目标 |
|---|---|---|
| C1 | 全貌与数据模型 | 区分法术规则、物品实例、安装顺序、法杖固定属性和执行状态；说明 Skills、Run、Character 各自拥有或消费什么 |
| C2 | 编译与规则冻结 | Compiler 如何校验并冻结配置？学习版本、值快照、只读集合与复制；解释修改卡序或 SO 为什么不应改写已发出的攻击 |
| C3 | 连续 Draw 与法杖状态 | Deck/Hand/Discard 如何变化？学习 Draw、回收、Reload、Shuffle、局部随机状态；手工推演连续两次施法 |
| C4 | Modifier、Multicast 与 Scope | 参数共同结算的范围如何确定？解释后置修正、继续 Draw、Scope 关闭与统一 Bake，并区分安装顺序和实际执行结构 |
| C5 | Trigger 与未来执行 | 命中、计时、终止怎样释放子程序？学习独立子 Scope、冻结输出、生命周期事件与取消；解释构建未来层不等于未来层已经发射 |
| C6 | Mana、次数、资格与节奏 | 区分 Mana、法术次数、本局资格和技术预算；区分 Cast Delay、Reload Time、动画起手及其对端到端施法间隔的影响 |
| C7 | Copy、固定特性与复杂边界 | Alpha/Gamma 如何借用指令？固定特性如何执行？学习身份、支付语义、显式执行栈和预算上限，避免把借用理解成复制物品 |
| C8 | 真实资源事务与材料输出 | 候选结果怎样成为真实施法？学习资源预留、票据、Prepare/Complete/Cancel、根层与子层提交、版本校验及重复请求 |
| C9 | 从玩家输入到世界攻击 | 输入和瞄准快照如何进入 FSM，在 Animator 阈值释放，经 OwnedWandCastAdapter、Run 事务和 SpellCaster 生成攻击，再进入统一伤害入口？ |
| C10 | 研究台、预览、Trace 与回放 | 预览怎样复用解释器且不推进真实状态？学习执行图、参数来源、虚拟时钟和世界观察；比较预测、支付、出生、触发与取消 |

固定示例的递进顺序：

```text
普通弹
→ 修正 + 普通弹
→ 多重施放
→ 连续抽牌与换周期
→ 独立 Trigger 子程序
→ Copy 与固定特性
→ 材料附着、真实支付与世界执行
```

每个例子都记录：执行了哪些指令、进入哪个 Scope、资源如何变化、产生什么候选结果、世界实际出现什么。

推荐检查点：

- C1～C4 后：能够手工推演卡牌流转和输出参数，不只依据 UI 左右位置判断。
- C5～C7 后：能够预测子层范围、触发时机、Copy 来源与预算停止条件。
- C8～C10 后：能够解释为什么“推演成功”“资源已支付”“世界已发射”是不同事实。

Noita 的对照材料只用于解释已核实的规则来源。Norn 的资源政策、具体数值、3D Physics 与部分边界具有自己的实现，不默认与 Noita 完全等价。NPC/Boss 的保留求值路径在相关板块中作为职责分支说明。

## 7. E 阶段：完整 Gameplay 与独立设计解释

| 编号 | 完整案例 | 要串起的协作与观察点 |
|---|---|---|
| E1 | 探索获取法术 → 拾取 → 调整配置 → 施法 → 击杀 → 领取奖励 → 返回保存 | 跟踪同一个物品实例的归属、程序版本、资源消耗和奖励。按实际规则选择局内可用的背包编辑或返程后的研究台；完整研究台只在获准 Hub/Home 区域使用。P7/P8 的返回路径单独标明 |
| E2 | 携带资产出征 → 满足条件 → 开始撤离 → 成功结算，再与死亡失败比较 | 专门使用通用 Raid 条件撤离链，比较成功、死亡、放弃和保存失败时的资产；同时说明哪些规则不应套用到 P7/P8 |
| E3 | 购买材料 → 带入 Home → 采集、附着、投放或施法 → 返回 Hub | 串起商店、库存、容器、材料世界、法术输出和和平转场；追踪真实数量和释放时机 |
| E4 | 研究台预测 Trigger 组合 → 实际施放 → 回看执行记录 | 对照预测、提交、出生、未来触发及取消；练习从症状判断应检查规则、资源、Unity 时序还是表现层 |

每个案例最终交付：

1. 一张跨模块调用图，标明直接调用、请求事件和结果事件。
2. 一张状态变化表，记录所有者、修改前后值、确认时机和失败结果。
3. 一个关键失败分支，例如容量不足、保存失败、触发弹提前销毁。
4. 一段用户自行完成的设计解释，包含玩家结果、职责划分、核心机制、trade-off 和证据边界。默认不附代写的模拟面试答案。

## 8. 原始需求覆盖对照

| 用户关注点 | 主要学习板块 |

- 使用真实源码的小片段和可点击路径；说明先读哪个入口、接下来跟踪什么、读完应回答什么。
