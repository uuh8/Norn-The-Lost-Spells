## 1. 先区分玩家操作经过的几层

一个物品在界面中“看见了”，不代表所有输入和写权限都已就绪。

| 层次 | 负责什么 | 本次怎样验证 |
|---|---|---|
| View / UGUI | 把已确认数据画成格子、图标、文字和选中框 | 原 Prefab 的 RectTransform、CanvasScaler、CanvasRenderer mesh 与作者 Rect |
| Input System / Character | 接收按下/松开，检查 Focus、暂停、World 阻断与当前 Owner | QueueStateEvent 经过真实 InputAction，不直接调用请求方法代替按键 |
| Run 只读源与命令入口 | 解析同一实例、当前归属、版本及候选，提交意图 | 检查 ItemId、CallerId、ConnectionEpoch、ExpectedInventoryVersion，提交前不乐观修改资产 |
| DS / 业务服 | 裁决在局行为及长期资产 | 本文的 EditMode 输入测试不替代 HTTP/KCP、DS 收据、Owner Snapshot 和持久化验收 |

本次界面修复没有修改格子容量、物品归属、Prefab/Scene 的作者布局或资产 SO。输入修复也没有跳过在线身份、Frozen、Focus、版本或权威确认。

## 2. “中间格子被拉宽”：实际是边线在缩小时消失

### 症状与排除过程

截图中的附近物品区、法术储存条出现相邻几格连成一大格的视觉效果。最初检查的是单格 anchor stretch、LayoutGroup 和旧布局 Owner 残留，但当前 `InventoryGridView`、`NearbyItemGridView`、`SpellStorageView` 与 `WandProgramPanelView` 都给实际单格设置相同的正方形 Rect。

这四种 View 共用 [InventoryGridLinesGraphic.cs](../Scripts/UI/Inventory/InventoryGridLinesGraphic.cs)。原实现把全部横竖边线做成一份 mesh，线宽固定为 **1 个 Canvas 参考单位**。参考单位不是屏幕像素：正式背包参考面积为 1920×1080，Controller 的视口配置在运行时使用 `CanvasScaler.ScreenMatchMode.Expand`。

在用户报告的 1424×714 尺寸下，比例是 `min(1424/1920, 714/1080) ≈ 0.6611`。原 1 单位边线仅约 0.66 pixel；1280×720 下约为 0.67 pixel。无足够覆盖的窄四边形可能在 Rasterization 时漏掉整条线，于是等宽格看起来像被合并。

### 实际 RED

[grid-selection-first-red.xml](../../../docs/superpowers/evidence/player-input-regression-20261115/grid-selection-first-red.xml) 的小窗口用例实际测到约 **0.661 / 0.666 pixel**，低于保留容差后的 0.998 pixel 下限。首轮还有几个夹具问题，不能混称产品失败：

- Unity 6000.3 的 `CanvasRenderer.GetMesh()` 没有带目标 mesh 参数的重载，最早编译被阻止；[Blocked 证据](../../../docs/superpowers/evidence/player-input-regression-20261115/grid-red-compilation-blocked.json) 保留，未执行旧 Assembly 冒充测试。
- 1920×1080 正控制最初对 `renderingDisplaySize` 做 Vector2 ExactEqual，内部浮点转换产生微小误差，输出四舍五入后看起来相同。只把目标视口比较改为距离小于 0.01 pixel，实际 mesh 线宽下限没有放宽。

夹具修正后，[pickup-grid-capacity-first-red.xml](../../../docs/superpowers/evidence/player-input-regression-20261115/pickup-grid-capacity-first-red.xml) 中 Grid fixture 为 **4 passed / 9 failed**：四个 1920 正控制通过；八个小窗口用例和同一网格连续缩放用例失败。

### 修复原理与取舍

现在的参考单位线宽为 `max(1, 1 / Canvas.scaleFactor)`：

- 小于设计尺寸时，至少覆盖 1 个屏幕像素。
- 大于设计尺寸时，保留原 1 个参考单位，避免把作者原来的边线反向缩细。
- CellSize、格子位置、拖放命中和真实容量仍按原来的几何计算。

只在 mesh 生成时读比例还不够。同宽高比缩放时，Canvas 的设计面积、Content rect 和 CellSize 都可能没变，原 `Configure` 缓存不会要求重建。因此 Graphic 在 `LateUpdate` 比较缩放值，变化时将既有 mesh 标 dirty。稳定帧不创建格子、Material 或临时集合。

`InventoryGridPixelGeometryTests` 共 13 cases：使用正式 `CombatInventory.prefab`、真实 View.Refresh 和单格模板，在独立 Camera/CanvasScaler 下测量真实 RectTransform 投影及 CanvasRenderer 上传的 mesh；不是只重复产品的尺寸公式。同树缩放测试保持原 cell/Graphic 实例身份，不用重开背包掩盖刷新问题。无参 GetMesh 返回的 mesh 归 Graphic 管理，测试只读 vertices，不销毁它。

### 验证边界

13 项在 [driver-grid-green-pickup-red.xml](../../../docs/superpowers/evidence/player-input-regression-20261115/driver-grid-green-pickup-red.xml) 和最新关联回归中均通过。它证明当前生产 Screen Space Rect 树的格子等宽及边线宽度，不代替 Native 最终截图、字体和透明度观感。任意额外的局部非均匀缩放、World Space 相机距离不在本次像素下限保证内；当前正式路径未发现这些额外缩放。World Space 保留原设计单位行为。

## 3. “已占 19/64 格”压在第一行：恢复内部顶边留白

正式资源中，`BackpackRuntime_Capacity` 位于 BackpackRegion 顶部：文字高 30、顶端 -2；同父的 GridViewport 却 stretch 到顶部，`offsetMax.y=0`。两者自然覆盖同一片空间。`UiViewportLayout` 只移动整个面板，不改变这两个兄弟节点的相对位置，因此不是整体居中造成了重叠。

旧 `SinglePlayerHubAreaSetup.ConfigureGrid` 已明确为容量文字预留 **32 个参考单位顶行**。但旧工具的文字高度曾是 24；当前作者已改成 30。首次测试机械采用 24 高断言，得到的 5 项失败是错误测试前提，不能据此把作者文字缩回去。修正后的测试保留原 Text Rect，只要求可见网格不覆盖它。

[capacity-red.xml](../../../docs/superpowers/evidence/player-input-regression-20261115/capacity-red.xml) 为 **3 passed / 4 failed**。四个真实来源——共享 CombatInventory、原 PracticeInventoryWorkspace Prefab、Hub Tab、Home Tab——都因 Viewport top inset 仍为 0 而失败；已有 48 inset、仓库、商店三项控制用例通过。

修复在 [BackpackWorkspaceView.cs](../Scripts/UI/Inventory/BackpackWorkspaceView.cs) 的离散 `Refresh` 绑定中完成：

1. 从同一 Controller 的 internal 只读 `BackpackGridView` 取得已接线网格，不搜索其他 Canvas。
2. 只处理已有 `BackpackRuntime_Capacity`，并要求文字与 Viewport 同父，确认是原 Tab 容量行。
3. 只写 `viewport.offsetMax.y = min(原值, -32)`。文字 Rect、作者外框、Content 的局部布局和 CellSize 不改；原来更大的留白，例如 -48，继续保留。

这里缩小的是 **可见裁剪区域**，不是背包的 8×8 等真实容量。ScrollRect 仍负责访问超出可见区的 Content。重复 Refresh 不累计位移，也不每帧重排。

Hub 仓库和商店已清除 Tab 专用 `_capacity` 接线，由各自 `WarehouseWorkspaceView._bagCaption` 显示容量，不能强行给它们插入一条顶行。7 项回归覆盖以上四个来源、五种视口、文字与其他作者 Rect 不变、实际不重叠、重复绑定及三项控制。最新 7 项均通过；相接边界只容许 0.01 Canvas 单位的浮点转换误差。

## 4. 数字选择卡住：通用输入门不能等待可施法法杖

正式线上选择由 [OnlineCastDriver.cs](../Scripts/Character/Spells/OnlineCastDriver.cs) 接收：1–3 使用原法杖选择绑定，4–0 对应七个工具槽。选择只提交命令，HUD 应等待服务器确认的选择事实，不提前把瓶子或法杖改成已选中。

首轮 12 个真实数字键用例中，7 个工具键和 3 个法杖键均通过；失败集中在两种恢复路径：最后一把法杖已移入背包或当前没有装备法杖，失焦后再回焦并解除 World 阻断，工具键仍不提交。

原因是 `StepPrediction` 原先在施法 `Ready=false` 时过早返回，World 的 `SetBlocked(suppressed)` 没机会同步。没有可施法程序是合法库存状态，但旧的通用输入阻断会一直保留，连工具选择也被挡住。

现在先确认当前为本地 Client Owner，然后同步 World 的通用阻断，再检查施法 Ready。这样空手角色可以恢复工具选择，后面的 Ready 仍继续阻止无程序施法。不能简单在回焦回调里无条件解锁：World 可能仍 Frozen、断线或处于菜单占用。

回归使用真实 Keyboard 事件，验证失焦时拒绝、回焦但 World 仍阻断时拒绝、World 放行后恰好提交一次；同时检查当前版本、实例与目标槽，并证明确认前 Source 选中项不变、没有生成施法输出。完整 `OnlineCastDriverTests` 的 124 项已通过。

这项修复也影响工具/容器输入使用的共同资格门，但本次没有把容器 F/H/G/K 改成绕过 Driver 的另一条入口。容器动作仍解析已确认的 EquippedTool 实例、Owner、槽位及 UseKind，真正数量和输出仍由 DS/Run 事务裁决。

## 5. F 拾取的已复现生命周期缺陷与未证实部分

[NearbyPickupInput.cs](../Scripts/Character/Interaction/NearbyPickupInput.cs) 把真实 F 交给同 Actor 的 `NearbyPickupController`，再由 `WorldItemPickup` 提交原拾取意图。站点和 Portal 仍有优先权，已有待确认拾取不能重复提交。

已复现的路径是：输入组件收到失焦事件，将 `_focused` 记为 false；随后 Driver/原 Hub 停用该组件；窗口恢复 Focus 时它未收到回调；重新启用后继续沿用旧 false，第一下新 F 被拒绝。

修复只在 `OnEnable` 边界重采 `Application.isFocused`。持续启用期间仍保留 Focus 回调及失焦拒绝，不能改成始终 true，也不能每次 F 都绕过该门。

`NearbyPickupKeyboardTests` 的四项分别验证：Controller 早到、Controller 晚到、持续失焦拒绝及启停后恢复。它们让 Keyboard F 穿过真实 InputAction、Character、Run 和 WorldItemPickup，最后观察原命令事件；检查 CallerId、同 Actor/Source、WorldOwnerId、版本、Epoch、待确认状态，并确认请求时地面物仍在、只读库存版本未被客户端推进。

首批四项曾因测试构造的地面实例/身份/目录前提未通过校验而提前失败，这不是 F 产品行为 RED。修正该输入前提后，[driver-grid-green-pickup-red.xml](../../../docs/superpowers/evidence/player-input-regression-20261115/driver-grid-green-pickup-red.xml) 为 **140 passed / 1 failed**，唯一失败就是启停恢复用例：预期一次拾取意图，实际零次。其余三个 F 控制用例已通过。应用产品修复后四项全部通过。

**这只能确认一条具体生命周期缺陷。** 用户报告的“看见附近物品但按 F 无响应”还可能停在候选/距离、UI 输入占用、Portal/站点优先级、当前 Source、在线资格或权威收据等其他边界。本次不凭单测把它们全部排除，更不把这一条路径写成首次进入副本故障的唯一根因。

### PlayMode 的 cacheError：同 deviceId 不等于同一个 Keyboard

首轮 PlayMode 的 7 个失败包含 Input System 错误：`Cached unprocessed value unexpectedly became outdated`，读取新值为 1、旧缓存为 0。它发生在 `BackpackWorkspacePlayModeTests.Keys` 排队真实键盘事件后，不能用忽略日志把它算成通过，也不能直接归因于产品 Esc/购买行为。

在 [play-cache-diagnostic-v1.xml](../../../docs/superpowers/evidence/player-input-regression-20261115/play-cache-diagnostic-v1.xml) 中，诊断明确指向 `Assets/_Project/ScriptableObjects/Input/Inventory/Action_Cancel.asset / Cancel / /Keyboard/escape`。该 Action 引用的 Keyboard 与当前 `InputSystem.GetDeviceById(deviceId)` 返回的 Keyboard 不是同一个对象。两者名称和 deviceId 可以相同，因为 `InputTestFixture.Setup` 切换 InputManager/runtime 后会复用设备编号；对象身份才是这条边界的依据。

已经加载的共享 InputActionAsset 仍可能持有旧 ActionMap runtime state。旧 Control 通过复用编号读取新 buffer，却没有随新 Keyboard 收到对应的缓存失效通知，于是缓存值与当前值冲突。诊断的 40/30 不是新发现了 30 个玩法缺陷，而是更早的引用断言在更多 case 中捕获了同一夹具污染。

修复只落在 [BackpackWorkspacePlayModeTests.cs](../Tests/RunPlayMode/BackpackWorkspacePlayModeTests.cs)：在旧 runtime 仍有效时，记录项目 Actions、该 Review 依赖的输入资产及逐 Action enabled 状态，Disable 后 Dispose 非序列化 ActionMap runtime state；再由 InputTestFixture.Setup 和本例 Keyboard 重新解析。结束时先卸载本例 Scene，执行 InputTestFixture.TearDown 恢复旧 manager，再恢复原 manager.actions 内存引用和逐 Action enabled 状态。

这里释放的是临时运行状态，保留原 Asset、binding、override 与资源文件；没有改 ProjectSettings，没有改玩家键位，也没有关闭 cache 检查或放松原玩法断言。最终同一组合 **70/0**：CombatPresentationRuntime 3、ContainerUse 11、EarlyCombatPresentationLifecycle 1、OnlineSharedInventory 2、CombatHudResolution 1、ShopQuickPurchase 32、WarehouseShopWorkspace 20。这个结果覆盖所选场景 UI/库存与输入生命周期回归，不把测试切换 InputRuntime 的问题推断为 Native 进程存在相同故障。

## 7. Native 键盘路径与实际结果

此前直接调用选择或投掷请求，可以验证权威交易与资产结果，却无法证明数字键、F、G 的 Action 和生命周期接线。此次扩展的 [SinglePlayerInventoryRegressionProbe.cs](../Scripts/Multiplayer/Diagnostics/SinglePlayerInventoryRegressionProbe.cs) 与 [NativeInventoryRegression 工具](../../../Tools/Networking/NativeInventoryRegression/README.md) 已用于本轮 Native 验证，补上输入事件入口。

专用 Development/Editor 诊断对象必须通过私有配置显式开启 `AllowSyntheticKeyboard`，只允许 1–0/F/G。Probe 持有自己的虚拟 Keyboard，通过 `QueueStateEvent` 排队，正常 PlayerLoop 消费；不递归调用 InputSystem.Update，不用 OS SendInput，也不直接调用 Driver 请求方法代替按键。

Harness 必须等报告显示实际 deviceId 和已处理的 down/up，再等待原命令成功收据、Owner Snapshot、物品位置及数量结果。仅看到 `QueuedSyntheticKey` 不是通过。显式 `direct` 模式保留旧请求路径，但报告必须声明它不覆盖键盘。测试期间释放自己的虚拟设备，不能重置或删除其他键盘。

19 项 EditMode 诊断测试覆盖显式授权、键白名单、Action 真实 performed/canceled、持键及设备所有权。它们是验证工具的扩展，不把之前焦点前置失败的无效 RED 计入产品修复证据。最终 Native 已有效执行 F/G 与数字 1、4–7 的 Input System 至业务链；旧数字选择分支的缺口及修复后证据在下文分别记录。这仍不能声称覆盖 OS/硬件输入、鼠标 Raycast 或主观手感。

同图 HUD 出现两个蓝框的静态假设未获支持：当前 CombatHud、Hub、Home 的普通 Frame Sprite 与 `_selectedFrame` 不同，十个 Selection Image 均透明，没有据此修改 DefaultFrame 缓存或作者素材。旧 Native 的投掷后清图标与法杖回退检查有效，但当时数字选择误判跳过了其 HUD/Driver Caller 断言。修正工具后的新 Native 已对六次实际数字选择分别验证真实单个选中 Frame，同时保留投掷后清图标检查；覆盖只限实际执行的这些选择。

### 旧 P7：60 项检查、一次真实入场，数字选择覆盖已收窄

[旧 P7 evidence.json](../../../docs/superpowers/evidence/player-input-regression-20261115/native-p7-20261115T114003Z/evidence.json) 的 `Passed=true`、`InputMode=keyboard`。下列事实仍有效，但该模式标签不能单独证明所有动作都走了键盘：

- 法术卡先经历真实 30→29→28 次数和原 UI 角标检查，再通过原 UI 提交 DropItem（Kind 14）；真实虚拟键盘 F 经原 WorldItemPickup 提交 PickupItem（Kind 15），匹配收据和 Owner 版本后，同一实例进入本人的 SpellStorage（LocationKind 7），**仍为 28 次**。

旧轮次正例覆盖法术卡和空容器 F 路径、四瓶连续 G 投掷及投掷后的 HUD 状态，但当时没有覆盖 Native 数字选择。它没有复现用户原会话的所有前置状态，不能据此断言最初 F 故障只有 Focus 一个原因。

### 最终复核发现的数字选择工具缺口

旧工具用 `Number(intent, "Kind")` 判断是否为选择命令，而 Number 只尝试 `JsonValue.TryGetValue<ulong>`。本地 `new JsonObject` 中 Kind/TargetSlot 实际由 CLR int 构造，读取失败返回 0，使 selection=false，落入 direct inventory 请求，同时跳过该分支的 HUD 和原 Driver Caller 断言。日志中的 `SyntheticKeyboardProcessed` 只有 F/G，没有数字键，正好暴露了这个缺口。

旧 60 项结果继续保留，F/G、交易及投掷后状态可以引用；其数字键 Native 通过声明已撤回。[json-value-parser-reproduction.log](../../../docs/superpowers/evidence/player-input-regression-20261115/json-value-parser-reproduction.log) 独立复现旧 `TryGetValue<ulong>` 返回 false/0，以及严格读取 CLR int 后 Kind 3、slot 3 正确映射到 held index 6/key 7。修复的是 Console harness 对本地意图数值的读取，未修改 Native 产品输入规则。Home 16 项没有数字选择动作，其已执行范围不受此分支影响。
