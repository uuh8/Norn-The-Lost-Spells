# 移动同步平滑度与远端动画修复计划

**目标：** 修复玩家实测的远端逐包跳动、高延迟和滑行动画；保留独立 DS 权威、原角色控制器、原 Animator、P7/P8 和共享 UI。

**授权与范围：** 用户于2026-10-28直接要求结合业内方案优化现有移动同步。本计划是该修复的实施说明，沿用既有 N3/N4 架构，不引入新的网络框架或玩法。按用户此前要求连续完成已授权工作，不重复请求阶段启动确认。N4 原有人工验收项仍保留。

**执行：** 主控执行与协调 Editor/测试/构建/服务；独立算法与动画调查可以委派。按 systematic-debugging、writing-plans、executing-plans 和 verification-before-completion 工作；先观察回归失败，再修复。当前工作区存在大量尚未提交的 N4 改动，不重置、清理或夹带提交。

## 1. 已有证据与待验证假设

1. OnlineWorldBootstrap.PumpSnapshots 使用 now+interval，持续丢失晚帧余数；配置15Hz不等于实际15Hz。Mirror 自己的 AccurateInterval 注释也说明同一问题。
2. RemoteMovementInterpolation 仅在首包/Frozen固定 receivedAt-ServerTick/30 的 offset。FixedStepClock 过载会丢掉逻辑步；一次普通卡顿即可让 Client 播放时间永久超前，之后退化成“到包跳一下”。首包延迟也可能永久锁住多余滞后。
3. Replica 的 Animator speed 来自本渲染帧位移是否超过1mm。欠载时多数帧为0、来包时为1，原 Idle/Run Transition 可能持续被打断；资源和 Animator 没有缺失或关闭。
4. 输入 FIFO 最多32帧，持续收包时不能用“最后收包未超时”证明队头新鲜。先增加队列指标，不在缺少边沿/Ack设计时粗暴跳过输入。
5. 以上是静态可证缺陷，不代表已采到用户那次会话的唯一现场根因。旧探针 Rtt/Jitter/Loss 是注入值，不是实际网络测量；新证据必须标清。

## 2. 方案比较与取舍

| 方法 | 本次选择 | 原因 |
|---|---|---|
| 本机 Prediction + 权威 Reconciliation | 保留 | 自己的操作立即响应，最终权限仍在DS；不回滚整场Unity物理 |
| 远端 Snapshot Interpolation | 修复播放时间轴与缓冲反馈 | 适合当前非确定性CharacterController/AI/物理；与Render FPS解耦 |
| catchup/slowdown、bounded resync、抖动缓冲 | 加入预分配环形历史 | 普通卡顿可恢复，轻微漂移平滑纠正；不把首次offset当永久时钟 |
| 仅增加发送频率 | 不作为单独修复 | 无法修复时钟永久失步；先观察正确调度15Hz，再决定30Hz的带宽/延迟取舍 |
| 无限 Extrapolation / Dead Reckoning | 不采用 | 墙、急停、Dash结束和击退处容易穿透/回拉；缺包时有界停住 |
| Hermite | 暂不采用 | 当前协议没有完整线速度，不能从输入方向伪造速度；保留Lerp/Slerp与精确端点 |
| 全量NetworkTransform/NetworkAnimator替换 | 不采用 | 会产生双Owner并绕过现有身份/协议/权威边界；保留原Animator与显式消息 |
| Lockstep / 全世界 Rollback / FPS式命中回溯 | 不采用 | 与本次2–4人合作、现有Unity非确定性物理和材料架构不匹配 |
| 输入冗余 | 后续记录风险 | 不在本次改Schema；单份Unreliable边沿仍有丢包风险 |
| 连续输入积压压缩 | 纳入本次修复 | 只替代旧连续方向，Jump/Dash、JumpHeld和Suppressed转换按顺序执行；每权威Tick仍只执行一个输入，不以补跑取得额外速度 |

- https://mirror-networking.gitbook.io/docs/manual/components/network-transform/snapshot-interpolation
- 项目锁定Mirror/Core/SnapshotInterpolation及Core/Tools/AccurateInterval源码。
