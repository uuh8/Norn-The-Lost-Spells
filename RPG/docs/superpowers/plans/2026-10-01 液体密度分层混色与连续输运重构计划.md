## 2. 已确定的行为和数量映射

### 2.1 Density 分组和纵向区间

物理上，Density 决定浮沉，混溶还与材料性质有关。这里按用户要求采用游戏规则：**配置相同 Density 的材料共享液层；不同 Density 的材料按重到轻从下往上排列。** 这个规则不声称模拟真实混溶化学。

Density 在进入 Play 时读取 SO 并冻结。同组使用完全相同的配置数值；不在热路径用模糊的 epsilon 两两归组，避免 A≈B、B≈C、A≉C 产生不稳定排序。默认 Water=1.0、Poison=0.9、Sticky=1.15。

一个粗格的容量为 C，某一 Density Group 的各材料数量之和为 Qg：

```text
ThicknessFill(g) = Qg / C
BaseFill(g)      = sum(Qh / C)，h 的 Density > g
TopFill(g)       = BaseFill(g) + ThicknessFill(g)
Share(i)        = Qi / Qg，i 属于 g
```

例如 C=510、S=0.5m，Water=306 GMU、Poison=102 GMU：Water 从底部到 0.30m，Poison 从 0.30m 到 0.40m，空余高度为 0.10m。不能把 408 GMU 都解释为 Poison，也不能让 102 GMU 的 Poison 拥有与整池相同的厚度。

多层满格之间由局部 Density Exchange 逐渐调整材料位置。格内区间只是同一数量状态的空间解释，不修改材料 ID 或 GMU。局部交换必须同时扣加两种材料，维持各自数量和全场总量。

### 2.2 同密度混色与不同密度界面

同密度混色在 Linear Color Space 进行，权重来自同一个平滑数量场。当前位置 p 的材料权重为：

```text
Ai(p) = sum(K(p - cj) * Qi(j))
wi(p) = Ai(p) / sum(Ak(p))，k 与 i 同 Density
Color(p) = sum(wi(p) * MaterialColor(i))
```

K 为紧支撑 Kernel，即只读取有限邻格、在半径外为零。不能先对每格选赢家再平滑赢家颜色，否则格子身份切换依然可见。Shallow、Deep、Fresnel 颜色和 Alpha 分别使用同一套权重；不同材料的数量及反应仍分别保留。

不同 Density 使用各自的 Base/Top 和连续层覆盖场。上层边缘圆润地收回下层顶部，下层边缘才收回地形。颜色只在界面极窄的过渡带内抗锯齿，不把上下两层整体混成一种颜色。

几何采用统一外壳：下层外侧、上层自由面和上层圆肩都属于这一套外壳，Vertex 带材料权重。内部相接处不重复绘制两张共面的透明面，因此不会靠多份透明 Geometry 制造抖动。下层仍有真实厚度和侧面；统一外壳并不等于把整格都涂成上层颜色。

### 2.3 保持可见量与 Gameplay 量相称

- 保留 S=0.5m、C=510 GMU、现有单位体积倍率和 GMU→m³ 换算，不再次偷偷放大法术产量。
- 主体和浮层厚度直接来自上述数量区间。现有圆冠公式允许有界的艺术夸张，但逐层累计同一高度映射，不能对每层分别套无条件最小厚度。
- 从 World Space 查询状态时，按查询细格与液层区间的重叠长度计算 Amount。同密度混合层再乘各材料份额。
- 地形支撑坐标修正同时提供给状态投影和 Renderer，不能只把画面往下拉到斜坡、Gameplay 仍悬在半空。

累计艺术高度使用单调映射，例如 `H(f)=f+min(.15*f,.65*min(f,1-f))`；层底/层顶同时调用H，满格仍对应H(1)=1。它把旧主体之外的圆冠也纳入总高度上限，避免“主体只加15%，圆冠又额外抬很多”的重复放大。角色查询使用真实区间加地形支撑修正，圆冠不额外制造Wet/Poison作用体积。

## 3. 斜坡与连续运动怎样实现

### 3.1 缓存真实地形，不在每帧逐格调用 Physics

新增有界 `LiquidTerrainSupportCache`，在 Chunk 首次使用或显式 Rebuild Terrain 时读取静态 Collider：复用 `RaycastHit[]`，使用 `RaycastNonAlloc`，过滤 Trigger、动态 Rigidbody、CharacterController 和角色/Projectile。Normal 和 Height 全部使用 World Space。

每个支撑采样至少存 GroundHeight、Normal、Valid、TerrainVersion。对同一可见平面使用中心和四角采样拟合/验证平面；跨 Cube 边缘或悬崖不能把两个高度直接平均成一条虚构斜坡。墙体继续由 Solid 和有界路径检查阻挡，不能把所有有上表面的 Cube 都当成可穿越斜坡。

Grid 仍是粗粒度近似。用连续支撑面建立“逻辑支撑高度→真实支撑高度”的局部映射，并在角色查询中复用；不要新增一次全场 Cut Cell 容量重算。遇到多层平台、洞穴或无一致支撑平面，保留该格原有保守阻挡并记录诊断计数，而不是错误投影到远处地板。

### 3.2 活动液体保存速度，静止湖底没有速度对象

每个活动格/材料使用预分配 Slot 保存横向速度、未满一格的位移和通量小数余量。休眠后回收 Slot，GMU 留在 Store/Stable Region。速度是运动状态，不是物质量。

切向重力为：

```csharp
Vector3 gravity = Vector3.down * 9.81f;
Vector3 tangentGravity = gravity - Vector3.Dot(gravity, normal) * normal;
velocity = (velocity + tangentGravity * dt) * Mathf.Exp(-drag * dt);
```

这里 Dot 是沿法线的投影长度；减掉法线分量后，剩下的加速度沿斜坡向下。平地的切向重力为零，平地摊开另由邻格自由面 Height 的差驱动。Drag 是速度衰减率，单位为 1/s；它与 Density 分开配置，空气中三种液体仍使用相同重力。

首轮配置目标为 Water Drag=1.5/s、Poison=4/s、Sticky=12/s；这些是初始游戏参数，需要最终观感检查，不是实测物性。保留既有 GMU 通量上限作为硬预算。地面最大平移速度先限制为 2.0m/s：S=0.5m、dt=0.1s 时单步位移不超过 0.4格，减少跨多格越墙的风险。

横向候选同时寻找邻列本层和有限的下斜层，检查 Solid/支撑区间；一次转移必须通过 Store 的成对扣加。通量小数余量避免较小速度全部被整数 GMU 舍弃。轻重交换、注入、燃烧和转换都必须正确失效相关 History，避免用转换前的材料继续显示运动。

### 3.3 Tick 间插值需要连续场，而非只插值 Transform

单纯增加 normal 波纹不会让岸线移动。新 `LiquidTransportHistory` 保存相邻两个已提交 Tick 的局部数量/姿态；每个材料都参与同一 Presentation Epoch。

```text
alpha = clamp((PresentationTime - PreviousTime) / (CurrentTime - PreviousTime), 0, 1)
```

默认显示时间比 Gameplay 落后一个 Tick，在 10Hz 下约 100ms，换取不预测未来碰撞。注入等离散事件在下一可提交 Epoch 出现，不无限等待。Warm Start、暂停/恢复、Catch-up 多 Tick 和场景重新初始化需要各自处理时间原点。

对运动液体，在插值数量场前按已记录的有界位移对上一帧和下一帧的采样位置做双向 Warp，再插值；直接对两个固定位置的占据格做 alpha 混合容易变成原地缩小/另一格长出。Warp 位移不能超过已验证的通行距离。Solver 没有处理到的格维持姿态，不能让 Renderer 擅自替它积分越墙。

GPU 每帧提取这个连续场的外壳，改变拓扑时也无需 CPU 在两套不等长的 Mesh Vertex 之间寻找配对。冻结整批 Epoch、保留旧完整结果、下一批追赶新版本的原则继续保留；稳定湖底不复制到 History。

## 4. 为什么选择这一条路线

| 方案 | 可以解决的部分 | 代价与选择 |
| --- | --- | --- |
| 继续调 Crown/Kernel 或提高 SideFlow | 个别轮廓与摊开速度 | 不改变 Tile 材料 Owner、层厚度或 Tick 跳步，无法解决本轮根因 |

## 5. Assembly、只读接口与资源预算

### 5.1 责任与数据流

```text
Behavior SO：Density、Drag、速度/通量上限
  → ElementField：数量、支撑缓存、局部输运、液层、History
  → 只读契约：相邻 Tick、层区间、材料份额、TerrainVersion
  → Rendering：CPU 上传 → Compute 连续场 → Surface Nets → Draw

角色/反应查询 ← ElementField 的真实液层与材料数量
Stable Region → 稀疏 Patch / 局部接触展开 → 同一显示 Epoch
```

`Game.ElementField` 和 `Game.Rendering` 的现有单向依赖不变，不增加 `Combat→ElementField` 或 `ElementField→Rendering`。Renderer 不能调用 Wake、Move、TryConvert。GPU Data 不回写 Quantity，GPU 读回只用于低频诊断。

新契约的核心形状如下；所有数组由调用方在初始化时预分配：

```csharp
public readonly struct LiquidLayerSample
{
    public readonly int DensityGroup;
    public readonly float BaseFill, ThicknessFill;
    public float TopFill => BaseFill + ThicknessFill;
    public LiquidLayerSample(int group, float baseFill, float thicknessFill)
    { DensityGroup = group; BaseFill = baseFill; ThicknessFill = thicknessFill; }
}

public interface ILiquidLayeredSurfaceReadOnly
{
    int MaterialCount { get; }
    int GetDensityGroup(MaterialId material);
    bool TryGetLayer(Vector3Int cell, int densityGroup, out LiquidLayerSample layer);
    float GetGroupMaterialShare(Vector3Int cell, MaterialId material);
}
```

Transport 契约输出 Previous/Current 采样时间、数量、OffsetCells 和 VelocityWorld；Snapshot 固定 Epoch 和 TerrainVersion。时间使用秒、Velocity 使用 m/s、Offset 使用无量纲 Cell 单位；World Position 统一为 `Origin + CellCoordinate * CellSize` 加局部修正。不能把角色细格坐标与液体粗格坐标混用。

### 5.2 GPU 内存必须预先算清楚

新增 Grid 专用 Render Profile，不复用旧 PBF 的 `LiquidRenderProfile`。预算以同一世界所有活动材料的共享资源计，不允许每个材料各分配 128MiB。

- 初始化硬预算默认 **128MiB**；预算不足时在进入 Play 前降低可用细分页上限，运行中不临时扩容。
- 每页 K=8 个 Gameplay Cell；数量/运动输入含每边 3 Cell Halo，输入采样数为 `(K+6)^3`。
- 每材料输入 16 bytes：数量用 ushort 无损保存；Flags 和 half 编码的有界 Velocity/Offset 放入四个 uint。CPU Solver 继续使用 float。Half 是 GPU 上传压缩，不改变数量精度；需要验证最大速度和位移的解码误差。
- Previous/Current 两份输入；Terrain 16 bytes/输入格，仅一份；最多 8 个配置液体槽。
- Surface Nets Vertex 48 bytes：World Position、Normal、8 个 half 权重和深度信息；每个采样 Cube 固定一个候选 Vertex Slot。
- Index 最坏为每个 Core Cube 3个 Quad，即18个 uint；空 Cube 输出退化三角形/零 Draw Count，不使用无界 Append Buffer。
- 三维细分默认 r=2，只影响 Presentation。为平滑和法线保留 3 个细 Cube Halo。全部可见活动页使用同一 r，避免页边 LOD 裂缝；r=1 是预算回退。

细/粗资源同时计入长期预分配高水位。可见页超过细页上限立即使用r=1；回到上限的75%以下并持续1秒才恢复r=2，避免相机边缘或临界页数导致反复切换。r变化仍使用同一连续Field和材料权重，切换的体积误差也纳入回归。

默认3材料、128粗页/64细页的预分配高水位示例：

```text
CellSlots = 128 * (8+6)^3
CubeSlots = max(64*(16+6)^3, 128*(8+6)^3)
NodeSlots = max(64*(16+7)^3, 128*(8+7)^3)
IndexSlots = 18 * max(64*16^3, 128*8^3)

Bytes = 2*CellSlots*3*16 + CellSlots*16
      + CubeSlots*(48+24) + NodeSlots*4 + IndexSlots*4
      ≈ 105.28MiB
```

24 bytes/Cube 是平滑位置的双缓冲，105.28MiB 不含少量 Args/Palette/Patch/诊断，因此预算判定仍需把这些实际 Buffer 全加上。增加材料数必须重新计算允许的细页上限，不能沿用“3材料”的估算。

如可见页超过128，必须保留覆盖：已有完整表面继续显示、超额页进入明确的 CPU 参考/粗面回退并计数；不能只选最近128页并让其余液量在镜头内消失。回退只能降低显示细度或更新频率，不能改 Quantity。资源创建失败时整套切到参考路径，旧 GPU 和 CPU 不得重复绘制同一页。

GPU Draw 使用 [Unity 6.3 `Graphics.RenderPrimitivesIndexedIndirect`](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Graphics.RenderPrimitivesIndexedIndirect.html)。逐页的 World Bounds 用于 Culling 和透明排序，不能用一个覆盖全世界的大 Bounds 掩盖丢面。每帧不做同步 `GetData`；GPU 诊断读回只在关键检查中使用缓存的 `AsyncGPUReadback` 回调。
