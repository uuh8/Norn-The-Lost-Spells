# 背包左上整理修正与流体表现审查

本轮依据：用户明确将整理方向从右上更正为左上，并要求审查现有流体的断续运动、空中格跳以及 Terraglass 可借鉴之处。整理直接修正；流体交付源码证据、方案取舍与分阶段建议，本轮不将“审查”扩大成更换权威模拟器。

## 1. 整理规则修正

- 共用 `BackpackOrganizeOps` 与业务服 `AccountInventoryMoves` 都按 Y 从上向下、X 从左向右寻找合法位置，每个位置优先原朝向，再尝试其他朝向。
- 保留类型、ContentId、实例稳定排序；兼容材料数量合并、独立法术身份、占格形状、版本、Reservation 与失败原子性均沿现有路径。
- 修改已有混合形状/同类相邻/重复整理与 HTTP 幂等回归的目标方向，先保存 RED，再运行受影响规则、UI gateway、业务测试。
- 刷新 GameplayHash、构建同源 Client/DS、发布业务服；仅在无玩家实例且原 PID/启动时间符合时更新本地默认产物，保留旧目录。正式 Scene/BuildSceneList/输入等文件前后 Hash 比对。

## 2. 流体源码与参考审查

- 模拟：正式配置、时间与空间步进、flux/重力/惯性、Stable/Dynamic/Pending 和碰撞。
- 同步：真实 authority Tick、Commit/发送、快照内容、Replica 历史与渲染输入；区别前轮已修的 Delta 排队与仍存在的连续运动限制。
- 渲染：GPU/CPU fallback、field 重建、surface 插值、空中形状、flow/normal/foam/refraction，以及现有 PBF 路径的适用边界。
- 参考只使用开发者或原始技术资料。明确“参考公开实现”“本项目源码证实”“待 Native Profiler/录像确认”三者，不能根据两张静态截图推断帧率或完整算法。
- 写入中文解析：症状 → 调用链 → 证据 → 可优化点 → 分阶段验收。优先连续运动和空中体积，再做水面细节，保持 DS 数量权威与 Client 只读表现。

## 3. 交付边界与资源

整理无需新增美术资源；流体审查也不要求用户提供新资产。后续如进入水面细节制作，优先复用现有材质和程序噪声，并在实施计划内说明 normal/foam 贴图依赖及 fallback。当前不升级依赖、不改协议、不提交或推送、不把静态审查称为流体体验已改善。
