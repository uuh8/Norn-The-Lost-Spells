### 追加：客户端进程重启后的原 Run 恢复

本轮独立审计确认：当前主菜单进入据点时正确拒绝被原 Run 锁定的资产，但新进程没有 `_room`/Coroutine，无法使用已有的进程内重连。合作队友仍在线时，这会长期阻断该成员恢复。业务端 `GET /rooms/current` 已支持从当前 Session 身份找回原房间；Ticket 消费也已保持原 Actor 并提高 ConnectionEpoch，因此无需新增协议或解除租约。

沿用户本轮直接修复授权实施以下最小方案，不增加新的玩法模式：

1. Enter 按钮在本次 Profile 证实有活动 Run 时表达“恢复当前副本”，普通账号仍沿原进入 Hub 流程。锁定资产不能走 `TryArmHubEntry`。
2. 冻结恢复的 PlayerId/ActiveRunId，仅查询原 current room，核对成员、Run、Epoch、Dungeon 和单人标志，再复用现有 Ticket/Connect/Connected。Starting 只跟踪原房间；失败/未知结果保留锁定，不请求新 Run，不重发初始物品。
3. 单人 current room 的验证与首笔 single-entry 命令确认分开；不伪造原命令 ID 或 ExpectedVersion。异步等待后重验身份，换账号不能接受原回复。
4. 新进程原主菜单作为独立导航来源挂起，不放进 `_suspendedHub`。同进程原 Hub 往返保持原路径。cold 恢复后的个人退出必须确认 receipt 和完整 unlocked Profile，再恢复原菜单；继续进入据点仍经过原来的本次 Profile Gate。这比在恢复协程中另建一套 Hub 装配更小，代价是冷启动恢复退出后多一次进入据点点击。
5. 使用正式方法边界编写 RED/GREEN：锁定入口分流、单/多人 current 身份验证、错误 Run/Player/Dungeon/成员拒绝、重复点击/失败重试、已确认退出前不恢复菜单、原 Hub 往返不回归。业务端补充新 Session 找回原房间并兑换更高 ConnectionEpoch 的真实 test MySQL 证据。

实现所有权交给 Inventory reviewer 转任的恢复 Agent：Account/Room Runtime、必要的 Core 只读 view/UI 文案及新增恢复 tests；Root 继续统一测试、Editor、构建、Git。广泛回归运行期间先不写 Assets 源码，避免中途重编译。完成后独立 review，再刷新兼容 Hash 并构建。
