# 仓库容器标注与商店购买确认框 Implementation Plan

> 执行方式：用户确认本计划后，用 `superpowers:executing-plans` 在当前工作区实施；不使用 SubAgent、不创建 worktree、不提交 Git。设计与实施步骤合并在本文件，不另建 spec。

**Goal：** 仓库中的独立容器显示自己的已装量/容量；商店购买先进入可调整数量的确认框，最后一次确认才成交。

**Architecture：** 确认框属于 Game.UI，读取现有商品、钱包和库存快照。ShopController 统一管理购买意图和弹层生命周期；最终通过现有 ShopTradeRequestedEvent 交给 Game.Run 的交易服务。UI 不直接写金币、供货或容器内容，不新增交易后端或购买预览清单。

**Tech Stack：** Unity 6000.3.16f1、UGUI Image/Text/Button/Slider、Input System、EventBus、Unity Test Runner、Profiler。

## 1. 当前证据与玩家操作

2026-10-12 本轮只读检查确认：当前单独打开 SinglePlayer_Hub，非 Play，场景没有 Dirty 标记。商店左栏 GoodsRegion 下已有 Search、Category、Offers、Buy；作者已删除旧 QuickPurchaseRegion 和数量输入框。ShopController.Start、Send 和 TryMaterialTarget 仍直接读取 `_quantity`，不能只添加一个弹框而继续依赖已删除的对象。右侧只有 DetailsRegion，符合暂缓详情开发的要求。

WarehouseCatalogGridView 已将每个容器独立分组，但 Caption 仍统一拼接 `×1`，然后另起一行拼接容量。容器改成名称与 `已装量/容量`，如 `采集瓶\n9/150`；空瓶显示 `0/150`。非容器的按类计数保留。背包与仓库显示来自同一份具体容器快照，切换窗口不会改变材料量。

购买流程：

1. 第一次点击商品只选中，仍不成交。
2. 点击左栏现有购买按钮，打开居中的“购买物品”确认框。保留此前要求的第二次点击商品时的鼠标旁小菜单；该菜单的“购买”也只打开同一个确认框。
3. 框中调整数量，查看总价；点“取消”关闭，选中商品保留。点框内“购买”才发送一次交易命令。
4. 成功后关闭确认框，刷新仓库/背包、供货、所有金币栏，并在独立的简短反馈位置说明实际去向。失败保持资产不变，在框中显示明确原因；需要重新选择时关闭框并提示。

此方案保留用户此前授权的两种入口，集中管理真正的成交时机。替代方案是恢复左下数量输入区，或第二次点击直接购买；前者与作者删除冗余区域的意图冲突，后者无法让玩家确认数量与总价，因此不采用。

## 2. 确认框内容、数量规则与边界

使用半透明遮罩和一个可精修的居中 Panel。信息按参考图排布：标题；商品图标、名称与关键说明；购买数量；减号、水平 Slider、加号及最小/最大值；剩余供货、单价、总价、当前金币；取消/购买。元素购买额外显示指定容器名称和当前储量/容量，避免玩家不知道材料进入哪个瓶子。

目前商品快照没有描述文本。本轮不扩张物品配置或凭空编造介绍，关键说明由已存在的数据生成：商品种类、法术初始次数/无限状态、普通物品背包优先且空间不足入仓、连续元素注入指定容器。后续商品文案可单独扩展。

- 初始数量为 1，每次重新打开都重置，避免上次批量数量造成误购。
- 普通商品以“份”为单位；按连续元素报价的商品以 GMU 为单位。Slider 使用 Whole Numbers，按钮每次加减 1。
- 最大可购买量 = 供货、金币可支付数量的最小值。普通商品还遵守后台当前单笔 128 份限制；连续元素还受所选瓶子剩余容量限制。背包空位不限制购买数量，因为现有规则允许自动入仓。
- 金币可支付数量用整数除法计算，不使用 float 计算价格。UI Slider 仅表现有限整数范围：普通商品最多 128；容器配置容量来自正整数。对极端大容量需要明确处理 Slider float 精度，采用数量整数为权威并映射 Slider 进度，禁止直接把 ulong 股票数量强转 float 后当成交数量。
- 最大值为 0 时不可购买，给出缺少金币/供货/兼容容器/容量的对应原因；不创建 minValue 大于 maxValue 的 Slider。只有一个数量可买时 Slider 和加减按钮禁用，确认仍可用。
- 库存更新后读取最新余额与供货，不把旧框中的报价当成后端权威。总价使用 checked 整数乘法，异常配置禁用成交而非溢出。

元素购买仍要求中列已经选中具体容器；不兼容、满瓶、非容器不能购买。判断“能否打开确认框”使用至少 1 GMU 的容量检查，彻底退出对旧数量输入框的依赖。确认框记录商品 OfferId 和容器 InstanceId，不能因为后台变化自动换瓶。外部目标消失或改变可达归属时关闭并要求重选；其他余额、容量、供货变化重新计算上限并钳制数量，明确更新显示。最终发送当前库存/商店版本，后台继续复核并保证整笔原子提交。

遮罩阻止点击穿透至商品、出售按钮和中列拖拽。Esc 优先关闭确认框，其次关闭鼠标小菜单，最后关闭商店。Tab 切背包、离开区域、禁用控制器或关闭商店必须清理两个弹层，不改变已有暂停/光标恢复逻辑。购买按钮提交时加提交状态保护并禁用，防止同一手势重复扣钱；按现有同步交易结果恢复或关闭。

## 3. 资产依赖和作者布局保护

无需用户补充图片、字体、VFX、音频或模型。复用现有物品配置中的 Sprite 和当前 UI Font；图标缺失时隐藏图像区域并使用名称/说明，不生成假的商品图。

保留左栏 Search/Category/Offers/Buy 的位置、尺寸、图片、字体和排序；保留中列背包/仓库及金币接线、右侧详情占位。只增加 ConfirmPurchaseDialog_购买确认层及必要反馈 Text；反馈如果已有可复用节点就复用，不重建棕色区域。不恢复购买预览，不重新套用旧商店布局生成器。

## 5. Editor 验收、Debug 与回退

正式应用只增加购买确认层及引用，用户无需手动把底层购买按钮重复绑定到最终提交方法。Hierarchy 中可修改确认框色块、图标尺寸、Text、Slider Handle 和按钮样式，保留全屏遮罩的 raycastTarget 与层级最上方关系。按 Play → E 打开商店：商品选中、两种入口、Slider 调数量、取消零扣款、确认只扣一次；选两个不同储量瓶子分别购买，验证仓库无 ×1，三界面金币一致。右详情区域保持占位。

Debug 顺序：引用是否为空 → 确认框是否挡住底层 → 当前选中商品和容器 ID → 最大数量/单价/当前金币 → 最终命令 Quantity/版本 → 后端 receipt 与真实余额/材料。不要通过增加钱包 Text 数字或改变库存来掩盖失败。对已失效商品/目标给明确原因。

增量 Scene 操作出错时整组 Undo 回退；源码按本任务具体 diff 回退，不 reset/清理整个工作区，不删用户新增布局。测试失败先修根因，不覆盖正式场景来绕过 Dirty 保护。自动验证后恢复单独据点并报告未保存的本次 UI authoring 状态。
