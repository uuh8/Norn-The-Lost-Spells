# M3-T1 容器采集与数量交易实施计划

范围来自总案 M3-T1；本轮继续开发和集中试玩已经授权。只完成采集、组分、固体物品及保存基础，倾倒/投掷交给 M3-T2，法术附着交给 M3-T3。没有新的玩法分歧需要确认。

## 1. 玩家成果与数量规则

在独立 ContainerSandbox 直接体验固定速度收集近处材料。容器显示真实各组分和容量；范围内混合材料按实际比例一起转移，容量不足按比例部分采集。整数 GMU 是唯一数量真值。速率用 GMU/秒，保留小数时间余量；松开输入、失败、暂停不积攒下一次突发预算。普通瓶子的允许组分在 ItemDefinition 配置，默认排除 Fire 与固体，固体走单独采集成物品入口。

空瓶在同一格位堆叠时，先在同一背包寻找合法独立位置，提交时同时分开和装料；满包失败保留原堆叠和世界。固体采集必须预留真实物品格位，份量进入 MaterialItemState，不能用显示名/StackStateKey 冒充数量。新配置使用测试参数，不视为最终平衡值。

## 2. Assembly 与事务

- Core：MaterialAmount（byte 稳定键、ulong GMU）、采集意图/世界命令/结果与同步目标预约接口。Core 不依赖 Materials、Run、ElementField。
- Run：ContainerComposition 预分配 256 槽，公开只读，唯一内部写入口；ContainerReservation/InventoryMaterialTransferService 负责容量、归属、背包空间和版本。RuntimeItemState 持有只读状态引用；连续采集原位更新数量，不重复复制完整库存。读者 CopyTo 获得自己的快照，事件不借出临时数组。
- ElementField：MaterialInventoryTransferAdapter 与真实 Owner Journal，采样按各后端自身 origin/cellSize，有界范围和条目；不从 byte projection 或 Renderer 反推。先聚合、比例分配、预约目标，再逐项 StageRemove，几何/拓扑预检通过才提交目标并发布世界改变；失败逆序 Undo，液体保留 dynamic/stable receipt。Explicit export ledger 与 conversion consumption 分开。
- Character：MaterialCollectionController 仅提交 Core 意图，使用 Input System 和预分配输入对象，固定速率累计，距离限制由 Runtime 同时检查。
- UI：ContainerCompositionView 读取实际组分；界面在离散结果/低频显示刷新，不引用 ElementField 或直接改账本。

同步主线程调用栈是 commit boundary：预约期间 Run 锁阻止移动、施法和保存；World Stage 期间不发布事件，不允许重入。请求带库存范围、WorldId、RequestId 与 expected inventory version；每个客户端单调序号拒绝重放。World 命令只接受已预约的目标引用，并在结束解锁。没有无人接收的预约留到下一帧。

## 3. 持久化与兼容

存档 Schema 2 显式保存 MaterialAmount 数组以及固体键/数量；兼容读取 Schema 1 的空容器/无材料状态。恢复验证未知键、重复组分、超容、容量配置变更和物品种类不匹配，失败保留原档。预约不写磁盘；装料后的堆叠兼容直接比较真实组分，避免字符串键伪造和每 tick 字符串分配。

## 4. 文件与验证

新增 Core/Materials 与相关 Events；Run/Containers 的组分/比例/预约、Inventory/MaterialItemState 与 transfer service；ElementField/Materials adapter 与 Runtime transfer partial；Character/Interaction controller；UI/Containers view；Editor 独立场景生成器；Run 和 ElementField focused tests、Run PlayMode 场景测试。

修改 ItemDefinition/InventoryItemRules、RuntimeItemState、ItemOwnershipStore、ItemStackOps、ProfileSaveMapper/DTO、SinglePlayerInventorySession 和官方 TestRunner Gate（增加 ElementField 的明确 fixture）。不修改战斗控制、P7/P8、当前 Scene。

测试先验证生产 API 缺失，再验证水/毒 100:50 采 30 → 世界 80:40、容器 20:10，比例/整数余数、容量、空瓶拆堆空间不足、重复请求、过期版本、Unknown key、固体成物品、保存恢复、stable Owner 与 Gas/Ice 真数量、几何拒绝及 Undo。回归 M1/M2，运行官方 Editor 的 EditMode/PlayMode，创建独立 Scene 并留图。用户集中试玩、Standalone 和 Profiler 单独记录，没测不报通过。

## 5. 资产、性能与调试

不需要外部资产：使用已有测试整备 UI、Unity primitives、已有 GridLiquid/solid/gas profile 与 OS 字体，所有新 SO 放 ScriptableObjects/Tests/SinglePlayerContainers。Renderer 不影响 GMU 采样。正式外部地图仍属于 M6。

连续路径复用采样地址、quantity、receipt、MaterialAmount 数组与预约对象；选择/首次拆堆/新固体拾取是离散操作可分配。几何重建可能有 Unity Native 成本，应由 Profiler 定位而非改采样真值。范围/缓冲超限明确失败，不能静默只拿前几种材料。保留已有材料休眠/圈外暂停；不删除可见材料掩盖性能。

调试按症状→证据→排除→根因→修复与取舍→回归→限制记录。回滚本 Task 时保持旧资产 GUID，Schema2 原档保留，不能让旧读取器覆盖不认识的新档。

## 6. 画面验证后新增的必要修复

独立 Scene 实际提交 Poison Mesh 和 stable Water，但 D3D12 日志报 Dormant Shader 缺少 `_LiquidOwnerLookup` SRV，跳过 Draw。原因是旧独立表面路径不使用连续场归属表，仍需满足 Shader 的资源绑定要求。限定在 Game.Rendering 内新增 LiquidSurfaceDomainBindings 初始化一个全零 int4 Structured GraphicsBuffer，为 LiquidSurfaceRenderer 和 StableLiquidSurfaceRenderer 的两份归属查询绑定安全默认值；连续场路径按既有逻辑覆盖真实域。各 Renderer 在 OnDestroy 释放自己的 Buffer，不使用 static GPU 资源，不改变材料数量、透明度、Shader 或采样。

先让真实 Scene PlayMode 测试明确检查默认 Buffer 缺失，取得 RED；再实现绑定并复查截图、Buffer 生命周期与旧 Boss/材料/法杖回归。取舍：每个旧 Renderer 增加一次初始化分配和16B GPU 数据，换取严格的图形 API 合法性；无新增每帧上传。该修复只涉及已有 Rendering 内部资源责任，无新增生产 Assembly 依赖。
