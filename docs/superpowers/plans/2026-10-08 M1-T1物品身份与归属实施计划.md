## 1. 玩家结果、目的与范围

这一 Task 建立以后背包、法杖装配、保护、搜获和交易共同使用的资产基础。例如两张水法术引用同一个固定法术配置，但分别保存剩余 3 次和 8 次，移动其中一张不会搬走另一张。固定配置回答“这是哪一种物品”，实例回答“玩家拥有的这一份目前是什么状态”。同名副本不能被旧奖励去重规则合并，也不能用显示名称或 Unity 的临时对象编号做存档身份。

本 Task 交付代码及独立规则测试，还没有背包操作界面、保存文件、实际扣费或三杖切换。完整二维占格、堆叠与丢弃在 M1-T2；整备 UI、保存和 InventorySandbox 在 M1-T3；法杖资源和法术执行扣次在 M2。字段设计允许后续扩展，但不会用空实现假称后续功能完成。

本 Task 不需要用户提供地图、模型、贴图、音频或字体。EditMode 测试创建临时 ScriptableObject，测试结束销毁；不创建或覆盖真实玩家资产和 Scene。

## 2. 核对后的基础与实施选择

- 旧 `RunSpellInventoryOps.TryAppendUnique` 按 `SpellDefinition` 引用去重，继续服务 P7/P8。
- `RunSpellSession` 已隔离 Runtime Library/Wand 和模板数组，不能替代独立资产归属表。
- `Game.Run.asmdef` 已引用 Core/Combat/Skills，Tests/Run 已引用 Run/Core/Skills，无需修改 asmdef。
- 当前 Editor 有显式请求入口；新增本 Task 专用测试入口，避免改造旧元素测试工具或启动第二个 Editor。

**推荐：独立实例表。** 每个实例一个稳定字符串 ID，目录用区分大小写的稳定配置键索引；位置只存在归属表中。它能明确保存同名副本，并允许后续 UI 读取版本号决定刷新。

**替代：在旧法术数组增加次数数组。** 数组下标随拖拽变化，需要同时维护多个数组，无法可靠表示背包、装备、地面与具体保护对象。

**替代：每份物品复制一个 SO。** 能隔离对象，但 SO 引用不是磁盘身份，管理大量运行时 Unity 对象也增加生命周期责任。因此固定配置共享，动态状态使用普通 C# 对象。

## 3. 数据与公开接口

### 3.1 配置和实例

| 类型 | 具体责任与生命周期 |
|---|---|
| `ItemKind` | Spell、Wand、Backpack、Container、Material、Consumable；显式 byte 值，后续只追加 |
| `ItemDefinition` | SO 的私有序列化配置：稳定 ContentId、Kind、显示名、图标、可选 SpellDefinition；对调用方只读 |
| `ItemCatalog` | SO 中的配置列表；初始化时检查空引用、非法/重复键、非法种类、法术配置缺失 |
| `ItemCatalogIndex` | 成功初始化后创建的只读查询目录；字典不暴露，键采用 `StringComparer.Ordinal` |
| `RuntimeItemState` | 只读 InstanceId/ContentId、有限剩余次数、显式无限标记；位置不再重复存一份 |

实例构造接收恢复数据；加入归属表时统一验证，非法数据不能进入权威库存。无限使用通过独立 bool 表达，不用负数伪装无限。新发放由 `RuntimeItemState.Create` 在离散操作中生成 `Guid.NewGuid().ToString("N")`；读取、移动、保存恢复保留原 ID。

总案示例中的无参 `new ItemOwnershipStore()` 是概念示例。正式接口要求传入有效 `ItemCatalogIndex`，使未知 ContentId 无法混入资产。后续保存恢复也必须先建目录，再恢复实例；这是初始化细节的明确化，不改变玩法。

```csharp
bool ItemCatalog.TryCreateIndex(out ItemCatalogIndex index, out string error);
bool ItemCatalogIndex.TryGet(string contentId, out ItemDefinition definition);
RuntimeItemState.Create(string contentId, int remainingCharges = 0, bool hasUnlimitedCharges = false);
new RuntimeItemState(string instanceId, string contentId, int remainingCharges,
    bool hasUnlimitedCharges = false);
new ItemOwnershipStore(ItemCatalogIndex catalog);
```

形状、堆叠和不同装备的专属参数由后续 Task 接入，此处不设置未确认的背包大小或法杖槽位容量。

### 3.2 唯一位置与验证

`ItemLocation` 是不可变值，保存 Kind、OwnerId、格坐标、90° 旋转次数和槽号。Warehouse 是根位置；Backpack 的 OwnerId 指向背包实例；WandSlot 指向法杖实例；EquippedWand/EquippedBackpack 指向装备上下文；WorldItem/ThrownContainer 指向地面或在途上下文。

```csharp
bool ItemOwnershipStore.TryAdd(RuntimeItemState item, in ItemLocation location);
bool ItemOwnershipStore.TryGet(string instanceId, out RuntimeItemState item);
bool ItemOwnershipStore.TryGetLocation(string instanceId, out ItemLocation location);
InventoryOperationResult ItemOwnershipStore.TryMove(string instanceId, in ItemLocation destination);
```

`Count` 和 `Version` 只读。新增/实际移动成功后 Version 增加；失败和移动到同一位置均不增加。结果包含 Success、Reason、Version；Core 失败原因保留总案指定值，并追加 InvalidIdentity、DuplicateIdentity、UnknownContent。

验证顺序：身份/配置/次数 → 位置字段 → 父实例存在与持有链无循环 → 物品/父对象种类 → 独占槽冲突 → 一次提交。循环检查沿已有父链遍历，以实例数作为上限，不分配临时 HashSet。

本 Task 检查负格坐标、旋转范围、槽号、非法 Kind 与唯一槽；Backpack 的具体形状碰撞/容量交由 M1-T2，WandSlot 的容量交由后续法杖配置。公开方法不声称已经验证二维几何。全局“携带最多三杖”由 M1-T2/M2 的整备服务落实，此处 EquippedWand 只允许 0/1/2 三个槽。

## 5. Review Focus 与测试输入

1. 同名副本共享配置但实例不同；移动一份、拒绝重复 ID 都不能改另一份。
2. 无效目录、未知配置、空身份和负次数不得进入库存；初始化失败不发布半份目录。
3. 无父对象、自持有、间接循环、错误父种类都不能改变原归属。
4. 独占槽、负坐标、非法旋转和槽号必须拒绝；无变化移动不造成刷新。
5. 测试入口不得自动保存当前场景、进入 Play Mode 或修改真实库存；原 P7/P8 的定义去重回归仍通过。

## 7. Debug、性能与回滚

资产问题沿 `ContentId → 目录 → InstanceId → Location → 父链 → Version` 检查；重复/非法请求先比 Count、Version 和旧 Location，确认失败没有部分写入。配置错误不能退化成按显示名查找。

目录初始化、Guid 创建与字典扩容属于离散操作；查询和值结果不分配，归属层没有 Update/FixedUpdate。独占槽检测暂用 O(n) 顺序扫描，持有链 O(depth)，在完整背包容量确定后再按实测决定是否增加索引；本 Task 不宣称 Profiler 零 GC 已验收。

回滚可移除这批独立新脚本并禁用新测试入口，旧角色/战斗/施法和 P7/P8 未改动。Unity 自动生成 `.meta`；不手写 GUID，不清空资产，不改变用户当前场景。
