**Goal：** 为 Water、Poison、Sticky 及未来液体建立共同的持久物质底层，使液体数量不依赖 PBF 粒子池；支持局部流动、长期留存、状态接触、材料反应和连续可见表面，再用稳定液体区域加速大水体的储存与排水。

**Architecture：** 第一层使用稀疏三维格子保存与推进液体；第二层仅对符合条件的稳定液体使用容量／水位表示。统一查询、转移记账和表面输入，压缩不等于更换渲染风格。正式 P7 已切换至 Grid Liquid；现有 GPU PBF 代码与停用组件保留，回退依靠切换前备份和独立 Profile，不在 Play 中切换数量 Owner。

**Tech Stack：** 项目当前 Unity 6.3、C#、URP、ScriptableObject、Sparse Voxel Grid、活动队列、守恒流量交换、Surface Nets 候选网格生成、容量曲线与低频结算。首轮不引入新包，不预先要求 Burst/Jobs 或新的 Compute Shader；CPU 实现只是便于建立清晰原型，不预设它比 GPU 快。

**Spec：** 本文同时承担设计说明与实施计划，不另建 spec。旧 Phase A—F 记录保留，本文使用 L1—L4 编号，避免混淆旧工作进度。

## 1. 先理解我们到底要改变什么

### 1.1 玩家应看到的结果

玩家可以在三维空间留下水、毒液和粘液。稳定后它们继续可见并参与玩法，走入液体不会导致整块水面换形。液体可在上下分开的洞穴分别积存；上层开口后，下层能收到流出的液体，上层水位逐渐下降；堵口后流动停止，两个区域再次稳定。

**2026-09-26 用户确认补充：** Norn 是卡通风格，允许较粗的液体轮廓、大尺度起伏和较少微小飞溅；优先保证场上能容纳足够多的长期液体。自然场景应在初始化时就包含水池、毒池、粘液区，法术只是改变物质世界的一种输入。天然液体与法术生成液体使用相同材料身份、查询和反应规则，不能将天然湖泊降为没有 Gameplay 的水面装饰。规则空方格、Chunk 方形切口、闪烁和秒级显现不属于可接受的卡通化取舍。

我们接受简化的流速、压力、波浪和延迟结算。优先保持材料身份、数量归属、反应结果和视觉连续。没有必要逐帧计算湖底每一格，但必须知道流出去的液体由谁扣除、由谁接收。

### 1.2 当前证据与尚未证明的部分

| 事实或判断 | 证据与限制 |
|---|---|
| 角色接触读取曾请求整块 Dormant 唤醒 | 已在此前修改中移除；用户反馈走动触发的抖动改善 |
| 休眠网格默认每种材料每三帧重建一块 | 当前 DormantLiquidCellRenderer 的调度；60 FPS 下约 20 块/秒是理论吞吐，不是本次实测 |
| 粒子转为 Cell Amount 后不保留完整粒子形状 | 当前归档与恢复路径；外观连续性不能仅靠统一 Shader 保证 |
| 查询和反应接口含粒子量化概念 | ILiquidOccupancyReadOnly 要求 AmountUnitsPerParticle，不能直接充当新后端的通用契约 |
| 空方格和多水时延迟存在 | 用户截图和反馈；不能仅凭截图确定每个孔洞的根因 |
| PBF 有多轮邻居、约束、碰撞与表面构建工作 | 当前 GpuPbfFluidRuntime 与 GpuLiquidSurfaceRenderer；没有新 Profiler 数据，不能宣布 GPU 是唯一瓶颈 |

旧计划解决了不少容量与生命周期问题，但将休眠表现退化为 Cell Proxy 的取舍不符合现在要求。新计划先解决表示稳定性，再谈大规模压缩，避免继续用更多补丁掩盖架构差异。

### 1.3 四个概念不能混为一谈

- **数量权威（Authority）**：哪一处数据有权决定液体实际数量。
- **模拟活动（Activity）**：哪些数据需要在本轮执行流动或反应。
- **可见性（Visibility）**：哪些表面需要提交给相机。
- **存储驻留（Residency）**：哪些数据目前在内存中，哪些使用紧凑表示。

同一片液体可以保留权威数据、停止流动更新、持续显示。玩家转动相机不能改变其数量；角色读取 Wet 不能自动把整个水体展开。

## 4. 核心数据与算法：为什么这样设计

### 4.1 数量单位与材料容量

物质量单位沿用 GMU 的业务含义，但新模拟不通过 particle count 定义它。L1 初始建议同尺寸格子满容量为 255 GMU，以便对接已有 byte 接触读取；这是待校准的初值，不表示旧 GPU 中 255 GMU 必然具有相同几何体积。

权威计算使用足够宽的整数和 checked 边界；总量审计使用 ulong。逐格单材料值可采用紧凑类型，但中间加减不能在 byte 上溢出。低流速产生不足 1 GMU 的余量时保留固定精度累计值，达到单位后再转移，避免粘液永远不流或每 Tick 凭空舍入。

相同格子可包含多个材料份额。L1 采用启动时按液体 Catalog 建立紧凑材料索引，在预分配 Chunk 内保存各材料量；占用容量按所有液体之和判断。新增材料需要重进 Play 重新构建配置，不支持运行中扩展 Catalog。成本随液体种类数增加，必须显示内存预算。

原型使用等体积 GMU：不同材料相同 GMU 占据相同格子容量，流速差异由行为数据决定。暂不模拟真实密度分层。未来若增加比体积，需要显式迁移容量公式，不能只改颜色或 PBF 密度参数。

已有状态查询返回 byte，保持代表当前材料份额；它是 Gameplay 投影。反应的扣除和稳定区域账本读取精确数量，不能用饱和截断后的 byte 做大水体记账。旧 PBF 的 8 GMU/particle 保持旧后端兼容，不成为新后端舍入步长。

### 4.2 局部流量交换

每次 Tick 从同一份旧状态计算候选流量，再统一提交。每对邻格共享面只由一个方向负责，避免 A→B 与 B→A 重复处理。下落优先、水平铺开随后；复杂压力留到后续模型，L1 不承诺连通器正确性。

候选步骤：

1. 排除 Solid 面与不支持的边界；格子地形取缓存，不逐面调用 Physics。
2. 根据重力方向、填充差和材料流动参数提出候选量。
3. 按来源总余额限制所有流出；按目标空余容量限制所有流入。
4. 多来源争同一容量时按确定性权重缩放，再分配整数余量；不能按遍历顺序让首个来源抢完。
5. 为参与的跨页单元预留空间和提交预算，统一写入增减量。
6. 标记真正改变的格子、邻格和表面脏区域。

基本不变量：无反应时 `总量变化 = 外部注入 − 外部移除`。反应通过明确规则记入消耗／产出，不能假定所有反应严格体积相等；产物无空间时预留、延期或拒绝整个事务，不能静默丢弃。

这是一种面向玩法的局部流动近似，不应冒称完整 Finite Volume Navier–Stokes 求解。格子占据与流量足以覆盖第一轮水滩、下落和小容器；大水体响应是 L2 的独立问题。

### 4.3 活动预算和休眠

活动集合用预分配队列和标记去重。休眠必须持续若干 Tick 没有有效交换，且没有待处理写入／反应。满格不自动休眠；空格也可能是接收流量的活动邻居。

需要区分“时间预算没轮到”与“已经稳定”：没处理过的页不能计入稳定 Tick。跨页交换双方属于一个提交单元，预算耗尽时保留请求，不只扣源不加目标。采用固定模拟步长、有限补算次数，过载延迟量可见，禁止卡顿时无限补 Tick。

调度考虑用户附近的新写入、真实反应和最长等待时间，防止远端永久饥饿。相机可见性只影响几何优先级；远处已经发生的排水事件不能因为相机转开而立刻停止。是否允许极远区域降低频率，要用一致的累计时间规则说明。

### 4.4 通用材料与反应

LiquidBehaviorProfile 保存流动率、侧向扩散、稳定判定参数和是否允许稳定区域压缩。不要把旧 PBF viscosity 数值直接当作新算法参数：单位和数学意义不同，需分别调参。

同格与相邻格的反应继续依据现有 MaterialReactionCatalogSnapshot。水、毒液、粘液的身份不可平均。L1 允许按材料份额共存，但不承诺真实分层；渲染可以按份额选主要外观或混合属性，不能在同一表面画三层重叠透明 Mesh 造成 Z-fighting。选定的视觉混合策略不回写材料量。

新后端反应不应假扮 GPU Occupancy。抽出无 particle scale 的读取／命令提交协议；旧适配器继续执行旧粒子量化，新适配器按 GMU 预留和提交。Damage、状态与火元素写入必须与消费事务一致，失败重试不能重复伤害。

### 4.5 统一表面与显示时效

格子数据在 World Space（世界坐标）定义形状；每个 Chunk 的 Mesh 可存 Local Space（相对块原点）的顶点，再用矩阵平移到世界。相邻块必须用相同世界位置采样同一份标量场，法线也来自一致邻域。Halo 是为了取得边界外样本，不是复制额外水量。

只生成液体／空气等外边界，不生成深水内部的面。Surface Nets 为首选复用候选，不预定现有 Water Builder 原样可用。若浅液体阈值造成孔洞，要明确调整表面重建规则；不能用视觉填洞偷偷改变 Gameplay，视觉与实际占据误差必须受限。

新调度分两类：尚未显示的新区域优先；已有网格的细节更新可延迟。旧网格保留直到替代版本就绪，但若液体被实际移除，不能无限显示幽灵水面。移除、跨表示交接和邻接变化进入高优先级批次；相关边界由同一输入版本生成并成组发布，不能一边新一边旧长期共存。

缓存版本应按受影响页更新，不因某处发生一次归档让所有材料、所有页重新复制。重建预算同时考虑工作量、累计耗时和最老等待年龄；不恢复每三帧固定一块的唯一调度方式。L1 先提供可诊断的小粒度任务；若一个任务本身超过预算，应缩小或拆分任务，不能只延迟整个昂贵任务。

### 4.6 稳定区域与动态格子的转移

稳定区域拥有未转出的水量；局部格子拥有已提交接收的量。Prepared 状态只是预留，不新增数量权威。事务顺序是验证来源版本与余额、预留接收空间、提交双方变化，失败取消预留。实际提交一次完成，不跨帧暴露半边结果。

账目示例：上池有 1000 GMU，申请转出 10，局部只可接收 6；实际转移 6，上池 994，局部增加 6。未转出的 4 从未离开上池。已接受的外部注入可以处于有界 Pending 队列，必须纳入系统总账并记录等待；排队不是无限容量承诺。

### 4.7 容量曲线、出水与水面插值

L2 容量曲线把高度 h 映射到可容纳体积 C(h)。结合 GMU 体积换算，由剩余量求目标水位。曲线必须单调；低于池底、达到溢流高度、空池都要有定义。多段竖直空间可以记录，但上下不连通区域不能因为共享 XZ 坐标合并。

出口以可调、有限的工程近似估算流量：有效开口面积、上下游水头差、材料流动参数共同决定，再受接收容量限制。可参考重力出流的平方根关系，但不同材料和离散尺度需校准，不能宣称真实液压。下游淹没出口时减少有效水头；无有效水头时不继续机械排空。U 形管、虹吸和密闭压力不在 L2 承诺范围。

剩余水量按已提交转移更新，平衡水位低频计算。画面可在目标间插值，但插值不能生成新的权威量。定义最大可接受岸线误差；超过阈值立即刷新。接触查询使用权威占据，允许的小视觉误差要受控，不为了画面额外改账。原型先不增加复杂预测模型。

稳定区域很大时，显示也不能每次水位改变就重网格整个深水体。L2 简单容器复用自由液面拓扑并更新高度，岸线跨容量层时只更新受影响边界。任意形状对应的通用几何优化属于 L3，不能把矩形池结果外推成任意洞穴性能。

### 4.8 自动识别不是“Flood Fill 有水格子就完事”

L3 需要识别连通液体、地形约束、自由表面和可能的溢流通道。单纯搜索已有水格子不能获得注水后会占据的新空间，也无法定义容量曲线。搜索必须有空间上界、工作预算和地形版本；遇到开放边界或资格不明时拒绝压缩，继续格子表示。

候选识别不修改现有权威；完成后再次确认输入版本。发生改变则失效，避免把旧地形的湖盆提交到新世界。快速变化区域设冷却，防止反复申请／取消占满预算。

压缩／展开要预留接收存储，按可独立接管的区域推进；任何未完成部分仍由原 owner 服务。不能因为没有足够展开内存而删除稳定区域。遇到容量不足保留权威、暴露待处理状态，避免假装完成；L3 必须评估这种延迟是否破坏玩法。

### Task L3.3 封闭不规则湖盆与按区域合批水面（开发中，待集中验证）

**问题与选择：** 单台阶矩形容量曲线无法描述凹凸岸线；逐行绘制又使 Draw Call 随岸线复杂度上涨。先给显式 Authoring 增加平底列掩码，每个被纳入的列都有相同高度的空体积，单一 `ulong` 数量按层累计、按列排名精确分摊；这保留单 Owner、可查询和低深水成本。`bool[]` 只在加载时从静态 Solid 生成，运行时查询使用预建排名表；同行连续列先成行段，相邻行的同宽行段再合并成矩形 Patch，Renderer 把同一区域的 Patch 放到一张 Mesh，改变水位仅更新 World Space 平移矩阵。与逐格 Mesh／粒子相比，它用固定岸线几何换取低模拟和低提交成本，但无法自行表示斜底、外部无墙的开放浅滩或任意实时侵蚀。

**接入与文件：** `LiquidCapacityCurve.cs` 保存列排名、每层前缀和行段；`StableLiquidRegion.cs` 将 `Contains` 收紧到掩码；`StableLiquidRegionRuntime.cs` 限制总 Surface Patch 数、排除掩码外的动态物质、按行段输出只读面片，并允许凹岸线格作为出口边界；`StableLiquidRegionAuthoring.cs` 用 World Bounds 选择搜索区，仅接受下有 Solid 地板、整列空格、周边墙直到最大水位的形状。`LiquidWorldRuntime.cs` 与 `LiquidContracts.cs` 暴露预算及注册入口，`LiquidWorldProfile.cs` 和原型资产给出总 Patch 上限；`StableLiquidSurfaceRenderer.cs` 预建视图池和 List，按 RegionId 合为单 Mesh，静止 Tick 不重新提交顶点。`GridLiquidPrototypeSetup.cs` 在显式运行生成菜单时添加带凹口的小湖，避免自动改当前 Play 场景；`StableLiquidExpansionTests.cs` 增加列外排除、总量重建和 Patch 预算样例。

**验证与回退：** 本批依用户要求只写开发代码；后续一次性检查编译和定向 EditMode，再在原型中检查岸线、出水、三材料、Total GMU、Draw Calls、首次可见延迟及 `GC Alloc`。新的 `_deriveFootprintFromSolid` 默认关闭，原矩形和台阶数据继续走旧容量构造；关闭该开关即可回到旧场景表示。明确不把“人工指定封闭凹岸线”算作 L3 Gate 中的“自然开放湖泊自动稳定”；后者仍需有界候选搜索、局部排水／分片拓扑交接和性能证据。

### Task L3.4 有界不规则自动候选与原子数量交接（开发中，待集中验证）

**设计步骤：** 自动候选从已经满格的材料格启动，只把同一高度区间内“整列满格、下有 Solid 地板、上方自由”的相邻列加入有界 Flood Fill。每 Tick 探索量按最大验证格数扣减，队列、占地掩码和去重集合在 Runtime 初始化时预分配；超出候选格数、发现开放侧边、出现异种／部分填充或地形不匹配时保持动态 Store 权威，并按版本暂记失败范围。发现完成后按包围盒所在 Chunk 与静态版本等待安静期，再分 Tick 复查每个包含列与四边封闭条件。最后准备同量稳定区域，动态 Store 先预检整份掩码的满格和材料唯一性，再在一次主线程调用内提取，之后提交稳定 Owner。反向撤回仍受 L3.2 的一次展开预算约束。

**边界与取舍：** 只自动压缩平底、等深、满格、静态封闭的湖盆，不把开放浅滩、斜底或部分填充的池子误判成静水。候选搜索可跨 Tick，但最终提取是有界的单次事务；Profile 限制最多 65536 候选格，原型默认 8192。超过预算时保留动态格子，不能用丢水换帧时间。相同材料的几片湖各自独立候选，Water／Poison／Sticky 共享算法。`StableLiquidRegionDetector.cs` 负责候选、版本和验证；`LiquidVolumeStore.cs` 提供掩码预检后提取；`StableLiquidRegionRuntime.cs` 准备新区域；`LiquidCapacityCurve.cs` 从可复用掩码复制形状；`LiquidWorldProfile.cs` 给硬上限；`StableLiquidRegionCandidateTests.cs` 记录凹岸线、开口后封闭及数量不变案例。本批不运行测试，L3 Gate 仍依集中 Editor／Profiler 证据决定。

**超限回退：** 跨 Tick 搜索若遇到 Store／静态版本变化立即取消，避免把不同时间的湖岸拼成同一个候选。大于候选容量的湖泊把已经探索的满格按每 Tick 验证预算分批写入每材料预分配的负面缓存；缓存满后暂停该材料当前世界版本的自动搜索，下一次数量或地形版本改变才重试。超限水量始终留在动态 Store。这是 CPU 安全阀，代价是同一版本里更小的封闭湖盆可能等待下次变化才被发现；集中测试需同时看超限湖泊的候选拒绝次数、实际动态成本与小湖发现延迟。

### Task L3.5 变深湖底、自然岸线与有限速排水（定向 Editor 检查已完成，Player Gate 待办）

**目标与资格：** 自然凹地的湖底可逐列高低不同，水面仍近似水平。先支持每个 `(x,z)` 列只有一段由 Solid 地板托住的可容水空间；湖面外缘在当前水位必须由地形封住，明确的出口交给现有有限流量模型。洞穴顶、互相贯通的多层水系、移动地形及开放流动河面保留动态 Store。初版自动候选只接管总 GMU 与每列占用能准确重建的静止区域；不为了让 `StableRegionCount` 增长而平均掉无法解释的水量。

**数据设计：** 扩展 `LiquidCapacityCurve.cs` 的平底列掩码为“有效列 + 逐列底高”的容量表。按 Y 层预计算该层可容纳的列数、累计容量和列排名；`QuantityAt` 仍从单一 `ulong` 账本推导，不分配深水对象。水位跨过某列地板时，岸线占地随之扩张或收缩。优先复用显式 `StableLiquidRegionAuthoring.cs` 做受控原型，再让 `StableLiquidRegionDetector.cs` 识别同样资格；这样可以先验证容量和画面，再引入自动搜索的不确定性。每次动态转稳定继续采用“准备容量→逐格预检→一次提交”的数量交接，失败原 Owner 保留。

**表面与出流：** `StableLiquidRegionRuntime.cs` 只输出当前水位真正有水的 Surface Patch。`StableLiquidSurfaceRenderer.cs` 在水位跨整格地形层时重建该区域岸线 Mesh；层内的小水位变化仍只改 World Space 矩阵。开放出口由具体边界和高程产生，不因为外圈有一个空格就把整湖立刻摊平成外部水位；每 Tick 从稳定账本扣除的 GMU 受通道宽度和下游容量限制。底层格在排水后休眠，直到受扰动才重新参与局部模拟。

**取舍、文件和 Gate：** 单一湖泊在极浅水时可能出现几何层切换，需要画面检查是否突跳；多个盆地相通但水位不同应先分区，不能合并成一个曲线。显式 Solid 底高、自动候选、动态岸线 Patch 版本和独立原型生成入口已写入代码，新增 `LiquidCapacityCurveTests.cs` 与变深候选案例。依用户要求，本批没有运行 Unity 编译、EditMode、PlayMode 或 Profiler，也没有生成新场景资产。用户下一次执行原型生成菜单后，集中检查 1080p Player 的水位跨层、出口排水、`GC Alloc` 及 `GridLiquid.AutoRegion.Prepare/Extract` 峰值。此 Gate 通过后再进入 L3.6 的大湖分片展开与区域间转移；此时不能宣称 L3 整体完成。

### Task L3.6 大湖局部地形修改与分片交接（开发中，集中验证待办）

**目标：** 打开一格大湖内墙时，仅受影响的局部片区转为动态 Owner，剩余深水仍压缩。交接单元必须有各自数量、Patch、版本和预留 Chunk；相邻片区以有限速通量保持联系。若预算不足，地形修改在发生前返回明确拒绝原因，不能在修改后才隐藏液体或偷偷删量。

**顺序与 Gate：** 先定义可独立撤回的分片边界和区域间事务账本，再实现受限局部展开，最后检查多次开洞／堵洞、相邻液体材料反应、表面无双画与数量总账。保持当前最多 1024 格的一次性展开为小湖后备路径；大湖分片未经集中验证前不接入正式 P7 地形破坏流程。所需改动以 `StableLiquidRegionRuntime.cs`、`LiquidTransferLedger.cs`、地形预检入口及两个 Renderer 为主，具体接口在 L3.5 容量和岸线表示稳定后收敛。

**本轮收敛的实现设计：** 对显式配置的变深湖盆增加可选 Chunk 对齐分片，默认保持原单区路径。注册期先按 XZ Chunk 边界裁剪原始逐列湖底，计算每个分片的容量曲线与初始 GMU，再一次性预检区域槽、Patch、Solid、动态重叠和单片展开预算；只有全部通过才提交，失败不留下半个湖。每片的 XZ Bounds 不跨 Chunk，因而旧稳定液面与新动态 Mesh 交接时不会因为共用一个 Chunk 而互相遮挡。高度过深导致单片超过 1024 格时明确拒绝本轮分片配置，待垂直分片或更细表面裁剪完成后再支持。

**运行期：** 同组相邻分片仅保存预计算的接触边，不在 Tick 扫整个湖。两片都稳定时按水位差、接触宽度和每 Tick 上限在两个数量 Owner 间事务转移；一片展开后，邻区只向展开片区的边界动态格有限速出流，动态格向稳定邻区回流沿用局部 Solver。地形调用方在修改 Collider 前预检受影响片的格数、接收 Chunk 和 Surface 预算，拒绝后几何保持原状。区域版本和原有 Renderer 路径分别跟随真实数量或拓扑变化，保持 MaterialId 身份。原型单独验证三种液体、重复开洞／堵洞、总账恒定、交接时无双画、Editor 与 1080p Player 的 CPU/GPU 与 GC；在这些证据齐全前，生产场景不启用分片。

### Task L3.7 接近平齐的部分填充湖面自动接管（代码已写，集中验证待办）

**问题和目标：** 原自动候选只接受每个水格都是满量的封闭湖。实际流动停止后，深水底部往往满格，自由面顶层仍有 1～254 GMU；即使岸线和湖底完全符合 L3.4，顶层仍会让整片湖拒绝压缩。因此沿用已有有界 Flood Fill、安静期和单次 Owner 交接，允许“深层全满、同一顶层各列有同材料水、顶层接近平齐”的封闭湖盆。此能力通用于 Water／Poison／Sticky，不增加单颗 GPU 粒子的工作量。

**资格和数量：** 从已满水格寻找种子，只把紧贴其上的一层未满水格纳入候选；每个候选列之下仍要连续满格直到 Solid 地板，顶上必须自由，四侧在所在水层必须由相邻候选列或 Solid 封住。顶层不能混入其他材料；最低格量至少为单格容量的四分之一，各列最大与最小量之差不超过八分之一。这个阈值只限制压缩时的视觉拉平，不能被当作真实流体定律。跨 Tick 复核逐格求顶层真实 GMU，加上所有满格深层得出总账；稳定容量曲线接手时保留同一 `ulong` 数量，按当前总量生成统一近似水位。动态 Store 提取前重新扫描掩码的每一格，确认深层满格、顶层仍为单一材料，并精确对比预期总量，任何差异都在扣除第一格以前失败。旧 `TryExtractFull*` 的“必须全满”语义保留；新的 `TryExtractLevel*` 只给候选交接使用。

**文件与验证：** `StableLiquidRegionDetector.cs` 管候选拓扑、顶层平齐阈值与精确量；`LiquidVolumeStore.cs` 执行全量预检后的原子提取；`StableLiquidRegionRuntime.cs` 接受不超过区域容量的压缩数量；`LiquidWorldRuntime.cs` 与 `GridLiquidPrototypeCapture.cs` 暴露 `AutoPartialSurfaceCompressed` 累计值，区分新路线实际命中和旧全满压缩；`StableLiquidRegionCandidateTests.cs` 新增变深封闭湖未满顶层守恒、明显倾斜湖面拒绝、错误预计数量不扣除三例。`GridLiquidPrototypeSetup.cs` 新增独立 `Create Partial Surface Prototype` 菜单，创建三座彼此隔离的 6×6×2 格湖：底层 255 GMU、顶层 204 GMU，每座 16524 GMU、全场初始应为 49572 GMU；三材料共用现有 Shader／Material，但由各自行为数据驱动；每座湖配一个 Deposit Probe。场景生成只在资产缺失时执行，既能展示动态 Store 到稳定 Owner 的交接，也不重复覆盖已调过的场景。`GridLiquidPrototypeCapture.cs` 支持单独打开与构建该场景；`GridLiquidPlayerBenchmark.cs` 在 Development Player 记录投水前后的自动部分水面接管次数、种子扫描量、数量、P50/P95、CPU/GPU 与 GC，输出独立 `grid-liquid-partial-result.json`，不覆盖普通水滩和分片湖结果。场景资产已落盘，Player 尚未构建，二者都没有 Play／Player 运行证据。集中检查时先运行新增 EditMode 用例，再打开独立湖盆，核对压缩前后 `TotalQuantity`、`AutoPartialSurfaceCompressed`、区域数、视觉水位和首帧 Mesh 交接；打开岸线缺口应继续拒绝压缩。**Unity 已导入生成器，末次 Assembly Reload 后无新的 error CS；EditMode、PlayMode 与 Player 尚未运行。** 浅到完全没有满格种子的水滩、开放河道、强烈倾斜水面及超出候选预算的大湖继续由动态 Store 持有；未解决的 `AutoRejected`／`AutoSeedInspections` 静止增长须由下一次已安排的版本采样定位，不能宣称本任务顺带修好。

### 9.1 性能与时效目标：是验收目标，不是保证

基准沿用当前电脑、1920×1080、60 FPS；总帧预算约 16.67 ms。CPU/GPU 耗时不能直接相加，也不能把一个 Shader 很快当作整个功能达标。

建议第一轮负载固定格长 0.25 m、ChunkSize 8（沿用当前默认，仅作为可比较起点）：小水滩、约 8×8×2 m 静水体、三种液体同场；L2 再增加约 16×16×4 m 的明确容器。记录注入量、活动格子、实际分配和表面页数，不仅记录“粒子数量”。不得通过临时降低分辨率把新旧结果混为同一条件。

用户允许粗粒度后，0.25 m 只作为对照起点，不作为最终精度要求。提供启动时选择的较粗候选档位，例如 0.5 m；禁止为此增加运行中的动态分辨率迁移。比较时保持相同世界空间体积、注入体积和操作，不机械保持相同格子数或每格 GMU：格长改变会改变单格体积，必须显式换算容量与注入量，并同步检查接触和反应投影。记录两种不同证据：“相同分辨率的实现对比”与“降低精度后的产品取舍”，不混报性能收益。

模拟粒度、表面采样粒度、更新频率和材质复杂度分别配置。先接受更粗轮廓与更简单反光，不同时开启昂贵的各向异性重建、折射和多层效果。粗格可能封闭细通道、削弱浅水或岸边精度；用角色脚下接触与可通过的最小缺口约束可接受档位。较大粒度不是规避空洞、延迟和数量错误的理由。上述档位由用户在阶段验收时比较，不增加代理自动跑批。

建议用户记录的最小指标：

- 新写入被接受到首次可见的延迟，正常负载目标不超过 100 ms；秒级属于失败。额外记录投射物实际命中到入队的时间，防止把动画延迟归入 Renderer。
- 稳定输入不变时不应持续重建所有网格或扫描所有内部格子；轻量调度维护可以存在。
- 热路径 GC Alloc 目标 0 B；这是需要用户 Profiler 验证的目标，本轮没有证据。
- 看总帧时间的典型值与高分位、最大单次几何任务耗时、最老 Pending／Dirty 年龄。用户可先以是否明显卡顿与秒级加载反馈，详细数据只在存在问题时补充。
- 数量审计按材料记录注入、待提交、动态、稳定、显式移除、反应消耗／产出；不同反应不强求各材料量不变。

性能失败时先定位模拟、几何构建、上传、绘制、队列等待中的哪一段。不得再只提高预算到很大、删除旧液体或改 GMU/particle 来宣布优化成功。

## 14. 2026-09-27 Play Mode 反馈后的 L1 表面失效修复

用户已授权代理调动 Unity。2026-09-26 原型场景实测：两次水注入共 2040 GMU 均保留，Pending／Rejected／Overflow 为 0；扩散期最近 300 帧 P95 最高 47.8 ms，水表面有 48 个 Dirty View 时毒液表面也有 35 个。静止后活动格子与 Dirty View 归零，但 `StableRegionCount` 仍为 0、常驻 Chunk 为 111；该数据来自 Editor Play Mode，不能当作 1080p 独立 Player 性能结论。

修复范围先限定在 L1 表面失效协议，避免把尚不支持的开放水滩硬塞入矩形封闭湖盆：

1. `LiquidVolumeStore` 保留原有全局 Chunk 版本供事务／自动候选校验；另增加每材料 Chunk 表面版本及每材料全局表面版本。数量变动只标记该材料；混合格主导材料改变时同时标记失去／获得可见表面的材料。静态地形改变仍允许罕见的全材料失效，确保没有已驻留 Chunk 的相邻墙变化也能刷新。
2. `ILiquidSurfaceReadOnly`、`LiquidWorldRuntime` 和 `LiquidSurfaceRenderer` 传递带 `MaterialId` 的版本。Renderer 只在自身材料版本变化时检查已建 View；候选集合的既有独立版本保持不变。这样水波不会仅因共享版本让远处的毒液 Mesh 重建，同时保留跨 Chunk Halo 和混合格正确性。
3. 用定向 EditMode 测试验证水改动不脏化毒液独占 Chunk、混合格主导切换会脏化双方、静态地形失效和 Chunk 槽位回收后版本不误命中。完成代码后集中做一次 Unity Play Mode 注入与 Profiler 对照，不重复全套测试。

开放水滩的 `StableRegionCount=0` 不是简单开关错误：当前 `StableLiquidRegionDetector` 明确要求全满矩形、平底、四壁封闭，现有 `LiquidCapacityCurve` 和 `StableLiquidSurfaceRenderer` 只能可靠接管这种拓扑。L3 要支持自然开放湖泊，需要先定义岸线容量曲线、出流边界和接管／展开事务。未完成这些前保留动态格子权威与休眠，不能为了提高压缩数字引入看似静止但无法正确排水的湖面。后续性能 Gate 要分别看静止 CPU、常驻内存、渲染成本以及再激活时的延迟。

**同轮求解预算补充：** 按材料版本修复后 Unity EditMode 4/4 通过，但一次注入仍激活约 7500—9700 格，扩散时 P95 约 50 ms。曾试在每次 `Wake` 调用 `HasAnyLiquid` 排除空邻格：活跃队列降至约 2900，但 `ElementWorldRuntime.Update` 慢样本均值反升至约 44 ms，原因是每次成功转移都会同步查询约 14 个邻格的 Chunk；此尝试已撤回，不应把小队列数字误认为更快。

已采用两项明确有界的近似：每材料配置 `SideFlowDeadbandGmu`，小幅水平量差不再继续搬运，GMU 仍留在原 Owner；原型的每 Tick 处理上限从 4096 降至 1024，让突发流动分多 Tick 完成。Water／Poison 容差为 8 GMU，Sticky 为 4 GMU。前者控制无意义的低幅扰动传播，后者限制单 Tick CPU 峰值。代价是静水可保留细微不平衡、流动达到最终形状需要更多 Tick。

**集中验证结果：** `LiquidSurfaceVersionTests` 4/4、`LiquidFluxSolverDeadbandTests` 1/1 通过；相关 C# 程序集编译为 0 错误、0 警告。独立原型场景在原有 122400 GMU 基础上向空地注入 1020 GMU，最终总量 123420 GMU，Pending／Rejected／Overflow 均为 0；约 3 秒和约 10 秒采样时 Resident Chunks 为 16、Active Cells 和 Water／Poison Dirty Views 均为 0，最近 300 帧 P95 分别为 19.06 ms 与 18.86 ms。画面截图可见独立水滩，但单张静态截图不能证明流动过程无闪烁。此数据是 Unity Editor PlayMode，尚不能推出 1080p 独立 Player 稳定 60 FPS；P95 也仍高于 16.67 ms 目标。原始预置水池依然可见规则边界，开放湖泊仍是动态格子，并未得到 L3 稳定区域压缩。

**下一 Gate：** 在目标 Player 建立 1080p 的 CPU／GPU、GC Alloc 和首次可见延迟基线；随后为开放自然湖泊设计可验证的岸线容量与局部展开／排水交接，验证角色涉水、三材料反应和实际 P7 施法。性能不达标时先用 Profiler 区分 Solver、网格重建和透明绘制成本，再决定是否引入更粗格长、Jobs／Burst 或新的表面路线。

L3.2 的第一道安全边界限定为**离散地形操作前的有界展开**。调用方应先告知目标格即将变为 Solid 还是空格：若新 Solid 会压住现有液体、区域已有异种动态覆盖、所需动态 Chunk 超容量，或区域体积超过单次展开预算，则拒绝这次修改，稳定 Owner 和数量保持原状。可展开时先验证全部目标格及所需页数，在同一主线程调用内将旧区域临时从读取路径撤出、把同量 GMU 写入动态 Store、成功后关闭其出口；任何写入失败则撤销已写格并恢复旧 Owner。几何修改者最后调用原有静态缓存失效入口。这个限定保住数量和可见权威，但大湖内部破坏及分片展开仍是后续 L3 Gate，不能称为任意地形支持。

同一阶段补齐稳定区域的写入边界：法术命中湖内已满单格时，先按**整片区域的剩余容量**入账，不能先被单格 `FreeCapacity=0` 拦住；半径很小的请求每 Tick 只访问每个候选位置一次。局部流动进入湖盆也直接转给稳定 owner，即使入口高于当前水面，最后的可见水位由容量曲线决定。稳定区域初次注册拒绝包围盒中已有的动态液体；以后动态格进入或离开时，以空／非空转换维护混合占用计数，临时覆盖消失后可恢复吸收。这些仍是代码路径，数量及画面效果待集中 Gate 验证。

## 17. 集中 Gate 发现的两项局部修正（2026-09-28）

## 19. L4.3 动态表面成本收口（2026-09-30）

**证据与目标：** `LiquidVolumeStore.CopyChunkKeys` 仍将实际页扩成 Halo 集合，Builder 随后只保留实际含液体页；最大候选数组也因此按 `MaximumChunks × 27` 预留。Halo 是构建时读取相邻格的范围，并不要求空页拥有 Mesh。旧 Builder 在每格的角点、边点、侧壁判断中重复读取相同格子；即使邻域完全等高，仍生成九顶点、八三角形的顶面。这些是读码确认的冗余，不把它们自动判为所有闪烁的根因，也不预先宣称 FPS 提升。

**实现与取舍：** 保留原接口和数量权威。候选直接复制材料总量大于零的唯一 Chunk，容量变为 `MaximumChunks`；跨页接缝仍读取全局坐标邻居与原邻域版本。Builder 在初始化时预留一格厚 Halo 的动态／组合高度与版本数组；每次 Build 推进本地版本，按需读取每个邻格一次，避免稀疏水滴为了缓存而扫描整片页。只把已有支撑、无上方覆盖、九点完全同高且高于薄膜保护高度的内部顶面标为可合并，逐层执行 Greedy Meshing；岸边、洞边、起伏和空中液滴保留旧几何。世界位置不改，平面 `normalWS` 仍向上，Fragment Shader 继续按世界位置产生波纹；现有 Vertex Shader 无顶点位移，因此大 Quad 不会删掉几何波浪。不同 Chunk 之间不合并，保留局部失效和 View 调度。代价是每个 Builder 多预留约 `16 × (ChunkSize+2)^3 + 4 × ChunkSize²` 字节缓存，不宣称减少透明 Fragment／Overdraw 成本。

**准确文件：** `Scripts/ElementField/Liquids/LiquidVolumeStore.cs` 精简候选并移除只供 Halo 的范围维护；`LiquidContracts.cs` 明确候选语义；`Scripts/Rendering/ElementField/LiquidSurfaceMeshBuilder.cs` 加按需采样与平坦区域合并；`LiquidSurfaceRenderer.cs` 保留缓存 Mesh 并补几何只读计数；`Tests/ElementField/LiquidSurfaceVersionTests.cs` 补候选正确性；新增 `Tests/Rendering/LiquidSurfaceMeshBuilderTests.cs` 检查三材料平面成本、洞口、起伏、空中液滴、负坐标接缝与缓存更新。无需新美术资源，沿用现有 Material／Shader；Unity 自动生成新脚本 `.meta`。

## 27. 卡通浅滩圆肩调校（2026-09-30）
