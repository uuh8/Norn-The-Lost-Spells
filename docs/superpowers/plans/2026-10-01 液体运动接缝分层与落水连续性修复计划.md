# 液体运动接缝、分层与落水连续性修复计划

> 2026-10-01 后续实测边界说明：本计划中的“单格仅顶部材料自由面”没有实现用户要求的真实上下液层，同密度按数量混色也不在旧测试覆盖内；135/135仅表示本文旧规则的自动化验证通过，不表示最新截图问题已解决。新的分层/混色、斜坡连续运动和GPU连续外壳方案见同目录《2026-10-01 液体密度分层混色与连续输运重构计划.md》，该新方案当前待确认。

当前任务来自用户四项实测反馈，沿用已授权的液体开发范围。用户已确认：毒液浮在水上；水、毒液、粘液应有清楚的流动差异。保留 0.5 m Gameplay 粗格、510 GMU 容量和现有体积倍率，不重新引入全湖粒子模拟。开发后集中检查代码与关键回归，再交给用户检查真实观感。

## 1. 现象、源码证据与修复目标

1. 运动时出现方形接缝。当前 Shader 对合并 Quad 和四分之一格细分面分别做 Vertex 位移；虽然共享 World Space 正弦，长边的线性插值与细分边不一致。另一个原因是 Renderer 逐页直接提交，邻页可能对应不同模拟 Tick。目标是取消不兼容的 Vertex 起伏，以 Fragment normal 保留波动光照；动态页从冻结的数量/运动快照构建到备用 Mesh，完成后成批交换。
2. 混合液体抖动。Mesher 用“本格谁的 GMU 最大”决定可见材料，同一格的份额交叉就会换面；各材料的独立外壳还可能重叠。目标是由 Density 决定上层身份，单格只生成最上层材料的自由面，自由面高度读取总液量，避免两层从同一底面重复长出外壳。被遮住的液量仍留在 Store。
3. 水像泥浆。正式 Water 的扩散保留比例为 0.4，且开新格时强制至少四分之一格，覆盖较低的 Side Flow 上限，使三种材料的扩散前沿更接近。目标是让开新格的最小液团量也受本材料流率约束，下调 Water 的保留比例、提高横向通量，Poison 居中、Sticky 更慢。水平推动用所有材料的总填充差，避免向已有其他液体的高液面继续灌注。
4. 空中时量少、闪烁。现有空中 Surface Nets 只有一个粗格的采样步长；液团重心跨节点时，重建的外壳体积随采样相位变化，有限预算下源页撤去和目标页出现也不同步。目标是只细化空中三维外壳的采样（不增加 Gameplay 粒子），用真实填充量的立方根决定液团半径；跨页迁移成批提交。增加不同下落相位的封闭性与体积变化回归。

## 2. 架构与取舍

`Game.ElementField` 保有 GMU、Density、局部交换和流动参数，新增只读表面分层契约。`Game.Rendering` 读取契约，自行持有预分配的快照与备用 Mesh；显示快照不写回 Gameplay。快照只复制选中动态页的必要邻域，以及稳定区域的稀疏 Surface Patch 行段，不复制湖底。静水继续保留低频拓扑和水位 Uniform 路径。收尾检查发现，若静水版本变化就取消批次，持续排水可能让批次永远无法完成；最终改为冻结行段与水位，完成后统一提交，再追赶新版本。

Density 只控制局部上下排序及等体积交换，不计算全湖压力。用户选择 Poison 浮在 Water 上，默认相对 Density 为 Poison 0.9、Water 1.0、Sticky 1.15；这些是游戏数值，没有声称对应真实物性。黏稠度（Viscosity）的玩家效果用每 Tick 通量和扩散保留比例近似，不添加昂贵的 Navier–Stokes 求解。空气中三者使用相同重力，因为自由落体加速度不由 Density 决定。

Rendering 细化会增加活动三维网格工作量，仍受已有共享时间预算控制。双 Mesh 与数量快照以明确的启动内存换取零热路径分配和原子显示；不能通过无限增大 CPU 预算消除接缝。快照可能有有限显示延迟，等待期间保留完整旧表面，绝不逐页挖空。持续落水的实际帧时间和视觉延迟需要用户最后在 Play Mode 验收。

不采用整体提高 Gameplay 分辨率、每帧全湖重建、简单把所有液体设为 Opaque、仅用 Polygon Offset 遮盖穿插，也不复制 Unity_Slime 的完整 PBF。它们分别会增加模拟成本、破坏当前预算、损失现有材质效果或掩盖真正的数量/拓扑问题。

- [x] 六个正式/对照 Behavior SO：设置 Density 和水快、毒中、粘慢参数；基础算法原型维持旧默认语义。
- [x] `LiquidContracts.cs`、新增 `LiquidSurfaceFrameSnapshot.cs`：只读分层与预分配冻结快照；生命周期明确为 Capture → Build → Commit，后续写入进入下一批。
- [x] `LiquidSurfaceRenderer.cs`：备用 Mesh、冻结批次、完成后统一交换，源/目标页迁移也纳入同一批；仍共享原有 CPU 时间预算，保留稳定区域交接。
- [x] `LiquidSmoothSurfaceMesher.cs`：总填充驱动可见自由面，液体自身支撑与较细的三维采样、紧凑采样范围及体积半径。
- [x] 新增 `LiquidDropletTemplate.cs`：初始化一次 Icosphere，孤立液滴按 GMU 体积缩放，避免球面半径随采样相位变化；相连液团仍走 Surface Nets。
- [x] `Stable/StableLiquidRegionRuntime.cs`：异种材料进入部分填充的稳定格之前，有预算地展开接触 Owner/分片，统一分层；预分配展开 scratch，注入、转换和 Solver 接触复用同一入口，远处静水不展开。输出稀疏行段的材料、纵向范围及 Owner 活跃标记。
- [x] `StableLiquidSurfaceRenderer.cs`：动态批次等待时保留旧稳定画面，完成后读取同一份冻结行段；不能同时绘制已退役稳定 Owner 和新动态壳。
- [x] `ElementLiquidDormant.shader`、`ElementLiquidSurfaceLighting.hlsl`：停止不一致的动态 Vertex 起伏，在 Fragment 使用解析斜率保留 World Space 动态法线。仍复用现有颜色、深度、Fresnel 和波纹。
- [x] 关键回归集中执行，修复编译/Shader 错误与实际失败；更新 living explainer、总体计划和地形制作指南。

## 4. 验证、Editor 操作与资产

不需要用户提供新纹理、模型或 VFX。沿用已存在的材质和程序化 World Space noise。新增 C# 文件由 Unity 正常导入生成 `.meta`，不伪造 GUID，不覆盖用户场景或 Cube。

开发验证分两次关键节点：最小回归先确认失败；完成后集中执行流动、数量映射、Stable Region、表面跨页闭合、数量与体积关系、快照冻结、热路径 GC 和 Shader import。若 Unity 在 Play Mode，先读取状态，不擅自保存或替换场景。检查通过只证明相应自动化边界，不能替代真实 Game View 观感或 FPS。

用户最后在相同地面连续注入三种液体，检查 Water 最快、Sticky 最慢；在水池中注入 Poison，检查上层持续绿色、边界不反复翻面；从高度 2～4 m 持续注水并走动相机，检查空中无周期性消失、落地没有突然增量；让水跨多个 Chunk 流动，检查没有沿 Chunk 直线露地板。Profiler 关注 `GridLiquid.Surface.MeshRebuild`、队列最老年龄、未显示候选、GC Alloc 与总帧时间。

## 5. 回退和调试记录

分层排序通过 SO Density 调整；旧 profile 缺字段时默认 Density=1，并用稳定材料 ID 破平局。新网格细度仅影响 Presentation，GMU 和游戏状态不随之改动。出现退化时先区分 Shader seam、批次等待、表面采样相位和 Solver 活动格成本，记录症状 → 证据 → 排除 → 根因 → 修复 → 验证边界，禁止只降低透明度让问题难以看到。

实施结果：初次两个关键回归均失败，捕获干格强制128 GMU覆盖流率，以及满格空中包最小外壳只有约4%体积。稳定水/毒液接触回归也先确认失败。最终集中 EditMode **135/135通过**（2026-10-01 06:02:42—06:02:46 UTC），覆盖13个相关fixture；报告 `Temp/ElementPerformance/liquid-motion-feedback-final.xml`。这不是将128、133、73等中间批次累加成总数。孤立液滴的三个数量、九个下落相位均封闭，体积约为GMU理论值的99.5%，相位变化接近浮点误差；该结论不推广为相连水柱或整个艺术网格精确守恒。

P7只读接线审计Failures=0（05:52:26 UTC），Capture确认正式场景Playing=False、SceneDirty=False；未修改用户Cube或保存临时场景。收尾还验证了稳定Patch预算：统一冻结入口只复制活跃Owner，退役旧面由Renderer缓存交接，不能挤掉其它仍活跃湖面。

正式/对照的 Density 分别为 Water1、Poison0.9、Sticky1.15；侧流基准112/40/6，干格保留比例0.14/0.28/0.55，按510/255容量缩放后侧流上限224/80/12 GMU/Tick。全场数量和0.5m/510GMU映射保持。暖机快照、网格与局部展开有零托管分配断言；没有运行新的完整Play/Player FPS或GPU基准，真实观感、排队延迟和全游戏GC Alloc待用户集中验收。制作指南第九节给出操作与指标，完整解析L4.15记录技术原因和调试证据。
